# FS-202：多表示实际召回与可解释融合

> 日期：2026-08-31
> 状态：已完成
> 上游：[下一阶段迭代开发计划 FS-202](2026-08-30-迭代开发计划.md#fs-202-将-kb-22-接入实际多表示召回)、[FS-201 chunk_signal](2026-08-25-chunk-signal多表示设计.md)、[N 路具名融合设计](2026-08-26-KB-2.2-N路具名融合设计.md)
> 影响模块：`fastsearch-core`、`fastsearch-pg`、`fastsearch-engine`、`fastsearch-server`、TypeScript SDK

## 1. 要做什么

把 FS-201 已落入 `{chunks_table}_signal` 的 ready 向量接入真实检索：

- `PgStore` 从信号真源按查询向量产生分信号类型的 recall list；
- Engine 将这些列表与既有 `keyword:user_text`、`vector:user_text` 一起交给 `fuse_n_with_sources`；
- `explain=true` 时，在 `SearchHit.sources` 中返回信号的 `model` / `model_version` provenance；
- 保持旧请求、旧数据和没有 PG 真源句柄的部署逐位兼容。

用户无需增加请求字段。已有请求在库中存在兼容维度的 ready 多表示信号时自动获得额外召回；可继续用
`fusion.method=weights` 按 `vector:image_caption` 等稳定来源名调权。

## 2. 为什么

FS-201 已解决多表示“存得下、作废准、删得净、CDC 不误读”，但检索路径仍只消费主表正文向量。
这使 caption、OCR、ASR 和图像向量仍只是审计数据。FS-202 要闭合从 PG 真源到真实 Engine 排名与解释的最后一段。

## 3. 决策

### D1：首版从 `real[]` 做 PG 精确余弦召回

采用 `embedding::vector <=> query::vector` 的无索引精确扫描，并按 `embedding_dim` 先过滤。
它只依赖仓库已经要求的 pgvector，不增加扩展；信号更新立即可见，也不需要把 signal 加入 chunks CDC。

不在本轮创建 typed ANN 列或分区表。`real[]` 无固定维度，贸然选一个 typmod 会让其他模型写不进真源。
规模数据和每路维度稳定后，再以基准决定“typed 列/分区表/引擎派生多向量索引”。当前接口不暴露 SQL，后续可替换实现。

### D2：主表 `vector:user_text` 保持唯一旧文本向量路

信号旁表中的 `user_text` 不作为第二条同名路重复融合；它仍用于审计和后续迁移。额外路为：

| signal_type | 公开 source |
|---|---|
| `ocr` | `vector:ocr` |
| `asr` | `vector:asr` |
| `vlm_caption` | `vector:image_caption` |
| `image_bytes` | `vector:image_bytes` |

这样没有信号的旧库仍严格是原两路，已有权重键也不变化。

### D3：只有可证明可用的行进入召回

只读 `status='ready'`、`embedding IS NOT NULL`、`embedding_dim=查询维度`、父 chunk
`searchable=true` 的行。ACL 与 Filter 复用主表下推 + Rust 精确后过滤规则。调用方仍需保证查询向量与信号模型处于同一空间；
`model` / `model_version` 会返回用于审计，本轮不增加逐请求模型选择。

### D4：provenance 是来源明细的可选加法字段

`SourceHit` 增加省略空值的 `model` / `model_version`。既有 keyword/主向量来源不输出这两个字段，
默认 `explain=false` 仍完全不输出 `sources`，旧 SDK 不要求同步升级。

## 4. 深模块与 seam

- `PgStore::signal_vector_search` 是 PG 模块的公开 seam：内部隐藏 SQL、维度/status 筛选、ACL/filter、
  精确排序、按 source 分组和 provenance 映射；Engine 不理解信号表结构。
- `Engine::search` 仍是用户/测试观察实际 N 路行为的公开 seam，只接收 PgStore 已形成的召回结果。
- `core::fuse_n_with_sources` 保持纯融合模块，不引入 PG 或模型概念；Engine 在融合后按 `(source, gid)` 补 provenance。

## 5. 不做什么

- 不建立 signal ANN 索引，不改变 FS-201 的 publication/CDC 决策。
- 不增加请求字段、逐请求 embedder 或模型路由。
- 不让 stale/failed/pending/unsupported 信号参与检索。
- 不在本轮生成信号；摄取 worker 产信号属于后续作业面。
- 不改变 rerank 模态能力；那是 FS-203。

## 6. 用户使用例子

```json
{
  "query": "毛利率趋势",
  "mode": "hybrid",
  "explain": true,
  "fusion": {
    "method": "weights",
    "weights": {
      "keyword:user_text": 1.0,
      "vector:user_text": 1.0,
      "vector:image_caption": 0.6
    },
    "default_weight": 0.0
  }
}
```

命中来源示例：

```json
{
  "source": "vector:image_caption",
  "rank": 1,
  "score": 0.93,
  "contribution": 0.6,
  "model": "clip",
  "model_version": "2026-08"
}
```

## 7. TDD 纵向切片与验收

1. **PG 召回 seam**：真实 PG 写入 ready/stale、不同维度和不同 ACL 的 caption 信号；公开接口只返回
   ready、同维、可见结果，并按分数降序、同分 GlobalId 升序，带 model/version。
2. **真实 Engine 三路**：同一请求实际产生 `keyword:user_text`、`vector:user_text`、
   `vector:image_caption`，`sources` 贡献之和等于融合分，caption-only 候选可以进入最终结果。
3. **兼容性**：未设置 source PG 或没有可用信号时，现有两路结果与来源逐位不变；
   `explain=false` 响应仍省略 `sources`，旧字段不改变。
4. **确定性**：信号插入顺序、同分行顺序和 recall list 组装顺序变化不改变最终排序；浮点累加继续按 source 稳定排序。
5. **安全性**：tenant/ACL 与 Filter 对 signal-only 命中不可绕过；`searchable=false` 父行不召回。
6. **契约**：OpenAPI 和 TS `HitSource` 将 provenance 标为可选；旧 JSON 仍可反序列化。
7. **回归门禁**：三份现有 relevance golden 不回归；新增真实多表示 Engine golden。
8. **收口**：fmt、clippy `-D warnings`、workspace tests、真实 PG 环境门禁、TS tests 全通过。
