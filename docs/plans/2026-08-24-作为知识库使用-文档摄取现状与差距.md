## 1. 结论（先纠一处前提）

提问的前提是"本项目似乎没有：①文档处理（提取内容和分片）②文档解析（docparse-rs？MinerU？）"。
读完代码后，这个判断**一半不成立、一半成立，而且成立的那一半比提问说的更要命**：

| 提问里的"缺失" | 实际情况 |
|---|---|
| ① 文档解析 | **不缺**。docparse-rs 已 `git subtree` 并入 `vendor/docparse/`（17 个 crate），10 种解析器 + PP-OCR + UniRec 表格 + VLM 区域识别都在仓内、可跑。**不需要 MinerU**（§6）。 |
| ② 内容提取与分片 | **不缺**。`docparse_core::chunk::chunk_document` 是带 page/bbox/heading_path 的版面感知分块器；CLI 另有一个朴素 `chunk_text` 给 md/txt。 |
| （提问没点破的真缺口） | **解析和分块都不在 server 里，在 CLI 客户端进程内**。server 只认"已经切好的 chunk JSON"。 |

所以**"把文档直接给 fastsearch，然后查处理状态、检索"这个期望，当前不成立**，缺的不是解析能力，是**把解析能力接到服务端的那条链路**：

- `[当前缺口]` **没有任何"上传原始文件"的 REST 端点**——`/v1/images` 是唯一收字节的入口，且只收单张图片。
- `[当前缺口]` **没有作业（job）概念**：`/v1/index` 是**同步**的，一个 HTTP 请求里做完"嵌入 → 写 PG → 写派生索引"然后返回。没有排队、没有重试、没有 job id。
- `[当前缺口]` **没有"处理状态"可查**：全仓唯一的状态字段是 chunk 级的 `image_vector_status`（图片向量那一路），没有文档级状态机。
- `[当前缺口]` **没有"列出文档"的端点**：只有 `GET /v1/chunks?collection=&doc_id=`（还必须配了 PG 才可用），要先知道 doc_id 才能查。

一句话定位：**fastsearch 今天的契约是"调用方拥有解析、分块与文档台账，fastsearch 拥有检索"**，
这个边界是[通用 chunk 管理 API 计划](2026-07-23-generic-chunk-management-api.md)明确写下的（"Parsing and domain hierarchy remain caller responsibilities"、
Out of Scope 含 "Parsing full documents or splitting text in the server"），不是疏漏。
要不要改这条边界，是**产品决策**，不是 bug 修复——见 §5、§7。

## 2. 现状盘点（带落点）

### 2.1 解析：能力齐全，但只在 CLI 进程内

`[当前已实现]` `crates/fastsearch-cli/src/ingest.rs` 的 `parsers()` 注册 10 个解析器：
PDF / DOCX / HTML / MD / CSV / XLSX / PPTX / SRT / EML / 图片。三个增强器串联，**每个都由 feature + env 双重门控，未配则恒等变换**：

| 增强器 | feature | env | 作用 |
|---|---|---|---|
| `apply_ocr` | `parse-ocr` | `FASTSEARCH_OCR_MODELS` | 扫描页/无文本层 → PP-OCR 抽文本（进程内 ONNX） |
| `apply_vlm` | `parse-vlm` | `FASTSEARCH_VLM_URL` + `_MODEL` | 表格区域 → HTML；另配版面模型则加区域级转写（外部 OpenAI 兼容服务） |
| `apply_tables` | `parse-tables` | `FASTSEARCH_UNIREC_MODELS` | 表格结构识别（UniRec，**非 VLM** 的确定性 ONNX） |

用法与分档见 [文件解析与摄取](../文件解析与摄取.md)。

### 2.2 分块：版面感知的确定性分块器，但旋钮没暴露

`[当前已实现]` `docparse_core::chunk::chunk_document_with(doc, ChunkOptions)`：
按版面 block 阅读序累积段落，标题维护 `heading_path` + `section_id`（父文档/auto-merge 检索的锚），
表格/图片作为独立 item 拼接进阅读序，图片 chunk 的 `text` 绑定相邻图注 + 上下文（`IMAGE_ADJ_GAP=40pt`、`IMAGE_CONTEXT_CHARS=300`），
小于页面 1% 的装饰图被过滤（`MIN_IMAGE_COVERAGE`）。每个 chunk 带 `page` + `bbox`——这正是 fastsearch `citation_id → {page,bbox}` 深链的来源。

`[当前缺口]` `ChunkOptions` 只有两个旋钮（`target_chars: 800`、`table_markdown: false`），**没有 overlap**；
且 `cmd_ingest` 调的是无参的 `chunk_document(&doc)`，所以**连这两个旋钮都没有从 `fastsearch ingest` 暴露出去**。
知识库产品通常要按语料调块长/重叠，当前只能改代码。

`[当前已实现]` 另有一条更朴素的路：`fastsearch_cli::chunk_text`（空行分段 + markdown 标题维护 heading_path），
供 `index-dir` 喂 `.md/.txt/.markdown/.text` 文件夹用。

### 2.3 三个摄取入口——**全部在客户端**

| 入口 | 谁解析 | 谁分块 | 送给 server 的是 |
|---|---|---|---|
| `fastsearch ingest <file>`（`--features parse`） | CLI 进程内 docparse | CLI 进程内 `chunk_document` | `POST /v1/index` 的 chunk 数组 |
| `fastsearch index <chunks.json>` | 调用方（仓外） | 调用方 | 同上 |
| `fastsearch index-dir <dir>` | 无（纯文本） | CLI 的 `chunk_text` | 同上 |

`[当前已实现]` 这是**有意的架构约束**，不是懒：CI 有 `hot-path-isolation` 硬门禁，对
`fastsearch-{server,engine,core,text,vector}` 五个热路径 crate 跑 `cargo tree -e normal | grep -qi docparse`，
命中即红（见 [devlog](../devlog/2026-06-28-CI热路径隔离与parse分档.md)）。
`crates/fastsearch-server/Cargo.toml` 里确实一个 docparse 依赖都没有。**任何"把解析塞进 server"的方案都会撞上这条门禁**。

### 2.4 server 的端点全表：没有文件、没有作业、没有状态

`[当前已实现]` `fastsearch_server::router` 的全部路由：

```
GET  /healthz /readyz /metrics /openapi.json
POST /v1/search  /v1/similar  /v1/assets/resolve
GET  /v1/asset/{cid}  /v1/asset/{cid}/bytes  /v1/object/{opaque}/bytes
POST /v1/index                       ← 收 chunk 数组（JSON），doc 级替换
POST /v1/chunks/batch-{get,upsert,delete}
GET  /v1/chunks?collection=&doc_id=  ← 列某个 doc 的 chunk（需 PG，否则 503）
POST /v1/images                      ← 唯一收字节的入口，且只收单张图
DELETE /v1/docs/{collection}/{*doc_id}
POST/GET /v1/collections ; GET/DELETE /v1/collections/{name}
        （全局 body 上限 20MB）
```

`[当前已实现]` `index` handler 是**一次同步请求做完全部工作**：鉴权 → 限流 → 身份注入（覆盖客户端传的 tenant/acl）
→ 媒资落对象存储 → 维度校验 → **调 embedder 批量嵌入** → `PgStore::upsert_doc`（doc 级 delete+insert）
→ pgvector 写穿 `set_embedding` → 引擎 `remove_doc` + `ingest_vector` → commit。
**没有 202 Accepted、没有 job id、没有断点续传**：一次 HTTP 往返内要么全成要么报错。

`[当前缺口]` 由此推出几个直接后果，做知识库产品会立刻撞上：
1. 一份 200 页 PDF 的嵌入（几百次 embedder 往返）挂在**一个 HTTP 请求**上——网关超时即前功尽弃，且没有恢复点。
2. body 20MB 上限对"整本手册 + inline 图片字节"不够。
3. 失败没有部分进度可查：调用方只知道 500，不知道停在哪一步。

### 2.5 唯一存在的"状态"：chunk 级图片向量状态

`[当前已实现]` `core::ImageVectorStatus`（`Embedded` / `TextFallback` / `Pending` / `AssetMissing` / `MissingBytes`），
由 `index`/`image_upload` 在嵌入时判定并写进 chunk，会经 PG 持久化。这是全仓最接近"处理状态"的东西，
但它是**单 chunk、单一路（图片向量）**的，不是文档级流水线状态。

`[当前缺口]` 没有 `queued/parsing/chunking/embedding/indexed/failed` 这类文档级状态机，
没有 lease/heartbeat/retry/error/TTL，没有失败原因回传。

### 2.6 已经存在、但**没接进来**的两块拼图

`[当前已实现]` **docparse 自带 REST 服务**：`vendor/docparse/crates/docparse-cli/src/server.rs`——
`POST /parse?format=json|markdown|text|chunks|okf`（multipart 文件上传）+ `GET /healthz` + `/openapi.json`。
query 开关覆盖 `ocr` / `layout` / `table_model` / `formula_model` / `vlm_describe` / `vlm_tables` / `images=embedded` / `table_format=markdown` / `envelope=true`。
解析跑在 `spawn_blocking`。**明确声明的边界**：无鉴权、无多租户、无队列，默认只绑 `127.0.0.1`（同机信任模型）。

`[当前已实现]` **docparse 自带 MCP 服务**：`parse_document` / `get_chunks` / `outline` / `export_okf` / `locate` 五个工具。

`[当前缺口]` **这两者都没有被 fastsearch 侧任何代码调用**。fastsearch 与 docparse 的实际接缝只有一条：
`fastsearch-cli` 的 `parse` feature 以 path 依赖直接 link `docparse-core`/`-pdf`，在 CLI 进程内跑。
也就是说，"文档解析服务"这块拼图**仓内已有，但躺在 vendor 里没通电**。

`[当前缺口]` 顺带一个已知的字节交接缺口（[FastGPT 参考建议 §4.2](2026-08-24-fastgpt知识库与多模态检索参考建议.md) 已记录）：
`cmd_ingest` 从不调用 docparse 的 `embed_images`/`export_images`（对应 CLI 的 `--image-embed`/`--image-dir`），
而适配器 `from_docparse_chunk` 只从 `ImageMeta.data_base64` 解 `media_bytes`——
所以走 `fastsearch ingest` 的文档图片**通常只有 `DocRegion` 坐标和 caption 文本，原始字节没进来**。
同理 `--vlm-describe`（自然图描述）在 docparse 侧有、fastsearch ingest 侧没接。

### 2.7 最有力的证据：本仓自己的 example 是怎么绕过去的

`[当前已实现]` `example/`（Hono + SQLite + AI SDK 的知识库 agent 示例）的做法：

- `example/src/server/lib/chunk.ts` —— **自己写了一个朴素 chunker**；
- `example/src/server/routes/documents.ts` —— 先 `chunkText()` 再 `indexDoc()` 打到 `/v1/index`，
  **同时往自己的 SQLite 里写一份 documents/chunks 台账**（`chunkCount`、`charLen`、标题）；
- README 直白写着："SQLite + Drizzle: local store for the **document list**（真源在 fastsearch/PG，这只是 registry）"。

**每个把 fastsearch 当知识库用的调用方，今天都必须自己造这三样：分块器、文档台账、状态显示。**
example 就是这个事实的活证据。

## 3. 要满足"文档直接给 fastsearch → 看状态 → 检索"，缺什么

按依赖顺序，共 7 项：

| # | 缺口 | 当前 | 需要 |
|---|---|---|---|
| G1 | **原始文件入口** | 只有 `/v1/images` 收单图；20MB body 上限 | `POST /v1/documents`（multipart / 预签名直传），返回 `document_id` |
| G2 | **解析执行位置** | CLI 进程内；server 零 docparse 且有 CI 门禁 | 决策：客户端 / server 内置 / **旁挂 worker**（§5） |
| G3 | **作业与状态机** | 无 | PG `ingest_job`：状态、阶段进度、lease/heartbeat、retry、error、幂等键 |
| G4 | **文档级视图** | 只有按 doc_id 列 chunk（且需 PG） | `GET /v1/documents`（列表 + 状态 + 计数）、`GET /v1/documents/{id}` |
| G5 | **幂等与替换** | doc 级 delete+insert 已有，但按 doc_id 而非内容 | 内容 hash 去重、重复上传的显式语义（跳过/覆盖/新版本） |
| G6 | **长任务承载** | 同步 HTTP，一次往返做完嵌入+写入 | 202 + 轮询/回调；分批提交；失败可从阶段续跑 |
| G7 | **分块可配置** | `target_chars=800` 硬编码，无 overlap，CLI 不暴露 | 每 collection 的解析/分块 profile（且要版本化，改了要能重建） |

**必须同时守住的既有不变量**（任一方案都不能破）：

1. **搜索热路径零 docparse/ONNX**——CI `hot-path-isolation` 是硬门禁（§2.3）。
2. **ACL 服务端注入不可绕过**——上传/作业入口同样要走 `principal_from_headers` → 覆盖请求体 tenant/acl，
   `index` handler 的 `apply_ingest_identity` 是现成范式。
3. **PG 是真源、派生可重建**——作业表进 PG 时**要不要进 publication 是个必答题**：
   派生状态进了复制流就可能造 CDC 反馈环，现有 DDL 靠"publication 列清单排除派生列"断环
   （[FastGPT 参考建议 §5.2](2026-08-24-fastgpt知识库与多模态检索参考建议.md) 已记录同类约束）。
4. **托管 PG 可移植**——作业表只能用普通表 + `FOR UPDATE SKIP LOCKED` 这类原生能力，不许引入 PG 扩展。
5. **无 `DATABASE_URL` 的 local-only 档**——现有管理端点在无 PG 时直接 503（`management_source`），
   作业/文档台账同理，必须显式降级而不是造第二个内存真源（现有 collection registry 就是个内存 HashMap，不跨副本、非真源）。

## 4. 现在就能用的最小配方（不改 fastsearch 代码）

`[当前已实现]` 在做任何决策之前，**今天就能把"给文件 → 可检索"跑通**，两条路：

**(a) 纯 Rust 调用方**：直接 `fastsearch ingest --features parse`，一条命令解析+分块+索引。缺的只是台账与状态。

**(b) 非 Rust 调用方**（Node/Python 后端，例如 `example/` 那种）：起 docparse 的 REST 服务当解析微服务：

```bash
# 1) 起解析服务。vendor/docparse 是被根 `exclude` 的独立 workspace，必须指 manifest-path。
#    注意：docparse serve 的**默认端口也是 8642**，与 fastsearch-server 撞，务必显式换端口。
cargo run --manifest-path vendor/docparse/Cargo.toml -p docparse-cli -- serve --port 8700
# 2) 解析成 chunk（可加 &ocr=true&table_model=true&images=embedded&vlm_describe=true 等）
curl -F file=@report.pdf "http://127.0.0.1:8700/parse?format=chunks&envelope=true"
# 3) 字段映射后 POST 给 fastsearch
curl localhost:8642/v1/index -H "x-api-key: dev" -d '{"collection":"kb","doc_id":"report.pdf","chunks":[...]}'
```

> 该服务**无鉴权**、默认只绑 `127.0.0.1`（其源码注释里写明是同机信任模型），
> 要跨机用必须自己套一层网关——这也是它今天只适合当"内部解析微服务"的原因。

字段映射（对照 `from_docparse_chunk`，两侧 schema 刻意同构，只有 3 处要动）：

| docparse chunk | fastsearch chunk | 备注 |
|---|---|---|
| `id` | `chunk_id` | 唯一的重命名 |
| `image.data_base64` | `media_bytes`（base64 解码）+ `media.asset=Inline` | 需 `?images=embedded` 才有值 |
| `image.file` / 皆无 | `media.asset=Object{uri}` / `DocRegion{page,bbox}` | — |
| `kind/text/page/bbox/heading_path/section_id/char_len` | 同名同义 | 直通 |
| — | `doc_id` / `tenant` / `acl` / `metadata` / `searchable` | 摄取期注入（tenant/acl 会被 server 按身份覆盖） |

`/v1/index` 的 chunk 元素是 `Chunk` 的**扁平展开**外加可选 `vector` 字段（`#[serde(flatten)]`），
即 `{"doc_id":…,"chunk_id":0,…,"vector":[…]}`，不传 `vector` 则 server 用配置的 embedder 现算。

**这条路的代价**：调用方仍要自己存文档台账、自己显示状态（就是 example 干的事）。它解决 §3 的 G1/G2，不解决 G3/G4/G6。

## 5. 三条路的对照

| | **A. 维持现状**（通用引擎） | **B. server 内置解析** | **C. 旁挂 ingest worker**（推荐） |
|---|---|---|---|
| 形态 | 调用方拥有解析/分块/台账 | `/v1/documents` 收文件，server 进程内 docparse | server 收文件+建 job；独立 worker 拉 job → 解析 → 回灌 `/v1/index` |
| 热路径隔离 | ✅ 天然 | ❌ **直接违反 CI 门禁**；ONNX/tract 进搜索二进制 | ✅ worker 是独立二进制/进程 |
| 部署复杂度 | 最低 | 低（单二进制，但二进制变重） | 中（多一个进程；可与 server 同机） |
| 长任务/重试 | 调用方自理 | 仍受同步 HTTP 与进程资源制约 | ✅ 天然：job lease + 阶段续跑 |
| 重模型（OCR/VLM/GPU） | 调用方自理 | ❌ 与搜索抢内存/CPU，无法独立扩缩 | ✅ 独立扩缩、独立限流与队列 |
| 复用仓内已有件 | — | 复用 docparse crate | ✅ 复用 docparse crate **或**已有的 `docparse serve` |
| 改动面 | 0 | server crate 结构性变化 + 门禁改写 | server：+ 上传端点 + PG 作业表 + 状态端点；worker：新 crate |
| 适合谁 | fastsearch 定位仍是"检索引擎"，产品层归调用方 | 只想要单二进制 all-in-one 的小规模自用 | 想让 fastsearch 直接面向知识库用户 |

> **✅ 2026-08-24 更新：闸门已开**。C 里的上传端点 + PG 作业表 + 状态端点，原本是
> [职责边界 ADR](../governance/2026-08-24-职责边界-不承担身份与控制面.md) 划给调用方的"摄取任务队列"；
> 该项已被 [职责边界修订](../governance/2026-08-24-职责边界修订-摄取作业面收回引擎.md)**显式推翻并收回引擎**
> （其余全部保留）。**C 是既定路径**，但受修订文的**七条红线**约束（无身份列、不进 publication、
> 不新增产品对象、worker 独立二进制等）。落地排期见
> [知识库引擎迭代计划 KB-3](2026-08-24-知识库引擎迭代计划.md)。

`[已决 · ADR 相应条款已推翻]` **选 C**。理由：它是唯一同时满足"文档直接给 fastsearch"和"搜索热路径零 docparse"两个约束的形态；
且仓内两块拼图（docparse serve、`from_docparse_chunk` 适配器）已经存在，worker 主要是**编排 + 状态**而非新算法。
B 的诱惑在于部署简单，但它要么改写 CI 门禁（放弃融合 Option B 的隔离约束），要么让搜索二进制背上 ONNX——
两者都是拿不变量换便利。

`[建议]` 若选 C，最小闭环的顺序建议是：
1. PG `ingest_job` 表（DDL 进 `fastsearch-pg/src/sql.rs`，publication 归属先答清楚）+ 幂等键 = 内容 hash；
2. `POST /v1/documents`（multipart，落对象存储/PG bytea，建 job，返 202 + job id）；
3. `GET /v1/documents` / `GET /v1/jobs/{id}`（状态、阶段、错误、chunk 计数）；
4. `fastsearch-ingest-worker` 新 crate：`SKIP LOCKED` 领 job → docparse 解析+分块 → 复用 `from_docparse_chunk` → `POST /v1/index` → 回写状态；
5. 顺手补 §2.6 的字节交接（`embed_images`）与 §3-G7 的分块 profile。

其中第 1、2、3 步已经越过 dev spec §0 的"复杂需求"线（新 crate / 改 DDL / 改数据契约），**各自要先立 spec**。

## 6. 关于 MinerU

`[建议]` **不建议引入**，理由三条，且与偏好无关：

1. **重复**：MinerU 的核心能力（PDF 版面分析 → 结构化 Markdown/JSON、OCR、表格、公式）与 `vendor/docparse` 重叠，
   而 docparse 已经产出带 `page`+`bbox` 的 chunk——那正是 fastsearch `citation_id → 深链高亮` 依赖的东西。
2. **形态冲突**：MinerU 是 Python + 重模型权重的生态，引入意味着 fastsearch 的部署从"单 Rust 二进制"
   变成"Rust + Python 运行时 + 模型分发"，与本项目"外部单二进制引擎"的定位相悖。
3. **真要用也不必改内核**：若某个语料上 MinerU 的效果确实更好，按 §5 的 C 方案，它可以作为**另一个 ingest worker 实现**
   接进来——只要产出同样的 chunk 契约（`text/page/bbox/heading_path/...`）即可，fastsearch 内核一行不用改。
   这也是 C 方案相对 B 的额外好处：**解析后端可替换**，跟 `RegionReader` 那条"识别后端可换"的接缝同一思路。
