## 1. 需求三件套

### 1.1 要做什么

把 **OvisOCR2**（0.8B 端到端文档解析 VLM，经 vLLM/SGLang 的 OpenAI 兼容端点）接成 docparse 的**区域级识别后端**，并在 fastsearch 摄取侧开一个 `parse-vlm` feature 把它接通，使 `fastsearch ingest` 能对难页产出更高质量、**且仍带真实坐标**的 chunk。

一句话形态：**版面模型继续提供几何，OvisOCR2 只负责"读"**——不做整页替换，不放弃 bbox。

### 1.2 为什么

| 动因 | 依据（代码/记录真源） |
|---|---|
| ① 学术难表 e2e 0.52 是**已判定的模型天花板** | [docparse status.md](../../vendor/docparse/docs/status.md) Phase 6：主因是 UniRec-0.1B **固定 960×1408 输入**在大/宽/密表上 under-segment + 超宽表 NO-PRED；抬分辨率到 1280×1792 破速度门。结论明写"真杠杆 = 更大/多分辨率表模型 / `--vlm-tables` 服务"。OvisOCR2 是动态 448²–2880²、Table TEDS 94.76 |
| ② 整页转写（G8d/2a）的模型档位塌缩 | [vlm-service-driven §2a](../../vendor/docparse/docs/refer/vlm-service-driven-capabilities.md) 原写"Qwen2.5-VL 7B 起步、32B/vLLM 才到生产质量线"。OvisOCR2 **0.8B / 1.71GB BF16**，把这条从"太贵、只能规划"变成可落地 |
| ③ 接入成本近零 | [`docparse-vlm::VlmClient`](../../vendor/docparse/crates/docparse-vlm/src/lib.rs) 的 OpenAI 协议已建成且被 mock 单测锁定；`refine_tables` / `transcribe_pages` 两处调用点的形状**与 VLM 调用完全同构**（见 §3.1），可抽同一个 seam |
| ④ fastsearch 侧 `parse-vlm` 本就是在案待办 | [ingest.rs:28](../../crates/fastsearch-cli/src/ingest.rs#L28) 标注"自然图 VLM 描述=`parse-vlm`（下一迭代，需服务）" |

### 1.3 ⚠️ 核心形态风险（review 2026-07-27 提出，决定 v1 是否成立）

**OvisOCR2 是页级端到端模型，本设计把它当区域级识别器用——这是 OOD（训练分布外）使用。**

调研引用的全部成绩（OmniDocBench 96.58 / Table TEDS 94.76 / PureDocBench 75.06）都是**整页口径**，对"裁一个区域丢给它"这个形态**一条都不适用**。对照组 UniRec 恰恰相反：它本来就是为逐区域识别设计和评测的（[openocr-0.1b-evaluation](../../vendor/docparse/docs/refer/openocr-0.1b-evaluation.md) 的 spike 就是拿单个表区域测的）。

完全可能出现"整页跑赢 UniRec、切成区域反而输"。因此**门 0（§7.0）排在写任何业务代码之前**：不过则本 spec 的 v1 形态不成立，须转向"整页模式 + schema 锁步"（§8 第一行）重写。

> 例外：§9 第 1–2 步（`RegionReader` seam 抽出 + `VlmClient` 参数修正）**与门 0 结论无关**——前者是纯重构，后者两条路都要。故可先行落地。

### 1.4 验收（总）

1. 开 `--transcribe-vlm` / `--vlm-tables`（新后端）后，**每个产出 chunk 的 `bbox` 仍来自版面/表格检测的真实几何**，`resolve_citation` 抽查 20 条全部落在正确区域；
2. 在 docparse 已记录的**短板样例集**上，同口径自测优于现役 UniRec 后端（门槛见 §7）；
3. 服务不可达 / 超时 / 返回垃圾时，**一律优雅降级回确定性结果**，解析不失败、退出码为 0；
4. `cargo fmt --all --check` + `cargo clippy --workspace --all-targets -- -D warnings` + `cargo test --workspace` 全绿（两个 workspace 各自收口）；
5. 未跑真实服务前，文档与提交如实标 `待运行验证`。

| fastsearch **检索侧**任何改动 | 它不是 embedder / reranker；不能做 M1 跨模态或 M2 ColPali（见调研 §7）。检索热路径**零改动、零新依赖** |
| PG schema / DDL / ACL / 融合 / 排序 | 本特性完全在摄取侧，不触碰任何关键不变量（§5 逐条核对） |

## 3. 功能设计

### 3.1 关键观察：两个调用点已经同构

`refine_tables` 与 `transcribe_pages` 现在做的是**同一件事**：

```
crop_region(rgb, w, h, &bbox, page_h, scale)          // 裁区域（已有，pub(crate)）
  → model.recognize(&crop, cw, ch, MAX_TOKENS) -> Result<String>   // 读
  → looks_degenerate(&text) 守卫                       // 退化拒收（已 pub）
  → 解释（HTML→Table / 文本→TextChunk）+ source 标注 + 失败保底
```

差别只在最后一步的"解释"。所以**唯一需要的抽象就是"读"这一步**——这正是 deep module 的窄接口：一行签名，把"进程内 ONNX"和"HTTP 服务"两种截然不同的实现藏在后面，两个调用点一行都不用改逻辑。

### 3.2 `RegionReader` trait（D1）

落在 `docparse-core`（不依赖任何后端，符合其分层不变量）：

```rust
// docparse-core/src/region_reader.rs
/// 一块待识别的区域图（紧凑 RGB8，`w*h*3` 字节）。
pub struct RegionImage<'a> { pub rgb: &'a [u8], pub w: usize, pub h: usize }

/// 区域图 → 文本。唯一的"识别后端"接缝：进程内 ONNX（UniRec）与 HTTP 服务
/// （VLM）在此处可互换，调用方（表格重识别 / 整页转写）不知道背后是谁。
pub trait RegionReader: Sync {
    /// 读一块区域。`max_tokens`：生成上限（防跑飞）——**实现必须真正施加**，
    /// 事后拒收（`looks_degenerate`）救不回已经烧掉的算力/时延。
    fn read(&self, img: RegionImage<'_>, max_tokens: usize) -> anyhow::Result<String>;

    /// 读一批区域，返回与入参**等长同序**的结果。默认串行（进程内模型的正确
    /// 形态：本来就在跑满 CPU，并发只会互相抢核）。HTTP 后端覆写成有界并发
    /// ——服务化模型的价值一半在批处理，串行发请求是最差用法。
    fn read_batch(&self, imgs: &[RegionImage<'_>], max_tokens: usize)
        -> Vec<anyhow::Result<String>> {
        imgs.iter().map(|i| self.read(RegionImage { ..*i }, max_tokens)).collect()
    }

    /// 产物溯源标签，写进 `Table::source` / `TextChunk::source`，
    /// 如 `"unirec-0.1b"` / `"vlm:OvisOCR2"`。
    fn source_tag(&self) -> String;
}
```

> **为什么 `read_batch` 带默认实现而不是让调用方自己并发**：`UniRec` 是进程内 tract 推理，rayon 并发它只会和自己抢核；`VlmRegionReader` 是网络等待，不并发就是纯浪费。**并发策略属于后端，不属于编排**——放进 trait 的默认实现，两个调用点写一样的代码，各后端自负其责。

> **为什么 trait 放 core 而不是 ocr**：若放 `docparse-ocr`，则 `docparse-vlm` 要反依赖 `docparse-ocr`（重 tract/ONNX），把轻量的 VLM crate 拖重。放 core（零依赖）后依赖图保持单向：`core ← ocr`、`core ← vlm`，两个后端互不相识，编排由 CLI 装配。

### 3.3 两个实现

**D2 · UniRec（零行为变化）**

```rust
// docparse-ocr/src/unirec.rs
impl RegionReader for UniRec {
    fn read(&self, img: RegionImage<'_>, max_tokens: usize) -> Result<String> {
        self.recognize(img.rgb, img.w, img.h, max_tokens)
    }
    // read_batch 用默认串行实现：tract 推理已跑满 CPU，并发只会自己抢自己的核。
    fn source_tag(&self) -> String { "unirec-0.1b".into() }
}
```

`refine_tables` 里 `table.source = Some("table:unirec-0.1b")` 改为 `Some(format!("table:{}", reader.source_tag()))`，`transcribe.rs` 的 `"transcribe:unirec-0.1b"` 同理 → **现役路径输出逐字节不变**（有 golden 断言，T1）。

**D4 · VlmRegionReader（新）**

```rust
// docparse-vlm/src/region.rs
pub struct VlmRegionReader { client: VlmClient, prompt: String }

impl VlmRegionReader {
    /// 文本区域：整段读出（保留公式 LaTeX / 行内结构）。
    pub fn for_text(client: VlmClient) -> Self { /* prompt = TEXT_PROMPT */ }
    /// 表格区域：要 HTML `<table>`（与 UniRec 输出同构，直接复用现有 parse_html_table）。
    pub fn for_table(client: VlmClient) -> Self { /* prompt = TABLE_HTML_PROMPT */ }
}

impl RegionReader for VlmRegionReader {
    fn read(&self, img: RegionImage<'_>, max_tokens: usize) -> Result<String> {
        // max_tokens 必须真正下发（见 §3.4 第 1 项）：OvisOCR2 有自认的
        // 截断-复读失效模式，不设上限就是让它烧满服务端默认额度。
        self.client.ask_about_image(img.rgb, img.w as u32, img.h as u32, &self.prompt, max_tokens)
    }

    /// 有界并发（`MAX_INFLIGHT`）：网络等待期不占 CPU，串行发请求会把
    /// vLLM 的批处理优势全部浪费掉。顺序由 rayon 的索引化收集保证。
    fn read_batch(&self, imgs: &[RegionImage<'_>], max_tokens: usize) -> Vec<Result<String>> { … }

    fn source_tag(&self) -> String { format!("vlm:{}", self.client.model()) }
}
```

`MAX_INFLIGHT` 默认 **4**（可经 `VlmConfig` 调）：够吃到 vLLM 的批处理，又不至于让一个摄取进程打爆共享服务。

Prompt 常量（区域级，非整页）：

```
TEXT_PROMPT        = "Transcribe all text in this document region in natural reading order. \
                      Keep formulas as LaTeX ($...$ inline, $$...$$ display). \
                      Output the transcription only — no commentary, no markdown fences."
TABLE_HTML_PROMPT  = "Extract this table as an HTML <table>. Preserve merged cells with \
                      rowspan/colspan. Output only the <table>…</table>, no commentary."
```

> **为什么表格 prompt 要 HTML 而不是现有 `--vlm-tables` 的 TSV**：`table_model.rs` 已有 `parse_html_table`（能吃 rowspan/colspan 并展开到每个被跨格），而 TSV 路 [`parse_tsv_grid`](../../vendor/docparse/crates/docparse-vlm/src/lib.rs#L231) 要求"合并格重复值"、拿不到拓扑。OvisOCR2 原生就出 HTML 表 → **走 HTML 路信息量严格更大，且复用现成解析器**。旧 TSV 路保留不动（兼容任意通用 VLM）。

### 3.4 `VlmClient` 修正（D5）——**必须与本特性同时改**

现有请求体与常量是为"图区裁剪描述"定的，直接用于区域识别会测出被自己参数拖累的假结论：

| 项 | 现状 | 改法 | 理由 |
|---|---|---|---|
| **`max_tokens`** | **请求体根本不发**（[lib.rs:71-80](../../vendor/docparse/crates/docparse-vlm/src/lib.rs#L71-L80) 只有 `{model, messages}`） | `ask_about_image` 增参并写进 body | OvisOCR2 官方样例用 `max_tokens=16384` 且**自带截断-复读清洗**（模型对该失效模式的自认）。不设上限＝让它烧满服务端默认额度；`looks_degenerate` 只能事后拒收，救不回已花掉的时延。**这一项不做，`RegionReader::read` 的 `max_tokens` 契约就是假的** |
| **`temperature`** | 不发（随服务端默认，通常 0.7～1.0） | 固定 `0.0` | 官方样例即 0.0；识别类任务采样毫无收益，且抬高复读概率。也让 A/B 少一个噪声源 |
| `MAX_IMAGE_SIDE` | `1024` 硬编码（[lib.rs:30](../../vendor/docparse/crates/docparse-vlm/src/lib.rs#L30)） | 提升为 `VlmConfig.max_image_side: usize`，默认仍 1024；区域识别路传 **2048**（OvisOCR2 支持到 2880²） | 1024 上限会把 OvisOCR2 的动态分辨率优势掐掉，**重演 UniRec 的固定分辨率天花板**——这正是本特性要解决的问题 |
| 渲染 scale | vlm 路 `2.0`，transcribe/table 路 `3.0` | 区域识别沿用调用方的 `3.0` | 识别比描述吃分辨率；且与现役 UniRec 路同 scale 才可 A/B 对照 |
| PNG 编码 | **stored（未压缩）deflate**（[lib.rs:368](../../vendor/docparse/crates/docparse-vlm/src/lib.rs#L368)） | **实测后决定：暂不改** | 判据是"单请求 <8MB 则不动编码器"。**实测（2026-07-27，stub e2e）**：一个 300×80pt 的表区域 @scale 3.0 → 900×240px → base64 后 **920 KB**，远低于阈值 → 维持现状。⚠️ 但**整页转写**要按区域数乘：一页 15 个区域 ≈ 13 MB 上行/页，若门 3 显示网络成为瓶颈，这里就是第一个该动的地方 |

> 前三项已落地；第四项按"实测驱动"处理并已给出实测值（见上）。

### 3.6 fastsearch 侧（F1/F2）

与 `apply_ocr` / `apply_tables` **完全同形**（env 存在即启用，缺则原样返回），挂在同一串联位置：

```rust
// crates/fastsearch-cli/src/ingest.rs
let doc = apply_ocr(doc)?;             // 已有：扫描页 PP-OCR 抽文本（含 PNG/JPEG 图片）
let doc = apply_vlm(doc, &file)?;      // 新增：VLM 区域识别（parse-vlm feature）
let doc = apply_tables(doc, &file)?;   // 已有：UniRec 表格——**VLM 已精修过的表跳过**
```

**⚠️ 双重精修必须显式定优先级**：`apply_tables`（UniRec）与 `apply_vlm`（VLM 表格）作用于**同一批 `Element::Table`**。两个 env 都设时，若不处理就会连跑两次推理、后者盲目覆盖前者，且 `table.source` 的最终值取决于调用顺序这个隐式细节。

裁决：**VLM 优先，UniRec 兜底**——先跑 `apply_vlm`，`apply_tables` 再跳过 `source` 已以 `table:vlm:` 开头的表。理由：VLM 是显式配了服务才启用的重档，用户配了就是想用它；而 UniRec 仍能覆盖 VLM 失败/拒收的表（`source` 未被改写），两级兜底自然成立。stderr 明确打印各自处理了几个表。

**页数闸**：`FASTSEARCH_VLM_MAX_PAGES`（默认 **50**）。批量摄取一份 100 页 PDF × 每页 ~15 区域 = **1500 次调用**，无闸会让一次 `ingest` 跑成小时级。超出页数的部分保留确定性结果并在 stderr 明确告知跳过了多少页（不静默截断）。

```rust
/// VLM 区域识别（`parse-vlm` feature，**需外部 OpenAI 兼容服务**，如 vLLM 起 OvisOCR2）。
/// 仅当 `FASTSEARCH_VLM_URL` + `FASTSEARCH_VLM_MODEL` 都设时启用；否则原样返回。
/// 能力按配置浮现：
///   - 恒定：表格区域重识别（HTML 路，覆盖解析层已检出的 Element::Table）
///   - 额外：若 `FASTSEARCH_LAYOUT_MODEL` 指向版面 ONNX，则整页区域级转写也开
/// 仅 PDF（需源字节栅格化，同 apply_tables）。任何服务失败 → 保留确定性结果。
#[cfg(feature = "parse-vlm")]
fn apply_vlm(mut doc: docparse_core::ir::Document, file: &Path) -> Result<Document> { … }
```

| env | 必需 | 作用 |
|---|---|---|
| `FASTSEARCH_VLM_URL` | ✅ | OpenAI 兼容服务基址（如 `http://localhost:8000`） |
| `FASTSEARCH_VLM_MODEL` | ✅ | 服务侧模型名（如 `OvisOCR2`） |
| `FASTSEARCH_VLM_KEY` | — | Bearer token（云端/带鉴权的服务） |
| `FASTSEARCH_LAYOUT_MODEL` | — | 版面 ONNX 路径；**设了才开整页区域转写**，否则只做表格 |
| `FASTSEARCH_VLM_MAX_PAGES` | — | 每文档最多送多少页给 VLM（默认 50，防批量摄取跑成小时级） |

Cargo feature（`parse-vlm` 是**重档**，与 `parse-tables` 同级——区域几何来自版面 ONNX，无法回避 tract）：

```toml
# 区域级 VLM 识别（需外部 OpenAI 兼容服务）。拉入 docparse-vlm（轻：ureq+base64）
# + docparse-ocr（版面/编排，重 tract）+ docparse-raster（PDF 栅格化）。
parse-vlm = ["parse", "dep:docparse-vlm", "dep:docparse-ocr", "dep:docparse-raster"]
```

> **搜索热路径零影响**：`parse-vlm` 与现有 `parse-*` 同为 opt-in feature，默认 `cargo build` 不编译任何一行；`cargo tree` 门禁不变。

## 7. Spike 门控与验收标准

照 UniRec spike 的老规矩：**四道门，任一不过就停并记录负结论**（负结论同样是成果）。

### 门 0 · 形态假设（**排在写任何业务代码之前**，见 §1.3）

本 spec 把一个**页级**模型当**区域级**识别器用，而它所有公开成绩都是整页口径——这个形态本身未经验证。

| 动作 | 判据 |
|---|---|
| 手工裁 10 个区域（5 表 + 5 文本块，取自 §7 门 2 的短板样例集），分别丢给服务 | 同区域 vs UniRec 输出人工对比 |
| 同时把这 10 个区域**所在的整页**也整页丢一次 | 对比"区域级 vs 整页级"两种形态下 OvisOCR2 自身的质量差 |

| 结果 | 结论 |
|---|---|
| 区域级 ≥ UniRec，且与整页级差距不大 | ✅ v1 形态成立，继续 |
| 区域级 ≥ UniRec，但**整页级明显更好** | 🟡 继续 v1（坐标优先），并把"整页模式 + schema 锁步"提为 v2 首位 |
| 区域级 < UniRec | ❌ **v1 形态不成立**。转向"整页模式 + schema 锁步"（§8 第一行）重写 spec |

**成本**：~1 小时，纯手工 curl + 肉眼，**零代码**。§9 第 1–2 步与本门结论无关，可并行进行。

### 门 1 · 坐标（一票否决，先于一切）

| 判据 | 门槛 |
|---|---|
| 每个产出 chunk 的 `bbox` 来自 `Region`/`Table` 真实几何 | 100%（代码保证 + T8 抽查 20 条落框正确） |
| 页级/整页矩形 bbox 出现率 | **0**（出现即说明走错了路径） |

不过 → **停**。不降级到整页模式（那需要先做 §8 的 schema 锁步）。

### 门 2 · 质量（同口径自测，**不引用官方 v1.6 数字**）

打 docparse **已记录在案的短板集**，而不是打榜单：

| 样例集 | 历史记录值（仅作方向参考） | 门槛 |
|---|---|---|
| 学术难表（2203 / 2305-pg9 / redp5110） | e2e 表 TEDS_X **0.52**（status §①，判为 UniRec 固定分辨率天花板）；Phase 7 A/B 另记 0.670/0.661（口径不同） | 相对**当次重测的 UniRec 基线** **+0.10 TEDS_X**；`< +0.03` = 无进展 |
| CJK/设计版面 | `skipped_1page` 0.231 / `skipped_2pages` 0.354 / `normal_4pages` 0.607 | 三项**均不劣化**，且至少一项 **+0.10** |
| 中文扫描件 | PP-OCR 现有结果 | 不劣化（本特性不替代默认 OCR，只需证明"不更差"） |

> **指标方向**：TEDS_X / NID 类均**越大越好**（Phase 7 的 0.206→0.654 记为 ≈3× 提升可佐证）。
>
> **口径要求（关键）**：历史数字来自不同日期/不同配置（同一"学术表"在 §① 是 0.52、在 Phase 7 A/B 是 0.670），**不可当固定及格线用**。门槛一律定义为"相对同一次运行里重测的 UniRec 基线的增量"——A/B 必须同 scale（3.0）、同样例、同评测脚本、同一天跑完，唯一变量是识别后端。§3.4 的 `MAX_IMAGE_SIDE` 必须先改成 2048，否则测的是参数不是模型。

### 门 3 · 速度 / 成本（官方**零速度数字**，必须自测）

| 指标 | 门槛 | 说明 |
|---|---|---|
| **整页端到端（`read_batch` 并发下）** | **≤ 30s/页** | ⬅ **唯一的通过/不通过判据** |
| 单区域延迟 | 仅**记录**，不设门 | 一个密排页有 10–20 个区域，"≤5s/区域"与"≤30s/页"在任何真实页上都不可能同时成立（review 发现的自相矛盾）。串行时代的 UniRec 门槛不能直接搬到并发的 HTTP 后端 |
| 有效并发度 | 记录（`MAX_INFLIGHT` 扫 1/2/4/8） | 定 `MAX_INFLIGHT` 默认值的依据 |
| VRAM 峰值 | 记录 | 0.8B BF16 预期 ~4GB（vLLM），需实证 |
| 单请求体积 | 记录 | 决定 §3.4 第 4 项（PNG 压缩）要不要动 |

不过 → 降级为"仅难页路由"（配合页型判官，属 v2）或停。

## 8. 已知限制与 v2

| 项 | 现状 | 何时做 |
|---|---|---|
| **整页模式**（最高质量的阅读序） | 排除。阻塞在坐标：docparse `Chunk` **无 `source` 字段**（IR 的 `TextChunk.source` 在 `chunk_document` 时丢失），fastsearch `Chunk.bbox` 非 `Option` → 无法诚实表达"这条没有页内坐标" | **前置 = 两侧 schema 锁步**：docparse `Chunk` 加 `source: Option<String>` + `coord_level: Page\|Region\|Line`，fastsearch `Chunk`/`Citation` 对应透传。与[多模态职责划分 §3](2026-06-25-多模态职责划分-docparse与fastsearch.md) 的 `time` 字段锁步项**合并成一次 schema 评审**做 |
| 图表→数据表（2c） | 未做 | 管线可 100% 复用，只差一个 prompt + 归一函数 |
| 图内嵌表 recall（2e） | **部分**：v1 只覆盖"已检出的表"，漏检的图内表救不了 | 需 `Figure` 区域也送 VLM 问"是否含表" → 与 2c 共管线 |
| 页型判官（2b，自动路由难页） | 未做 | OvisOCR2 不是分类器；仍需轻量通用 VLM 或几何判据 |
| 真实退化扫描件 | OvisOCR2 自认短板（PureDocBench real 66.56 < Gemini-3.1-Pro 71.98） | 该档继续用 PP-OCR，或留给通用大 VLM |
| 图片（非 PDF）输入 | v1 只走 PDF（同 `apply_tables` 的 PDF-only 约束）。**v1 期间 PNG/JPEG 扫描件照旧走 `apply_ocr`（PP-OCR），不是没人管** | 图片本身就是页图、不需栅格化，是个小增量；v1.1 |
| 确定性 | VLM 服务输出不保证逐字节可复现 | 按增强器规格标注即可，不追求可复现 |
