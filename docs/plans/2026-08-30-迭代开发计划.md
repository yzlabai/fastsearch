# fastsearch 下一阶段迭代开发计划

> 日期：2026-08-30  
> 状态：待评审  
> 依据：[`阶段性项目情况说明`](../reviews/2026-08-30-阶段性项目情况说明.md)、[`知识库引擎迭代计划`](2026-08-24-知识库引擎迭代计划.md)、`docs/plans` 全量审计  
> 目标：先恢复测试与契约可信度，再闭合 CDC 正确性、多表示检索和文档摄取作业面。

## 1. 迭代目标与边界

### 1.1 本阶段要达到的结果

完成本计划后，项目应达到“**0.2 候选：可重复验收的知识库引擎**”状态：

1. CI 不再受 HNSW 随机构图偶发失败影响，外部依赖测试的“执行/跳过”清楚可见。
2. Rust 请求结构、OpenAPI、MCP 和 SDK 的公开契约一致，`explain` 不再静默失效。
3. CDC 对 PK UPDATE、TRUNCATE、错误原子性和多副本 slot 首建具有明确、已验证的语义。
4. 同一 chunk 能持有多路具名信号，Engine 能实际消费多路并解释来源。
5. 文档可经 server 上传、同步或异步处理、查询状态、失败恢复；worker 不改变上传者 ACL。
6. 根发布元数据、文档状态和 CI 入口达到可发布候选的最低要求。

### 1.2 本阶段不做

- 不做 KB-4：用户/组织/角色、Dataset/Source 产品对象、版本回滚和 UI，继续遵守职责边界 ADR。
- 不把 HashEmbedder 或 caption-as-text 宣称为真实跨模态质量。
- 不在没有真实模型/对象存储/集群时宣称 OvisOCR2、S3/MinIO、K8s/HA 已完成。
- 不同时改 `chunk_signal` 和 `ingest_job` DDL；二者共享 `fastsearch-pg/src/sql.rs`，必须串行。
- 不通过降低有效召回阈值掩盖 HNSW 随机测试问题。

## 2. 优先级与依赖图

```text
M0 可信度基线
  ├─ HNSW 稳定门禁
  ├─ 契约一致性 / explain 裁定
  ├─ CI 漏项与 skip 可见性
  └─ 文档/许可/发布卫生
          ↓
M1 CDC 正确性与原子性
          ↓
M2A chunk_signal 多表示 ─→ M2B N 路具名融合/explain ─→ M2C 模态化 rerank
          ↓                                                ↓
M3 ingest_job DDL → 上传/状态 API → 独立 worker → MCP ingest_document
          ↓
M4 真实外部依赖验收与 0.2 发布候选
```

KB-1.2 分块 profile 可与 M1 并行设计，但实施前必须先裁定既有文档如何处理。真实模型、对象存储和 K8s 工作作为资源具备时启动的独立通道，不阻塞本地正确性工作。

## 3. 里程碑 M0：恢复可信度基线（P0）

### FS-001 HNSW 测试确定性与召回门禁

**问题**：`hnsw::tests::ef_search_override_honored` 已出现一次 `default=0.56 high=0.56` 的随机失败；实现使用 OS 随机种子建图。

**实施**：

- 优先给测试/构图引入可注入 seed；如果上游 HNSW API 无法注入，则改成固定语料、多次构图统计的稳定门禁。
- 分开验证“高 ef 不低于默认”和“绝对 recall 下限”，避免一个随机图同时决定两类性质。
- 在 CI 暂时增加 HNSW 专项重复执行并记录失败样本；问题关闭后保留一次稳定专项。
- 不降低现有生产质量目标，任何阈值调整都要有统计证据。

**验收**：

- 同一 commit 连续 10 次 `cargo test --workspace` 全绿。
- HNSW 专项至少 100 次构图无随机红灯，或统计门禁达到预先写入 spec 的置信标准。
- 召回阈值仍能识别故意降低 `ef_search`/破坏建图的回归。

### FS-002 公开契约一致性与 `explain` 处理

**裁定建议**：不删除 `explain`，把它作为 KB-2.2 第二步的一部分真正实现；在实现完成前，server 对 `explain=true` 返回明确的 4xx capability error，不能继续静默忽略。

**实施**：

- 建立 Rust `SearchRequest`、OpenAPI、TS 类型、Python 参数和 MCP allowlist 的字段矩阵测试。
- 补齐 OpenAPI 中当前已支持但未完整描述的请求/响应字段。
- 给 `SearchHit` 设计可选 `sources`/contribution；默认不返回，保持旧响应形状。
- 老 `Fusion::Normalized`/`Weighted` JSON 继续可用，新具名权重采用加法兼容。

**验收**：

- 任何公开字段都满足“实现并声明”或“明确拒绝”，不存在静默失效。
- OpenAPI、TS、Python、MCP 的自动契约测试在 CI 中运行。
- `explain=false` 的旧响应 golden 不变；`explain=true` 有来源、rank、原始分和贡献。

### FS-003 CI 覆盖和环境门禁可见性

**实施**：

- CI `parse-feature` 增加 `parse-vlm` compile check。
- Python SDK job 同时执行 `test_integrations.py` 与 `test_ingest.py`。
- 增加 MCP↔server 真二进制 e2e：探测、search、resolve、index_chunks、ACL 两 key 隔离。
- PG/模型环境缺失时，不再只在测试函数内 `return`；至少输出统一的 executed/skipped 汇总，关键 CI job 要断言 PG 用例确实执行。
- 把 `/readyz` 改为组件化状态，或在未完成前改名/文档化为进程存活，不继续暗示依赖就绪。

**验收**：

- CI 日志能明确看到 PG/CDC 用例执行数量，而非仅看到 cargo `ok`。
- `parse`、`parse-ocr`、`parse-tables`、`parse-vlm` 四档均有常态编译门禁。
- 两套 SDK、example、CLI↔server、MCP↔server 都有自动化入口。

### FS-004 发布与文档卫生

**实施**：

- 根目录补 Apache-2.0 `LICENSE`，根据第三方归属策略补 `NOTICE`；保持 vendor 自有许可文件。
- 新增根 `CHANGELOG.md`，记录 0.1.x 到 0.2 候选的破坏性与兼容性变化。
- 回写阶段报告 §7 所列历史计划的顶部状态；旧文档保留历史，不再当执行看板。
- 修正 `fastsearch-vector` 顶部陈旧注释和 `deploy/README` 的 CI 状态。
- 明确 TS 0.3.0、Python 0.2.0 的发布状态；example 升级到当前 SDK 并使用统一摄取 helper。

**验收**：

- README 的许可证、版本、安装方式和仓库实际文件一致。
- 所有活动需求只从本文进入；旧 plan 顶部能指回本文或标明已归档。
- `cargo about` 产物、根 LICENSE/NOTICE、SDK 包元数据进入发布检查。

## 4. 里程碑 M1：CDC 正确性与原子性（P1）

本里程碑必须使用 Docker pgvector + `wal_level=logical`，不能只做纯函数测试。

### FS-101 PK UPDATE 与 TRUNCATE 语义

**实施**：

- Update 同时读取旧 key 与新 tuple；主键变化时生成 `Delete(old)` + `Upsert(new)`。
- 为 `Change`/`IndexSink` 增加 TRUNCATE/clear 语义，清空对应派生 text/vector 索引。
- 将 `map()` 从单变更返回升级为零到多变更，保持同事务内顺序确定。
- relation 守卫从形状判定升级为配置化表名白名单，避免未来旁表形状碰撞。

**验收**：

- 真 PG 修改 collection/doc_id/chunk_id 后，旧 citation 不再命中，新 citation 命中。
- 真 PG TRUNCATE 后，keyword/vector/hybrid 均不返回旧结果。
- 非 chunks 表仍不产生 chunk 变更。

### FS-102 `IndexSink` 原子性与批量嵌入

**实施**：

- 先完成嵌入/PG 写穿准备，再改变 text/vector 派生状态；任一步失败不得留下可被后续 commit 带出的半状态。
- CDC batch 收集文本后批量调用 `embed_multi`，将网络等待移出全局 Engine 锁。
- 明确单 chunk 与 batch 的失败策略：全批回滚或可证明幂等的逐项提交，禁止模糊混用。
- 增加 embedding 超时、维度错误、PG 写穿失败和进程崩溃的故障注入。

**验收**：

- 任一故障后 keyword/vector 对同一版本保持一致；重试后收敛到 PG 真值。
- 批量摄取时搜索延迟不再随 N 次串行 HTTP 线性阻塞。
- `bench_capacity` 给出改造前后吞吐、p95 和锁等待数据。

### FS-103 LSN、slot 与运行健康

**实施**：

- 澄清或移除 `Applier` 生产未使用的水位跳过契约，统一事务 LSN/commit LSN 语义。
- `ensure_slot` 使用 advisory lock 或捕获 duplicate-object 错误，多副本并发首建幂等。
- 暴露 slot lag、last applied LSN、last successful poll、dead-letter count 和 rebuild-needed 状态。
- 保持 polling 为本阶段默认；流式 `START_REPLICATION` 另立性能项，不与正确性重构混做。

**验收**：

- 8 个并发实例创建同一 slot 全成功。
- 崩溃发生在 peek、apply、persist、advance 四个位置时，重启后不丢不重。
- readiness 能区分“进程活着”与“真源/CDC 已可服务”。

## 5. 里程碑 M2：多表示与可解释检索（P1）

### FS-201 实施 KB-2.1 `chunk_signal`

依据 [`chunk_signal 多表示设计`](2026-08-25-chunk-signal多表示设计.md) 实施；开始前评审并关闭其中 D1–D4。

**推荐裁定**：

- publication 永远只发布 chunks 主表，signal 表不进 CDC。
- signal 表名由 chunks 表名安全派生并通过 identifier 校验。
- 暂不删除旧 `image_vector_status`，先做兼容读写和迁移观察。
- 暂不改变既有 chunk upsert 清单向量的行为，迁移到多信号后另做一次可回滚切换。

**实施**：

- DDL、行模型、CRUD、status/hash/model/version/dim、失效规则和 PG 集成测试同一变更交付。
- `user_text/ocr/asr` 绑定正文 hash；`vlm_caption/image_bytes` 绑定工件 hash。
- 同一 GlobalId 可有多路信号，新增 signal type 时必须在穷尽 match 中定义失效规则。

**验收**：

- 设计文档 T1–T12 在真实 PG 全绿。
- 正文更新只使正文绑定信号 stale，视觉工件信号完全不动。
- signal 表不在 publication，CDC 无误删/毒丸/反馈。

### FS-202 完成 KB-2.2 第二步

**实施**：

- 增加具名权重表达和向后兼容反序列化；保留旧 `Normalized`/`Weighted` 输入。
- Engine 从 `chunk_signal` 产生实际多路 recall list，不再只把 `fuse_n` 当两路薄壳。
- `SearchHit.sources` 记录 source、rank、原始 score、model/version 和融合贡献。
- 所有浮点累加按 source 稳定排序，继续以 GlobalId 作为最终 tie-break。

**验收**：

- 两路旧请求逐位兼容，旧 SDK 不需要同时升级。
- 打乱 recall list 顺序与内部同分顺序，输出仍确定。
- 至少用 `keyword:user_text`、`vector:user_text`、`vector:image_caption` 三路完成真 Engine 测试。
- 三份现有 golden 不回归；新增多表示 golden。

### FS-203 KB-2.3 模态化 rerank

**实施**：

- 给 Reranker 加 capability：text/image/cross-modal、可接受 query/candidate 类型。
- 编排层遇不支持模态、空 token、服务错误时保持融合顺序，并写入 explain 原因。
- 当前 LexicalOverlap 明确标为 text-only baseline。

**验收**：

- image-only、纯标点/分词为空、多模态混合候选均不会被 gid 顺序覆盖。
- reranker 不适用时输出与 rerank=false 逐位相同。

### FS-204 KB-1.2 与 SDK 上下文预算

**分块 profile 推荐裁定**：profile 变化先只影响新摄取文档，并把 profile 写入 provenance；批量重跑能力等 KB-3 完成后提供。这样不在没有作业面时引入隐式后台重建。

**实施**：

- 暴露 chunk target、overlap 和 profile provenance；对坐标与引用做回归。
- TS/Python 增加与 MCP 一致的总字符预算，区分 per-hit truncate 与 total budget。
- SDK 返回 dropped/truncated/context_chars，不估算不存在的 token 精度。

**验收**：

- overlap 不破坏 page/bbox/heading/section 引用。
- 同文件同 profile 结果确定；profile 变化可追溯。
- MCP、TS、Python 对同一 hits 和预算给出相同保留集合。

## 6. 里程碑 M3：摄取作业面（P1）

M3 在 FS-201 合并后开始，避免与 `chunk_signal` 同时修改 DDL。

### FS-301 `ingest_job` 存储与状态机

**开始前必须裁定**：worker 写入口、适配器下沉、ObjectStore 是否拆 crate、source URI hash、覆盖语义和同步阈值。推荐：采用 job-scoped 写入口，ACL 从 job 行恢复；同 doc 默认覆盖且不保留版本，避免越过 KB-4 边界。

**实施**：

- 普通 PG 表实现 queued/parsing/chunking/embedding/indexed/failed。
- 使用 lease owner/epoch、heartbeat、`FOR UPDATE SKIP LOCKED`、retry/backoff；不进入 publication。
- 无 PG 一律 503，不建立内存 job 真源。

**验收**：

- 多 worker 不重复完成同一 epoch；旧 lease worker 的回写被 fencing 拒绝。
- 重试耗尽形成可观察 dead-letter，不增加第七个权威状态。
- tenant/ACL 与 chunk 行同构，不新增身份模型。

### FS-302 上传与状态 API

**实施**：

- `POST /v1/documents`：小文档同步 200，大文档/OCR/VLM 202，两档返回同构。
- `GET /v1/jobs/{id}` 与 `GET /v1/documents`：服务端 ACL 注入、分页、状态、错误和 chunk 数。
- 原始文件进入 ObjectStore；大文件采用预签名或分片，避免继续受全局 20MB 限制。
- job-scoped `/v1/jobs/{id}/chunks` 从 job 行注入 tenant/ACL，不使用 worker key 身份覆盖。

**验收**：

- 两个 tenant 互相看不到 job、文档、原始字节和错误信息。
- 同 hash 重复上传符合已裁定幂等语义。
- 所有新路由有 auth、ACL、rate-limit、audit 与 OpenAPI 测试。

### FS-303 独立 ingest worker 与 MCP 闭环

**实施**：

- 新建独立 `fastsearch-ingest-worker`，解析适配逻辑下沉到轻量 adapter crate；server/engine 不依赖 docparse。
- worker 领取 job、解析、分块、写 job-scoped chunks、更新状态并定期 heartbeat。
- MCP 远端档新增 `ingest_document`，同步档一次返回终态，异步档返回 job 与轮询提示。

**验收**：

- `hot-path-isolation` 持续全绿。
- worker/server 可独立扩缩容；worker 故障、重启、租约抢占后收敛。
- Agent 能用 MCP 完成上传→状态→搜索→引用，不需要自行拼底层 chunk。

### FS-304 作业面故障注入与运维指标

**验收矩阵**：

- 原始字节落对象存储后崩溃。
- job 建立后、领取后、解析后、embedding 后、PG chunk 写入后、派生 commit 前、CDC advance 前崩溃。
- embedder 429/5xx/超时，PG 短断连，对象存储失败，worker lease 过期。
- 每种故障均有明确 retryable/non-retryable 分类，最终能收敛或进入可操作死信。

## 7. 里程碑 M4：外部依赖与发布候选（资源门控）

以下项目只有资源具备时启动；未实跑前保持 `gated`：

| 项目 | 前提 | 最低验收 |
|---|---|---|
| 真实跨模态 KB-2.5 | 图文同空间模型服务 | ≥20 图含难负例，单路/融合 recall、nDCG 分开报告并进回归门禁 |
| OvisOCR2 门 0–3 | VLM 服务 + GPU/可接受 CPU 环境 | 形态、坐标、质量、速度四门逐项结论；失败允许停止路线 |
| S3/MinIO | 真实兼容服务 | 上传、Range、presign、过期、删除、跨 tenant 拒绝全链路 |
| PG/CDC 生产档 | pgvector + logical replication | 长跑、WAL lag、断连恢复、多副本首启、重建演练 |
| K8s/HA | test namespace | readiness、滚动升级、多副本、持久卷、故障恢复 |
| 发布候选 | M0–M3 完成 | tag、CHANGELOG、LICENSE/NOTICE、镜像、SDK 包、升级说明齐全 |

ColPali/MaxSim、视频精定位、流式 CDC、Helm chart、蓝绿索引切换属于 M4 之后的独立项目，不塞入 0.2 候选关键路径。

## 9. 迭代执行规则

### 9.1 每个 issue 的 Definition of Done

1. 复杂改动先更新对应 plan/spec，写明兼容与回滚。
2. 源码与测试同一改动；涉及契约时同步 OpenAPI、TS、Python、MCP。
3. `cargo fmt --all --check`、clippy `-D warnings`、workspace test 全绿。
4. 改 PG/CDC 必须在真 pgvector + logical replication 上执行，日志写明 executed 数量。
5. 改检索行为必须跑 golden；改外部面必须跑真二进制 e2e。
6. 无外部资源只能标 `代码完成/待运行验证`，不能标“已完成”。
7. 回写本文状态，并只在必要处更新旧 plan 顶部链接，避免多看板并存。

### 9.2 文件冲突与可并行通道

| 通道 | 工作 | 规则 |
|---|---|---|
| A 可信度 | FS-001/002/003/004 | 可与 CDC 并行，但 FS-002 会碰 core/server/SDK |
| B CDC | FS-101/102/103 | 通道内串行，共享 sync/engine/PG 测试 |
| C 检索 | FS-201→202→203 | 201 先于真正多路 Engine；202/203 都改排序，串行 |
| D 摄取 | FS-301→302→303→304 | 必须在 FS-201 DDL 合并后开始 |
| E 外部资源 | M4 | 与本地通道隔离，只有资源可用时运行 |

### 9.3 建议的阶段出口

- **出口 A**：M0 全部完成，主干门禁可信，可开始大改。
- **出口 B**：M1 完成，PG/CDC 正确性可以承载新表与新 worker。
- **出口 C**：M2 完成，多表示数据与可解释多路检索闭合。
- **出口 D**：M3 完成，Agent 可直接摄取文档并观察/恢复作业。
- **出口 RC**：M4 中与目标部署相关的真实验收完成，发布 0.2 候选。
