## 1. 迭代目标与边界

### 1.1 本阶段要达到的结果

完成本计划后，项目应达到“**0.2 候选：可重复验收的知识库引擎**”状态：

1. CI 不再受 HNSW 随机构图偶发失败影响，外部依赖测试的“执行/跳过”清楚可见。
2. Rust 请求结构、OpenAPI、MCP 和 SDK 的公开契约一致，`explain` 不再静默失效。
3. CDC 对 PK UPDATE、TRUNCATE、错误原子性和多副本 slot 首建具有明确、已验证的语义。
4. 同一 chunk 能持有多路具名信号，Engine 能实际消费多路并解释来源。
5. 文档可经 server 上传、同步或异步处理、查询状态、失败恢复；worker 不改变上传者 ACL。
6. 根发布元数据、文档状态和 CI 入口达到可发布候选的最低要求。

### 1.2 本阶段不做

- 不做 KB-4：用户/组织/角色、Dataset/Source 产品对象、版本回滚和 UI，继续遵守职责边界 ADR。
- 不把 HashEmbedder 或 caption-as-text 宣称为真实跨模态质量。
- 不在没有真实模型/对象存储/集群时宣称 OvisOCR2、S3/MinIO、K8s/HA 已完成。
- 不同时改 `chunk_signal` 和 `ingest_job` DDL；二者共享 `fastsearch-pg/src/sql.rs`，必须串行。
- 不通过降低有效召回阈值掩盖 HNSW 随机测试问题。

### FS-101 PK UPDATE 与 TRUNCATE 语义 ✅（2026-08-31）

**实施**：

- Update 同时读取旧 key 与新 tuple；主键变化时生成 `Delete(old)` + `Upsert(new)`。
- 为 `Change`/`IndexSink` 增加 TRUNCATE/clear 语义，清空对应派生 text/vector 索引。
- 将 `map()` 从单变更返回升级为零到多变更，保持同事务内顺序确定。
- relation 守卫从形状判定升级为配置化表名白名单，避免未来旁表形状碰撞。

**验收**：

- 真 PG 修改 collection/doc_id/chunk_id 后，旧 citation 不再命中，新 citation 命中。
- 真 PG TRUNCATE 后，keyword/vector/hybrid 均不返回旧结果。
- 非 chunks 表仍不产生 chunk 变更。

**完成记录**：

- `Change` 新增 `Clear` 与同 LSN 有序 `Batch`；PK 变化被映射为 `Delete(old)` 后接 `Upsert(new)`，整组应用成功后才推进水位。这里保证顺序与可重试性，不提前宣称 FS-102 所负责的派生索引事务原子性。
- pgoutput 映射由单变更升级为零到多变更；UPDATE 同时读取 old key/tuple 与 new tuple，普通非 PK 更新仍只产生一次 upsert，TRUNCATE 仅在包含配置真源表 OID 时产生 clear。
- `ReplicationConfig.source_table` 提供精确 `schema.table` 白名单，默认 `public.fastsearch_chunks`；白名单与列形状双重守卫让同形旁表继续被忽略。
- Engine 的 clear 同时清空 text/vector 派生索引；server 新增 `FASTSEARCH_CDC_SOURCE_TABLE` 配置并同步更新中英文 Agent 使用文档与 sync/server spec。
- 使用 PostgreSQL 17 + pgvector、`wal_level=logical` 的 Docker 实库验证：修改 `collection/doc_id/chunk_id` 后旧 citation 消失且新 citation 命中；TRUNCATE 后 keyword/vector/hybrid 均无旧结果；旁表守卫单测通过。环境门禁为 PG/CDC `executed=21 skipped=0 missing=0`。
- TDD RED 阶段新增用例因缺少 `Clear`/`Batch`/零到多映射产生 17 个编译错误；GREEN 后 sync 单测 23/23、CDC 实库套件 6/6、workspace 全量与 fmt/clippy 全绿。详见 [FS-101 开发日志](../devlog/2026-08-31-FS-101-PK更新与TRUNCATE.md)。

### FS-102 `IndexSink` 原子性与批量嵌入 ✅（2026-08-31，复审完成）

**实施**：

- 先完成嵌入准备、确定性向量约束预检和 PG 批内事务，再改变 text/vector 派生状态；这些已注入的失败不得留下可被后续 commit 带出的半状态。
- CDC batch 收集文本后批量调用 `embed_multi`，将网络等待移出全局 Engine 锁。
- 明确单 chunk 与 batch 的失败策略：全批回滚或可证明幂等的逐项提交，禁止模糊混用。
- 增加 embedding 超时、维度错误、PG 写穿失败和进程崩溃的故障注入。

**验收**：

- 本项故障注入覆盖的失败后 keyword/vector 对同一版本保持一致；重试后收敛到 PG 真值。跨 PG 与本地文件的进程崩溃窗口不伪装成分布式事务，纳入 FS-103 恢复协议。
- 批量摄取时搜索延迟不再随 N 次串行 HTTP 线性阻塞。
- `bench_capacity` 给出改造前后吞吐、p95 和锁等待数据。

**完成记录**：

- `IndexSink::apply_changes` 成为批次接缝，Engine 覆写为 prepare→publish：先完成全批 metadata/媒资校验、一次 `embed_multi`、向量数量/维度/有限值及当前索引维度预检，再排队 text/vector 变更；准备失败不会污染 Tantivy writer，Delete/Clear 也不会先于后续维度错误留下半批向量。
- `PgStore::write_embeddings_atomically` 把同批 set/clear 放入一个 PostgreSQL 事务；真实 PG 触发器令第二条写穿失败的负控曾留下第一条向量，改造后整批回滚，解除故障后同 LSN 批次重试让 keyword/vector 共同收敛。
- server 改用 `Engine::consume_once_shared`：peek、对象读取和批量嵌入在全局 Engine 锁外；PG 写穿事务与本地发布/持久化持锁，避免运行中搜索看到 PG 新向量与旧关键词；日志输出 prepare、lock_wait、lock_hold 微秒数。bootstrap/rebuild 同样一次批量嵌入。
- 故障注入覆盖 embedding timeout、返回维度错误、发布期索引维度冲突、PG 第二条写穿失败、纯本地 apply 后/persist 前进程退出；均验证失败后两路停留同一版本且重试收敛。`Applier` 水位现仅在整批 apply + commit 成功后推进，commit 失败保持原水位。
- `bench_capacity` release 同机并发对拍（N=64、64 个摄取期搜索、模拟每外部请求 5ms）：逐条持锁 161.97 chunks/s、搜索 p95 405.818ms；批量 8292.12 chunks/s、搜索 p95 0.140ms，吞吐提升 51.19×；prepare 6.39ms、lock_wait 0.000ms、锁内发布 1.33ms。结果为开发机指示性基线，不外推生产。
- Docker PostgreSQL 17 + pgvector、`wal_level=logical` 下 CDC 实库套件 9/9 通过；环境门禁显式清单由 21 增至 24。详见 [FS-102 开发日志](../devlog/2026-08-31-FS-102-原子批处理与锁外嵌入.md)。
- 2026-08-31 完成提交后双轴复审：Spec 轴零缺口；Standards 轴发现单条 `Applier::apply` 与批量 `IndexSink::apply_changes` 重复维护 `Change` 分派。已让单条路径统一委托批次接缝并删除第二套递归 match，新增 batch-only sink 回归测试完成 RED→GREEN；`fastsearch-sync` 单测增至 25/25，复审结论两轴均通过。

### FS-103 LSN、slot 与运行健康 ✅（2026-08-31）

**实施**：

- 澄清或移除 `Applier` 生产未使用的水位跳过契约，统一事务 LSN/commit LSN 语义。
- `ensure_slot` 使用 advisory lock 或捕获 duplicate-object 错误，多副本并发首建幂等。
- 暴露 slot lag、last applied LSN、last successful poll、dead-letter count 和 rebuild-needed 状态。
- 为 pgvector 写穿与本地文件检查点增加持久化批次意图/启动恢复；明确 PG commit 前后崩溃时 readiness 阻断与重放/补偿规则，不宣称不存在的跨存储 2PC。
- 闭合 Tantivy commit、Turbo rerank sidecar I/O 等本地存储错误：以 staging/swap 或持久化 undo journal 保证失败后恢复批前版本；在此之前 readiness 必须能标记 rebuild-needed。
- 保持 polling 为本阶段默认；流式 `START_REPLICATION` 另立性能项，不与正确性重构混做。

**验收**：

- 8 个并发实例创建同一 slot 全成功。
- 崩溃发生在 peek、apply、persist、advance 四个位置时，重启后不丢不重。
- readiness 能区分“进程活着”与“真源/CDC 已可服务”。

**完成记录**：

- 生产 `consume_once`/`consume_once_shared` 移除 `Applier` 事件水位：事件 LSN 明确为 WAL 行/事务起点语义，checkpoint 与 slot advance 只采用本批最高 commit LSN；空轮询从磁盘 checkpoint 保留 last-applied LSN。
- `ensure_slot` 捕获 PostgreSQL `duplicate_object` 竞态；真实 PG 下 8 个并发任务 8/8 成功，恰有一个创建 slot。
- 新增持久化 `cdc-batch-intent.json`：PG 写穿/本地发布前 fsync `applying`，persist 后更新为 `persisted`，advance 后删除并 fsync 目录。它不冒充跨存储 2PC；失败或崩溃时 readiness 阻断，由未推进 slot 的同批幂等重放恢复，持续本地 I/O 失败则要求从真源重建。
- `peek_batch` 暴露 commit LSN、slot lag 和死信；死信累计及 rebuild-needed 持久化，重启不能遗忘漂移。server 记录 last-successful-poll；CDC 开启后 `/readyz` 在 starting/source-error/rebuild-needed 返回 503，健康轮询后才返回依赖级 200；CDC 未开启时保留原进程级契约。Prometheus 新增七项 CDC 指标。
- 启动恢复 fail closed：CDC 缺 `DATABASE_URL` 直接拒绝启动；已有 slot + 本地 checkpoint=0 且无未完成意图时拒绝错误增量续跑，新副本须使用独立 slot 或从真源重新 bootstrap；新建 slot 的空表也持久化一致点。
- 真实 PG 故障测试覆盖并发首建、写穿失败留存/重放恢复意图，以及 peek/apply/persist/advance 四个崩溃点；最终均无丢失、无重复。CDC 实库 12/12 通过，显式 PG 环境门禁由 24 增至 28。详见 [FS-103 开发日志](../devlog/2026-08-31-FS-103-LSN-slot与运行健康.md)。

| E 外部资源 | M4 | 与本地通道隔离，只有资源可用时运行 |

### 9.3 建议的阶段出口

- **出口 A**：M0 全部完成，主干门禁可信，可开始大改。
- **出口 B**：M1 完成，PG/CDC 正确性可以承载新表与新 worker。
- **出口 C**：M2 完成，多表示数据与可解释多路检索闭合。
- **出口 D**：M3 完成，Agent 可直接摄取文档并观察/恢复作业。
- **出口 RC**：M4 中与目标部署相关的真实验收完成，发布 0.2 候选。

## 10. 风险与止损条件

| 风险 | 止损条件 |
|---|---|
| HNSW 上游无法固定随机性 | 不自行大改 ANN；改为统计门禁并保留 brute ground truth |
| `chunk_signal` 使 DDL/CDC 复杂度失控 | 保持 signal 表不进 publication；先只做 PG CRUD，不同时上多路 Engine |
| KB-3 越过产品控制面 | 一旦出现 user/role/dataset/version/UI 表，暂停并重新评审 ADR |
| worker ACL 无法从 job 行安全恢复 | 不允许退回普通 `/v1/index` + worker key；阻塞 FS-302/303 |
| 全局锁改造扩大风险 | 先完成批量嵌入和锁外计算，用基准决定是否分片 |
| 真实跨模态模型质量不达门槛 | 保留 caption-as-text，不为“已接模型”牺牲可解释基线 |
| 文档继续多看板漂移 | 本文作为唯一活动计划；旧计划只归档和链接，不再复制状态表 |
