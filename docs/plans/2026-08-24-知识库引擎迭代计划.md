## 0. "完善的知识库引擎"指什么（本文的口径）

拆成六条可验收的能力线（**L0 是 2026-08-24 复审新增，且排在最前**）。**前四条是引擎职责；第五条按 [2026-08-24 修订](../governance/2026-08-24-职责边界修订-摄取作业面收回引擎.md)一分为二——
作业面收回引擎，产品控制面仍归调用方**：

| 线 | 含义 | 现状 |
|---|---|---|
| **L0 Agent 易用** | agent 用**最少的回合与 token**完成"搜 → 拿上下文 → 溯源 → 往里加东西"；工具宣称的能力＝实际能力 | ⛔ **最弱的一环**：MCP 面只读、本地-only、宣称 hybrid 实为 keyword |
| **L1 摄取保真** | 给一份真实文档，出来的是**不丢信息**的可溯源 chunk：正文、表格结构、扫描件文字、**图片原始字节**、page/bbox 全在 | ⚠️ 格式覆盖齐全，**图片字节这一环断了** |
| **L2 表示完备** | 一个 chunk 可以有多种表示/信号（正文 / OCR / caption / 视觉向量），每种都知道来源、模型、版本、状态 | ⛔ PG 只有单 `embedding` 列 + `embed_model` |
| **L3 检索质量** | 多路召回 → **具名** N 路确定性融合 → **按模态**选重排 → 有真实数据的回归门禁 | ⚠️ 二路融合可靠；N 路、模态化重排、真实跨模态门禁都没有 |
| **L4 运维诚实** | 有无真源、能否重建、每条信号处于什么状态，都如实可观测 | ✅ 刚补齐（fail-closed plan）；信号级状态待 L2 |
| **L5 作业面 / 产品控制面** | 文档台账、摄取作业队列、来源版本、层级权限、UI | 🔓 **作业面已收回引擎**（KB-3）；**其余仍归调用方**——见 §1 |

**已经具备、本文不再重复规划**：混合检索内核（keyword/vector/RRF·归一化·加权）、不可绕过 ACL、
带 page/bbox/time 的安全 citation、PG 真源 + CDC + 快照重建、通用 chunk 管理 API（batch get/upsert/delete + 列表）、
10 种格式解析 + PP-OCR + UniRec 表格、四张脸（REST/库/MCP/CLI）、评测门禁框架、fail-closed 身份默认。

## 2.5 阶段 KB-0：Agent 面（新定位下的第一优先）

> 一句话：**使用者是 agent，不是知识库管理员。** 决定"方不方便用"的是四张脸里最像 agent 入口的那张——
> 而它恰恰是当前最弱、且**会对 agent 说谎**的一张。

### KB-0.1 MCP 能力诚实化 —— **bug 级，本计划最便宜的一刀**

- **事实**：`crates/fastsearch-mcp` **全 crate 零 embedder 引用**（`Cargo.toml` 与 `src/` 都没有）。
  但 `tool_defs()` 给 agent 的 `search` inputSchema 写着
  `"mode": {"enum": ["keyword","vector","hybrid"], "default": "hybrid"}`。
  而引擎的语义是（`fastsearch-engine/src/lib.rs` `run()` 上方注释与实现）：
  **`Hybrid` 无 `req.vector` 时静默退化为全文**，`Vector` 无 `req.vector` 时向量路直接不启用。
  ⇒ **agent 用默认 `hybrid` 调 MCP，拿到的永远是纯 keyword 结果，且没有任何提示**；
  显式传 `vector` 则近乎空召回。
- **为什么是本阶段第一刀**：[Agent 使用指南](../在Agent中使用fastsearch.md) §3.1 把 MCP 点名为
  **"Agent 原生（推荐给 LLM agent）"**，还把 `mode?` 列为可用入参。
  **这是文档与工具 schema 共同做出、代码无法兑现的承诺**——直接违反"重依赖 opt-in、诚实记账"，
  且打击面正是新定位的靶心。
- **做什么（第二轮复审后定稿：只做诚实化，不在 MCP 里养第二套嵌入配置）**：
  **schema 按运行时实际能力生成** —— 本实例能产出 query 向量就给三档，不能就只给 `keyword`；
  并且**显式传不支持的 mode 时返回可自纠的错误，而不是静默降级**。
  > **为什么不给 MCP 接 embedder（原 (a) 方案已撤回）**：`Engine::run()` **从不嵌入文本 query**——
  > `embedder` 只服务 `query_image`（`embed_query_image`），文本 query 的向量是 **server** 在
  > `search_request` 里算好塞进 `req.vector` 的。在 MCP 里补这条 = 复刻一份 server 的嵌入编排 +
  > 第二套 `FASTSEARCH_EMBED_*` 配置；而 **KB-0.2 做完后 hybrid 由 server 免费提供**。
  > 先做便宜且在两种未来下都正确的那一半。
- **验收**：① 不能产出 query 向量的实例，`tools/list` 里 `mode` 的 enum **只有 `keyword`**、
  `default` 为 `keyword`，`description` 如实说明本实例为纯全文；
  ② 显式传 `hybrid`/`vector` → **`isError:true` + 可自纠的错误文本**（告诉 agent 改用 `keyword`），
  **不再静默返回 keyword 结果**；③ `keyword` 路径行为零回归。
- **复杂度路径**：**简单需求**（单 crate、schema 生成 + 一处入参校验、可逆）→ 直接实施 + 回写 spec。
  **"schema 必须等于实际能力"这条要写进 MCP 的 spec/文档**，并作为 KB-0.2 的验收前提继续成立。
- **状态**：`[已实施 + 活服务验证 done · 2026-08-24]`

  **实施记录**：
  - `fastsearch-engine`：加 `Engine::has_embedder()`（3 行，仿既有 `has_pg_vector()`），
    并在文档注释里写明它**不**意味着能做文本语义检索（`run()` 从不嵌文本 query）——
    这条注释本身就是防止下一个人重犯同一误解的护栏。
  - `fastsearch-mcp`：`tool_defs()` 由 `pub fn` 改为 `McpServer` 的方法，`mode` 的 enum/default/描述
    全部由 `search_modes()` → `can_embed_text_query()` 推导；新增 `reject_unavailable_mode()`
    守卫（放行"调用方自带 `vector`"与"带 `query_image` 且引擎有 embedder"两条真能走通的路）。
  - **对齐两个 default**：`SearchRequest` 的 serde 默认是 `Hybrid`，而 schema 宣称 `keyword`
    ⇒ `tool_search` 检测 `mode` 是否**显式**给出，未给则按 schema 宣称的 `Keyword` 走。
    **不做这一步的话，agent 省略 mode 仍会掉进原来的静默退化**——这是本条最容易漏的一环。
  - 测试 +4（能力宣称、省略 mode 不退化、显式档报可自纠错、自带向量不误伤）；
    收口：fmt 净 / clippy `-D warnings` 0 告警 / `cargo test --workspace` **349 passed, 0 failed**。
  - **活服务验证**（实跑 `fastsearch-mcp` 二进制走 stdio JSON-RPC）：
    `tools/list` 返回 `{"enum":["keyword"],"default":"keyword"}` ✅；
    显式 `mode=hybrid` → `isError:true` + 三条改法 ✅；省略 mode → 正常返回命中 ✅。
  - 文档同步：[Agent 使用指南](../在Agent中使用fastsearch.md) §3.1（中/英各一处）、
    [00-模块拆分](../specs/00-模块拆分.md) 第 11 行。
  - **已知限制**：`query_image` 未在本面 schema 中宣称；若调用方硬传且引擎无 embedder，
    引擎侧仍是"静默不嵌"的老语义（守卫只在 mode 需要向量时才拦）。等 KB-0.2 一并处理。

### KB-0.2 MCP 远端模式：从"本地目录 only"到"能指向 server"

- **事实**：`fastsearch-mcp` 的 main 直接 `Engine::open(&data, cfg)` —— **它嵌引擎、读本地索引目录**，
  不是 REST 客户端。且 ACL 来自进程级 env（`FASTSEARCH_MCP_TENANT` / `_TAGS`），是**一个常量**，不是每请求身份。
- **后果**：① agent 宿主必须与索引数据同机、同文件系统；② **多租户场景用不了 MCP**
  （一个进程一个租户）；③ 与 server 的能力（嵌入后端、pgvector 直查、限流、审计）全部不共享。
  相比之下 CLI 早在 2026-06-28 就改成了纯 REST 客户端，MCP 是**唯一还嵌引擎的脸**。
- **做什么**：给 MCP 加 `--server/--key`（env `FASTSEARCH_SERVER`/`_KEY`）的**REST 客户端模式**，
  与 CLI 同款；保留本地嵌入模式作为单机默认。身份随 key 走 ⇒ ACL 回到"服务端从认证身份注入"的正道。
- **验收**：同一 MCP 客户端配置指向远端 server 时，`search`/`resolve_citation` 结果与直连 REST 一致；
  两个不同 key 的 MCP 实例看到不同可见集；本地模式不回归。
- **复杂度路径**：**复杂**（新增运行模式 + 触及 ACL 注入路径）→ **先立 spec**，
  且必须有"越权用例进测试"（不变量 #3）。

### KB-0.3 MCP 摄取工具：让 agent 能**往知识库里加东西**

- **事实**：MCP 面只有 `search` + `resolve_citation`，**全只读**。agent 无法把一份资料存进知识库。
  （对照：`vendor/docparse` 自己的 MCP 反而有 `parse_document`/`get_chunks`/`outline`/`locate` 五个工具。）
- **为什么**：定位是"agent 方便使用的知识库"，那"agent 读到有用的东西 → 存进去 → 以后能搜到"
  是基本闭环。现在这个闭环缺一半。
- **做什么**：加 `index_chunks`（已分块，薄封装 `/v1/index`）与 `ingest_document`（给路径/字节，走 KB-3 的上传端点）。
  ACL 仍由服务端注入，工具入参不得夹带 tenant/acl。
- **依赖**：KB-0.2（远端模式，否则写入没有身份）+ KB-1.4（摄取契约）+ KB-3.2（上传端点，大文档）。
  **小文档可先只做 `index_chunks`，不必等 KB-3。**
- **验收**：agent 经 MCP 存入 → 立即可搜到 → `resolve_citation` 能回原文；
  伪造 tenant/acl 入参无效；越权用例进测试。
- **复杂度路径**：**复杂**（新增写入口）→ 立 spec，与 KB-0.2 可合并一份。

### KB-0.4 上下文预算：agent 的稀缺资源是 context，不是磁盘

- **做什么**：在 **SDK / MCP 层**（**不是 engine**）提供 `max_context_chars|tokens` 与 per-hit 截断，
  超预算时按分数序丢弃尾部并如实报告"已截断 N 条"。
- **为什么**：TS SDK 的 `formatHitsForLLM` 已有 `maxCharsPerHit`，但 **MCP 面完全没有对应能力**，
  而 MCP 恰恰是 agent 直连的那张脸；`include_text=true` 全开会直接冲爆 agent 上下文。
- **落点必须在外层**：[FastGPT 参考建议 §5.2-5](2026-08-24-fastgpt知识库与多模态检索参考建议.md) 已论证
  **token 预算是答案层约束，不该塞进通用 engine 的 top-k**——本条遵循该结论，engine 一行不动。
- **验收**：给定预算，返回内容稳定不超预算；截断是确定性的（同输入同结果，不变量 #4）；
  被截断这件事对 agent 可见（不静默丢证据）。
- **复杂度路径**：**简单**（SDK + MCP 序列化层）。

### KB-0.5 Agent 自纠友好：错误信息与工具自描述

- **做什么**：① 每个工具的 `description` 说明**本实例**的 collection、可用 filter 字段、能力档位
  （而不是泛泛的"混合检索引擎"）；② 错误信息写成 agent 能据以自纠的形式。
- **为什么**：agent 没有人类的试错直觉，它只能读错误文本。本仓已有很好的范式——
  fail-closed 那次把启动错误写成"可直接粘贴的两条修复命令"。把这条惯例推广到工具面。
- **验收**：常见错误（collection 不存在、filter 字段拼错、越权、能力不支持）的返回文本里，
  都含"下一步该怎么改"的可执行指引。
- **复杂度路径**：**简单**，可随 KB-0.1/0.2 顺带。

## 3. 阶段 KB-1：摄取保真（不触 ADR，立即启动）

> 一句话：**让"文档进来"这件事不丢信息**。这三条做完，"调用方拥有解析"才真正可行。

### KB-1.1 图片字节闭环 —— 本阶段唯一的真 bug 级缺口

- **做什么**：`fastsearch ingest` 解析后**显式导出图片字节**（docparse 侧已有 `embed_images` / `export_images`，
  对应 CLI 的 `--image-embed` / `--image-dir`），经 `from_docparse_chunk` 落成 `media_bytes`（Inline）
  或 `media.asset=Object{uri}`；新增 `--images=inline|object|none` 选项控制。
- **为什么**：当前 `cmd_ingest` 从不调这两个函数，而适配器只从 `ImageMeta.data_base64` 解字节
  ⇒ 走 `fastsearch ingest` 的文档图片**只有坐标和 caption，原始字节从没进过系统**。
  下游一切视觉能力（`image_vector_status=Embedded`、图搜图、引用回看显示原图）都建在这个空地基上。
  PDF 侧还叠一层：`PdfParser.decode_images` 为省内存**默认关闭**，要一并按需打开。
- **落点**：`crates/fastsearch-cli/src/ingest.rs`（`cmd_ingest` / `from_docparse_chunk` / `IngestOpts`）。
- **验收**：含图 PDF + DOCX 各一份，摄取后 ①`media_bytes` 非空且 **hash 与源图一致**；
  ②`page`/`bbox` 不变（`resolve_citation` 仍能高亮）；③配了跨模态 embedder 时 `image_vector_status=Embedded`，
  未配时为 `TextFallback`/`Pending` 而**不是** `MissingBytes`；④`--images=none` 时行为与今日一致（不回归）。
- **复杂度路径**：**简单需求**（单 crate、落点清晰、可逆）→ 直接实施 + 回写 [17-cli spec](../specs/17-cli.md)。
  内存/体积是真实约束（整本 PDF inline base64 会撑爆 20MB body 上限）⇒ 默认 `object`、`inline` 需显式选。

### KB-1.2 分块 profile：可配置 + 可追溯

- **做什么**：把 `ChunkOptions`（`target_chars` / `table_markdown`，并**新增 overlap**）从
  `chunk_document(&doc)` 的硬默认里放出来，暴露为 CLI 选项与"每 collection 的分块 profile"；
  profile 标识 + 版本写进 chunk 的 `metadata`（provenance），使"这批 chunk 是用什么策略切的"可查。
- **为什么**：知识库产品必然要按语料调块长与重叠（`target_chars=800`、**无 overlap**、CLI 完全不暴露）。
  更关键的是**没有 provenance 就无法安全地改策略**——改完不知道哪些文档该重切。
- **落点**：`vendor/docparse/.../chunk.rs`（加 overlap）、`crates/fastsearch-cli/src/ingest.rs`、
  （若做 per-collection profile）`fastsearch-server` 的 collection registry。
- **验收**：同一份 PDF 用两组 profile 摄取 → chunk 边界不同但 page/bbox 仍精确；
  chunk 的 provenance 能反解出 profile；overlap>0 时相邻 chunk 文本重叠符合设定且 `char_len` 一致。
- **复杂度路径**：**复杂**（改 vendor 分块语义 + 影响检索结果 + 动契约）→ **先立 spec**。
  必答：profile 变更后已索引文档是**懒重建 / 批量重跑 / 只影响新文档**（见 §8 待决策）。
  注意 `vendor/docparse` 是被根 `exclude` 的独立 workspace，改它要单独收口。

### KB-1.3 自然图 caption —— **前置条件当前不成立，本阶段只做前置**

- **做什么**：*不*直接接 `--vlm-describe`。先解决"区域级调用下 VLM 不自行 EOS"的问题。
- **为什么**：docparse 侧 `vlm_describe` 早就有，fastsearch ingest 没接——但据仓内实测记录
  （commit `8157abd`/`662fd13`/`821d2f6` 门 0 系列，转引自 [FastGPT 参考建议 §8-3](2026-08-24-fastgpt知识库与多模态检索参考建议.md)）：
  OmniDocBench 人工 GT + 精确 TEDS_X（N=4）下 **UniRec 0.968（4/4 产出）、OvisOCR2 走产品路径 0.000**，
  4/4 `finish_reason=length`、0 次 `stop`——**页级模型当区域级识别器用，在"裁一个区域 + 要结构化输出"这个组合下它不停**。
  这不是模型差，是调用形态没跑通。**接上去只会把 0.000 引进摄取链路。**
- **验收（本阶段只到这）**：给出一组区域级调用配置，在 N≥10 的区域样本上 `finish_reason=stop` 占比 ≥90%，
  且 TEDS_X 不低于 UniRec 基线；达不到就**如实结论"该形态不可用"并停在这里**，不进 KB-2。
- **复杂度路径**：**调研/实验**，产出实测报告而非功能；结论为正才另立接线 plan。

### KB-1.4 摄取契约固化：让"调用方拥有解析"真正可行

- **做什么**：把[现状文档 §4 的配方](2026-08-24-作为知识库使用-文档摄取现状与差距.md)升级为一等交付物——
  ①`docs/` 里一份"非 Rust 调用方如何接文档摄取"的正式指南（docparse serve 或任意解析器 → 字段映射 → `/v1/index`）；
  ②TS/Python SDK 各加一个 `chunksFromDocparse()` 适配 helper（当前只有 Rust 侧 `from_docparse_chunk`）；
  ③`example/` 的自研 chunker 换成走这条正式路径，作为活文档。
- **为什么**：**ADR 把解析推给调用方，那这条缝就是产品表面**（同 ADR 对身份契约的论证："身份契约升格为一等交付物"）。
  今天调用方要自己读 Rust 适配器源码才能拼对 JSON——这是把职责推出去、却没把契约交出去。
  `example/` 自己写 chunker + SQLite 台账，就是这个欠账的证据。
- **落点**：`docs/`、`clients/{typescript,python}`、`example/src/server/lib/`。
- **验收**：照指南从零接一个非 Rust 调用方，跑通"上传 PDF → 可检索 → citation 能高亮"；
  SDK helper 有单测（含图片三态 Inline/Object/DocRegion 映射）；`example` 改造后行为不回归。
- **复杂度路径**：**简单**（文档 + SDK 薄封装），但**必须在 KB-1.1 之后**（否则固化的是断链契约）。

## 4. 阶段 KB-2：表示完备与检索质量（不触 ADR，但改内核契约）

> 一句话：**让一个 chunk 能诚实地持有多种信号，并让检索用得上它们**。
> 本阶段每一项都"影响检索结果或数据契约"⇒ 按 DEV_SPEC §0 **各自先立 spec**，不得作为顺手的 bullet。

### KB-2.1 `chunk_signal` 多表示子表

- **做什么**：新增 PG 子表，键含 `GlobalId + signal_type`，列含 `model`/`version`/`status`/`artifact_hash`/`embedding`。
  signal_type 至少覆盖 `user_text` / `ocr` / `asr` / `vlm_caption` / `image_bytes`。
- **为什么**：当前 PG 只有单 `embedding` + `embed_model`，"这一路向量到底是正文的、caption 的还是原图的"无法区分，
  也就无法做 §KB-2.2 的具名融合、无法审计、无法只重建其中一路。
- **两条必答的既有约束**（照抄 [FastGPT 参考建议 §5.2 的复核补充](2026-08-24-fastgpt知识库与多模态检索参考建议.md)，它们不是实施时能顺手决定的）：
  1. `upsert_chunk_sql` 的 `ON CONFLICT … embedding = NULL`（及 `upsert_doc` 的 delete+insert）
     是**有意的"正文变了就作废旧向量"防错配设计**。多信号之后必须重新定义**正文变了该作废哪些信号**
     （OCR 信号随正文废；视觉信号未必）。
  2. **新表不要进 publication**。且注意现有 DDL 用的是
     `ALTER PUBLICATION fastsearch_pub SET TABLE {table} (…)`——`SET TABLE` 是**替换**语义，
     所以任何在别处 `ADD TABLE` 进来的第二张表，**会在下次 server 启动时被静默移除**。
     要么明确"publication 永远单表"，要么改 DDL 为 `ADD/DROP` 精确收敛——**二选一，要写进 spec**。
     （反馈环本来就不是靠列清单断的：列清单只过滤值、不抑制事件，真正的阻尼是 `set_embedding` 的
     `IS DISTINCT FROM` 幂等守卫——新表若进流，这层阻尼不自动适用。）
- **验收**：同一 chunk 同时持有 caption 与视觉两路信号；正文更新后按规则作废正确的子集；
  CDC 重放后信号表收敛到真源；`DATABASE_URL` 集成测试覆盖；托管 PG 可移植不破（无新扩展）。
- **复杂度路径**：**复杂**（DDL + CDC + 数据契约）→ **先立 spec**，同 commit 更新 `sql.rs` DDL 与 golden。

### KB-2.2 N 路具名融合

- **做什么**：把二路 `fuse` 泛化为 `Vec<RecallList{source, weight, items}>`，
  来源至少 `keyword:user_text`、`vector:user_text`、`keyword:image_caption`、`vector:image_caption`、`vector:image_bytes`；
  hit/explain 里带每路 rank/score/model。保持同分按 `GlobalId` 升序 tie-break（不变量 #4）。
- **为什么**：图片 query 今天只有单路视觉，模型不可用时没有 caption 兜底；
  多信号（KB-2.1）落地后没有 N 路融合就用不上。
- **契约破坏面（本项最容易被低估的地方）**：`Fusion` 枚举的
  `Normalized{semantic_ratio}` 与 `Weighted{alpha}` 是**结构性二路**的（一个标量分给两边），
  改 N 路等于**换枚举形状**，牵动 `SearchRequest` 序列化契约、CLI/TS/Python SDK、以及全部 golden baseline。
  **`Rrf` 是天然可 N 路化的 ⇒ 第一步只动 RRF**；两个加权档单独一轮，且必须给向后兼容方案。
- **验收**：单路结果与今日逐位一致（回归）；N 路 RRF 确定性（同输入同序）；
  权重**只由版本化评测选择**，绝不把 FastGPT 的 0.3/0.7、1/0.7 设为默认；explain 能反解命中来源。
- **复杂度路径**：**复杂 + 破坏契约** → **单独 spec + 向后兼容方案**。

### KB-2.3 按模态选重排

- **做什么**：给 `Reranker` 加 capability 自描述（是否支持 image/多模态），编排层按候选模态与 reranker 能力决定是否重排；
  重排失败/不适用时**保持原召回序**。
- **为什么**：`Reranker::rerank(&self, query: &str, candidates: &[String])` 的签名**结构上只能吃文本**——
  这不是某个实现的缺陷，是编排层该拦的。纯图片 query 那条已在今日修复（整段跳过 rerank），
  但**已知限制仍在**：query 非空却被分词器切空（纯标点、分词器不认的语种）时仍会退化成 gid 序（见 [14-engine spec](../specs/14-engine.md)）。
- **验收**：image-only、query 被切空、多模态混合候选三种情况下顺序均不被 gid 覆盖；
  未启用多模态 reranker 时视觉序与不带 rerank 完全一致。
- **复杂度路径**：**复杂**（改 trait + 影响排序）→ 立 spec（可与 KB-2.2 合并一份）。

### KB-2.4 Embedder 能力探测

- **做什么**：启动时做一次可缓存的 capability probe：固定文本 + 小图各请求一次，
  校验数量、维度、有限值、重复稳定性；结果写进 introspection 与 metrics。
  失败时**显式二选一**：拒绝启动，或降级 text-only 并如实标注。
- **为什么**：`EmbedCaps{dim,text,image,cross_modal,semantic}` 目前**直接信任环境配置**，
  没有任何证据表明外部模型真的收图、真的同维、真的文图同空间。现有 live test 只覆盖文本。
  这与 fail-closed plan 的 B 条（运行档如实可观测）是同一条原则的延伸。
- **验收**：配一个只支持文本的服务却声明 `image=true` → 探测失败并按选定策略处理；
  introspection/metrics 反映**实测** caps 而非配置声明。
- **复杂度路径**：**中**（单 crate + server 启动流程）→ 可作为 fail-closed plan 的续篇，不必新 spec，但要回写 [16-embed](../specs/16-embed.md)。

### KB-2.5 真实跨模态质量门禁

- **做什么**：接一套真实跨模态服务，建 ≥20 张图 + 难负例的 golden：同图、近似图、语义相似但视觉不同、
  caption 错误、OCR 图表、跨语言文搜图；**分别报告单路与融合后的 recall/nDCG**，接入 `assert_no_regression`。
- **为什么**：仓内至今没有真实视觉质量证据，现有多模态门禁只验证 caption/转录文本的 keyword 召回。
  没有它，KB-2.1/2.2 的权重与信号取舍全是拍脑袋。
- **前置**：KB-1.1（图片字节）+ 一个真实图文同空间模型服务（外部资源）。
- **验收**：门禁在 CI 可跑（模型服务缺失时 env-gated 跳过而非假绿）；换模型/换权重必须过回归阈值。
- **复杂度路径**：**复杂 + 依赖外部资源** → 独立 plan，未真机跑通前一律标 `gated`。

## 5. ✅ 阶段 KB-3：文档摄取作业面（闸门已开）

### 5.0′ 闸门已走过：推翻的精确边界与红线

`[已决 2026-08-24]` [职责边界修订](../governance/2026-08-24-职责边界修订-摄取作业面收回引擎.md)：
**只推翻"摄取任务队列"一项**，收回的是**摄取过程的状态与可恢复性**，不是任何产品对象、层级、版本或权限模型。
三条理由的回应摘要：① 收回的是**一张表 + 两个端点 + 一个独立二进制**，而非一批产品表，
且"崩溃安全"这条卖点今天在摄取路径上本来就是断的（`/v1/index` 同步单请求、失败无恢复点）；
② 作业面**继续对身份没有观点**（只存 Principal 编译出的 tenant/tags）；
③ **解析继续归调用方**，收回的是状态不是算力，`hot-path-isolation` 保持绿。

**七条红线（违反即回滚整个 KB-3；逐条进 spec 的验收清单）**：

1. `ingest_job` **无身份列**（无 owner/role/member/group/继承），只有 `tenant` + `acl`，与 chunk 行同构。
2. **不进 publication**；且须先解决 `ALTER PUBLICATION … SET TABLE` 的**替换**语义（见 KB-2.1）。
3. 托管 PG 可移植不破：只用普通表 + `FOR UPDATE SKIP LOCKED`（PG 核心特性），零原生扩展。
4. 热路径隔离不破：解析只在独立 worker 二进制里发生，`hot-path-isolation` 持续绿。
5. 无 `DATABASE_URL` → 作业面一律 **503**（同 `management_source`），不造第二个内存真源。
6. **不新增产品对象**：无 dataset/source/version 表，无层级，无回滚。
7. ACL 服务端注入不可绕过：上传/作业/状态每个新入口都要有"越权用例进测试"。

> **`GET /v1/documents` 的定性（修订文 §2 记下的判断）**：它是**对既有 chunk 行与作业行的派生只读视图**，
> 不建产品对象表、不带层级与版本。一旦它开始长出"属于哪个 Dataset""owner 是谁""第几版"，
> 说明边界已被越过——按修订文 §5 回滚。

### 5.1–5.5 技术方案（按序）

1. **PG `ingest_job` 表**：`job_id`、`collection`、`doc_id`、输入 URI + **内容 hash（幂等键）**、
   解析 profile、`state`（queued/parsing/chunking/embedding/indexed/failed）、阶段进度、
   `lease_until` + `heartbeat_at`、`retry_count`、`error`、时间戳。
   **约束**：领任务用 `SELECT … FOR UPDATE SKIP LOCKED`（PG 核心特性，不破可移植不变量 #1）；
   **不进 publication**（且先解决 §KB-2.1 说的 `SET TABLE` 替换语义问题）。
2. **`POST /v1/documents`**（multipart）：鉴权 → **身份注入同 `apply_ingest_identity`（ACL 不可绕过，不变量 #3）**
   → 原始字节落**对象存储**（复用 `ObjectStore`/`S3ObjectStore`，不要塞 PG bytea）→ 建 job。
   **响应形状按大小分档（2026-08-24 复审修正）**：
   - **小文档（阈值内）→ 同步做完 → `200` + 已可检索的 chunk 数**。
     对 agent 而言**一次 tool call 就完成、不必轮询**是刚需——少一个回合、少一轮 token。
     原稿无条件 `202 + job_id` 会把最常见的场景变成"至少两次调用 + 一个轮询循环"，是**降低**易用性。
   - **超阈值 / 需重解析（OCR/VLM）→ `202` + `job_id`**，并在响应里带**建议轮询间隔**与"当前能否检索"的布尔。
   - 阈值可配；两档的返回体**同构**（都带 `job_id`，同步档直接是终态），让调用方一套代码处理。
   注意现有全局 body 上限 20MB，大文件需要分片或预签名直传。
3. **状态与列表端点**：`GET /v1/jobs/{id}`（状态、阶段、错误、chunk 计数）、`GET /v1/documents`（列表 + 状态）。
   **无 `DATABASE_URL` 时一律 503**，与既有 `management_source` 一致——不造第二个内存真源。
4. **`fastsearch-ingest-worker` 新 crate**：领 job → docparse 解析 + 分块（复用 KB-1 的成果与 `from_docparse_chunk`）
   → `POST /v1/index` → 回写状态。**必须是独立二进制**：CI 的 `hot-path-isolation` 门禁对
   `server/engine/core/text/vector` 五个 crate 硬断 docparse 依赖，**把解析塞进 server 会直接变红**。
5. **幂等与替换语义**：同 hash 重复上传 → 跳过/覆盖/新版本三选一（需在 spec 里定死）；
   worker 崩溃 → 租约过期后可续；失败 → 死信状态 + 可重试，不允许"只存在于内存的作业"。

**验收**：注入失败点（PG 写入后 / embedding 后 / 派生 commit 前 / CDC advance 前）→ 重试或重启后收敛到 PG 真值；
跨租户不可见作业与文档；worker 与 server 可分开部署与限流。

## 6. 🚫 阶段 KB-4：产品控制面（**仍封禁，且封禁理由已增强**）

层级权限（owner/read/write/manage + 继承）、来源版本与回滚、模型 profile 产品化管理、UI。

**新定位下更站得住（2026-08-24 复审）**：使用者是 **agent**——agent 不需要管理界面、不需要角色配置向导。
把预算投进 KB-4，等于为一个**本定位下没有使用者**的表面买单。

**为什么单列且不建议**：这正是 ADR 理由 ② 打击最准的部分——一旦引擎自持 users/orgs/roles/继承，
"ACL 不可绕过"就退化为"ACL 的正确性 = 我们自研 RBAC 求值器的正确性"，正确性面积大一个量级；
FastGPT 那个被点名"绝不能照搬"的 `authTmbId=false` 跳过成员鉴权分支，正是自持控制面必然长出的口子。

**若真要做**：资源管理权限可有角色与继承，但**检索数据面必须编译成服务端注入的 tenant/tags 且不可放宽**，
SQL 下推与 Rust 精确后过滤两端都不可取消（不变量 #5）。这条红线写不进 spec 就不要开工。

## 7. 收口标准（每一项都适用，不可省）

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings     # 硬门禁，build 通过 ≠ 收口
cargo test --workspace                                     # 涉及 PG 的设 DATABASE_URL 跑集成
# 改了检索行为/契约/CLI：再用二进制**实跑**验证一遍（本仓惯例：活服务验证）
```

外加每项**必须对照的清单**：

1. 托管 PG 可移植（只 pgvector + 逻辑复制，无 `shared_preload_libraries`）
2. PG 是真源、派生可重建
3. ACL 服务端注入不可绕过（新增入口必须有"越权用例进测试"）
4. 确定性（同分 `GlobalId` 升序 tie-break）
5. 预过滤 SUPERSET + 精确后过滤两端一致
6. **ADR 职责边界 + 其修订的七条红线**（本计划新增的第 6 条——KB-3 受红线约束，KB-4 仍封禁）
7. 搜索热路径零 docparse/ONNX（CI `hot-path-isolation`）
8. 重依赖 opt-in、诚实记账（未真机验证标 `待运行验证`）

## 8. 依赖与建议顺序

```
KB-0.1 MCP 诚实化（bug 级，最便宜）── 独立，先做
KB-0.2 MCP 远端模式 ──→ KB-0.3 MCP 摄取工具 ←── KB-1.4（契约）+ KB-3.2（上传端点）
KB-0.4 上下文预算（SDK/MCP 层，独立）

KB-1.1 图片字节 ──┬─→ KB-1.4 摄取契约固化（SDK/文档/example）
                  │
                  ├─→ KB-2.1 chunk_signal ──→ KB-2.2 N路融合 ──→ KB-2.5 真实门禁
                  │                                  ↑              ↑
                  │        KB-2.3 模态化重排 ────────┘              │
                  └─→ KB-2.4 能力探测 ────────────────────────────┘
KB-1.2 分块 profile（独立，可并行）
KB-1.3 VLM 区域级前置实验（独立；结论为负则就地停止）
────────── 🔓 ADR 闸门已开（§5.0′，受七条红线约束）──────────
KB-3.1 job 表 → 3.2 上传端点 → 3.3 状态端点 → 3.4 worker crate → 3.5 幂等语义
────────── 🚫 仍封禁：启动即需连带回滚 KB-3 ──────────
KB-4（不做）
```

**建议第一刀（复审后改判）**：**KB-0.1**——它是 bug 级、改动最小、且直接打在定位上（agent 拿不到语义检索却不知道）。
紧随其后仍是 KB-1.1。原判"第一刀 KB-1.1"的理由依然成立，只是 KB-0.1 更便宜也更急：

**KB-1.1 的理由**：它是唯一"真 bug 级"、改动局部、当场可验、且被四条下游能力依赖的条目——
性质上与今日已修的那两条（image-only rerank、`/v1/index` 写穿）同档。

## 9. 用户使用例子（各阶段完成后的样子）

```jsonc
// —— KB-0 后：agent 眼里的知识库（这是新定位的主场景）——
// tools/list 只列本实例真实具备的能力：无 embedder 就没有 hybrid 这一档
{"name":"search","inputSchema":{"properties":{"mode":{"enum":["keyword"]}}},
 "description":"collection=kb（1.2 万 chunk，中文年报）。可用 filter 字段：page/kind/modality。本实例为纯全文（未配嵌入后端）。"}
// agent 一次调用拿到可直接喂 LLM 的上下文，且不超预算
{"name":"search","arguments":{"query":"毛利率","top_k":8,"max_context_tokens":1500}}
// → {"hits":[…], "truncated":3, "note":"已按分数序丢弃 3 条以满足预算"}
// agent 把读到的资料存进知识库（KB-0.3），身份由服务端注入，入参夹带 acl 无效
{"name":"index_chunks","arguments":{"collection":"kb","doc_id":"note-1","chunks":[…]}}
```

```bash
# —— KB-1 后：解析归调用方，但契约到位、图片不丢 ——
fastsearch ingest --images inline --chunk-target 500 --chunk-overlap 80 \
  --server http://localhost:8642 --key dev --collection kb --doc-id r.pdf r.pdf
fastsearch search --collection kb --image ./chart.png --json   # 图搜图能命中（KB-2.5 门禁背书）

# —— KB-2 后：命中能解释来源 ——
curl .../v1/search -d '{"query":"毛利率","explain":true}' | jq '.hits[0].sources'
# [{"source":"vector:user_text","rank":1,"score":0.83,"model":"bge-m3"},
#  {"source":"vector:image_caption","rank":4,"score":0.41,"model":"…"}]

# —— KB-3 后（闸门已开，红线内实现）：小文档一次就完，大文档才给 job ——
curl -X POST .../v1/documents -H 'x-api-key: k' -F file=@note.md -F collection=kb
# → 200 {"job_id":"…","state":"indexed","chunks":12}      ← agent 不必轮询
curl -X POST .../v1/documents -H 'x-api-key: k' -F file=@report.pdf -F collection=kb
# → 202 {"job_id":"…","state":"queued","searchable":false,"poll_after_ms":2000}
curl .../v1/jobs/<id>   # {"state":"embedding","stage":"3/4","chunks":142,"searchable":false}
```

## 10. 待决策

1. `[已决 2026-08-24 · 第二轮复审]` **KB-0.1**：只做**诚实降级**（schema 按运行时能力生成 + 显式 mode 报可自纠错误）；
   **不给 MCP 接 embedder**——语义检索能力经 KB-0.2（远端模式）从 server 免费获得，理由见该条目。
2. `[待决策]` **KB-0.2**：远端模式做好后，本地嵌引擎模式**保留还是弃用**？
   保留 = 两条 ACL 注入路径要各自守不变量 #3；弃用 = 单机零依赖的卖点没了。
3. `[待决策]` **KB-1.2**：分块 profile 变更后，已索引文档是**懒重建 / 批量重跑 / 只影响新文档**？
   决定 profile 是否必须写进 chunk provenance（本文按"必须写"规划）。
4. `[待决策]` **KB-2.1**：正文变更时该作废哪些信号？（OCR 随正文废、视觉未必——需逐 signal_type 定死）
5. `[待决策]` **KB-2.1**：`fastsearch_pub` 是"永远单表"，还是把 DDL 从 `SET TABLE` 改为精确的 `ADD/DROP` 收敛？
6. `[待决策]` **KB-2.4**：能力探测失败时是**拒绝启动**还是**降级 text-only**？（fail-closed plan 的先例倾向拒绝启动）
7. `[已决 2026-08-24]` **KB-3 闸门已开**：只推翻"摄取任务队列"一项，见[修订文](../governance/2026-08-24-职责边界修订-摄取作业面收回引擎.md)。
