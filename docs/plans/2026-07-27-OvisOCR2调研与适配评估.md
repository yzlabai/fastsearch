## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 对本项目有帮助吗？ | **有，且是高杠杆的**——但帮助点**不在 fastsearch 检索侧，全在 `vendor/docparse` 摄取侧** |
| 它打中了什么 | docparse 记分牌**当前最大的两个在案短板**：① 学术难表 e2e 0.52（已判定为 UniRec-0.1B **固定 960×1408 输入的模型天花板**）；② CJK/设计版面整页转写（G8d，"唯一在案解"原本要 Qwen2.5-VL 32B 级服务） |
| 最大的变化 | 把 2a 整页转写的模型档位从"**7B 起步 / 32B 才到生产线**"拉到 **0.8B / 1.7GB 权重**——原来"太贵所以只能规划"的能力，现在**部署成本上可行了** |
| 接入成本 | **极低**：它就是 OpenAI 兼容服务（vLLM/SGLang），本仓 [`docparse-vlm::VlmClient`](../../vendor/docparse/crates/docparse-vlm/src/lib.rs) 协议已建成并被 mock 单测锁定 → 新任务 ≈ 一个 prompt 模板 + 一个结果归一函数 |
| **一票否决风险** | **文本无坐标**。官方输出规范只给 visual region 归一化 bbox，正文/表/公式**不带 bbox**；而 `core::Chunk.bbox` 是 **非 Option 的必填字段**，`resolve_citation → {page,bbox}` 深链高亮是本项目差异化的根。**直接整页替换会让引用坐标变成编造的** |
| 建议 | **做，但按 spike 门控做，且只做"区域级"接法（保坐标），不做"整页替换"**。三道门：坐标可恢复性（一票否决）→ 质量（打记分牌短板集）→ 速度（官方**未公布任何速度数字**） |
| 明确不做 | 不进 fastsearch 检索热路径；**不能**当 embedder/reranker 用；**不能**拿它的视觉塔做 M1/M2（跨模态/ColPali）——它是生成式解析器，不是检索训练出来的表征模型 |

## 1. 它是什么（事实，来自 HF 仓库文件 + 技术报告）

| 项 | 事实 |
|---|---|
| 定位 | **端到端页级文档解析**：一张页图 → 自然阅读序的 Markdown（含文本/公式/表/图区） |
| 参数 / 权重 | **0.8B**；`model.safetensors` **1.71 GB**（BF16）；全仓 ~1.73 GB |
| 架构 | `architectures: ["Qwen3_5ForConditionalGeneration"]`, `model_type: qwen3_5`；text: hidden 1024 / 24 层 / vocab 248320；vision: patch 16 / spatial_merge 2 / hidden 768→out 1024 / `num_position_embeddings` 2304 |
| 训练 | Qwen3.5-0.8B 后训练：SFT（0.8B 2 epoch）→ RL 只在 4B 分支（GRPO，文本/公式/表多分量奖励）→ **OPD 蒸馏** 4B→0.8B（student top-k reverse KL，on-policy）→ 权重平均融合。数据引擎混合真实页（含 PaddleOCR-VL-1.5 / MinerU2.5-Pro 产出）与 HTML 合成页 |
| 分辨率 | **动态分辨率预算**，448×448 ~ 2880×2880；**16K 上下文**；不强制统一分辨率 |
| 输出规范 | Markdown 主体；表 = HTML `<table>`；公式 = LaTeX `$…$` / `$$…$$`；标题 = `#/##/###`；**图区 = `<img src="bbox_{left}_{top}_{right}_{bottom}.jpg" />`，坐标归一化到 `[0,1000)²`**；元素以双换行拼接 |
| 推理 | **vLLM 0.22.1** / SGLang，OpenAI 兼容端点；官方样例 `max_tokens=16384`, `temperature=0.0`，并**自带"截断-复读"清洗**（模型有该失效模式的自认） |
| 许可 | **Apache-2.0**（与本仓、与 docparse 同）——无许可边界问题 |

## 3. 与本仓现状的对照

### 3.1 现状（代码真源）

| 能力 | 现状实现 | 位置 |
|---|---|---|
| 扫描件 OCR | PP-OCR（tract 进程内 ONNX），fastsearch 侧 `parse-ocr` feature + `FASTSEARCH_OCR_MODELS` | [ingest.rs:48](../../crates/fastsearch-cli/src/ingest.rs#L48) |
| 表格结构 | **UniRec-0.1B**（非 VLM，进程内 ONNX），`parse-tables` + `FASTSEARCH_UNIREC_MODELS` | [ingest.rs:86](../../crates/fastsearch-cli/src/ingest.rs#L86) |
| 整页转写 | docparse `--transcribe-model`：版面模型出区域 → XY-cut 排序 → **UniRec 逐区域读** → 替换该页文本 chunk；**保留区域级 bbox**；有退化门 `MIN_CHAR_RATIO=0.5` | [transcribe.rs](../../vendor/docparse/crates/docparse-ocr/src/transcribe.rs) |
| VLM 接入 | `VlmClient`：`POST {url}/v1/chat/completions` + base64 PNG data-URL，已有 `--vlm-describe` / `--vlm-tables` 两个任务，协议被 mock 单测锁定 | [docparse-vlm/src/lib.rs](../../vendor/docparse/crates/docparse-vlm/src/lib.rs) |
| fastsearch 侧 VLM | **未接**：`parse-vlm` 在 [ingest.rs:28](../../crates/fastsearch-cli/src/ingest.rs#L28) 标注"下一迭代，需服务" | — |

### 3.2 OvisOCR2 vs UniRec-0.1B（本仓现役）

| 维度 | UniRec-0.1B（现役，进程内） | OvisOCR2-0.8B（候选，HTTP） |
|---|---|---|
| 运行形态 | tract 纯 Rust，**单二进制 + 模型文件，断网可用** | **需 vLLM/SGLang 服务 + GPU** |
| 权重 | encoder 157MB + decoder 529MB ONNX | 1.71GB BF16 safetensors |
| 输入分辨率 | **固定 960×1408** ← *已判定为学术难表 0.52 的天花板* | **动态 448²–2880²** ← 直接打这个天花板 |
| 粒度 | **逐区域**（版面模型先给几何） | **整页**（一次生成全页 Markdown） |
| 坐标 | ✅ **区域级 bbox 真实**（来自版面检测） | ❌ **正文无坐标**；仅图区带归一化 bbox |
| 确定性 | ✅ 贪心解码，进程内，可复现 | ⚠️ 服务侧；temperature=0 也受批处理/后端影响，**不保证逐字节可复现** |
| 表输出 | HTML（含 rowspan/colspan，实测正确） | HTML `<table>`，TEDS 94.76 |
| 公式 | ✅ LaTeX | ✅ LaTeX，CDM 97.53 |
| 已知短板 | 大/宽/密表 under-segment、超宽表 NO-PRED | **退化真实扫描件**（PureDocBench real 66.56 < Gemini-3.1-Pro 71.98）；截断复读 |

**关键洞察**：两者**不是替换关系，是互补关系**。UniRec 守"离线、确定性、有坐标"的身份底线；OvisOCR2 打"UniRec 结构性打不动的难页"。docparse 现有的"确定性核心 + opt-in 增强器"边界**天然容得下它**，不需要动架构。

## 4. 它能填哪些**已记录在案**的缺口

对照 [vlm-service-driven-capabilities.md](../../vendor/docparse/docs/refer/vlm-service-driven-capabilities.md) 的七处：

| # | 缺口 | 原计划模型档 | OvisOCR2 能否填 | 说明 |
|---|---|---|---|---|
| 2a | **整页转写（G8d）** | **Qwen2.5-VL 7B 起步 / 32B 才到生产线** | ✅ **正中，且档位降到 0.8B** | 这是本次调研**最大的发现**：该能力的部署成本从"必须上 32B 服务"降到"1.7GB 权重的小模型"，从"规划"变成"可落地" |
| 2c | 图表→表格 | VLM 服务 | 🟡 部分 | 它把 chart 当 visual region 输出 `<img bbox>`，**不反抽数据表**；仍需单独 prompt |
| 2d | 公式→LaTeX | VLM 服务（ONNX 路卡住） | ✅ | 原生能力，CDM 97.53 |
| 2e | 图内嵌表 recall | VLM 服务 | ✅ **结构性地填** | 它是整页端到端，**不依赖确定性检测器先检出表**——正是"漏检救不了"这条的解 |
| 1-a | 图片描述 `--vlm-describe` | 通用 VLM | ❌ **不适合** | 它输出 `<img bbox>` 占位，**不生成描述文字**；描述仍需通用 VLM |
| 2b | 页型判官 | 3–7B 视觉模型 | ❌ | 它不是分类器（同 UniRec 的结论） |
| 2f | MCP/REST 透传 | — | n/a | 确定性工作，与模型无关 |

**净收益**：一个模型同时闭合 **2a + 2d + 2e** 三处，其中 2a 是记分牌上聚合 NID 的主拖累（`skipped_1page` 0.231 / `skipped_2pages` 0.354 / `normal_4pages` 0.607 那批 CJK 设计版面）。

## 5. 三个硬冲突（必须先解，否则不要动手）

### 5.1 🔴 坐标丢失 — 一票否决项

- `core::Chunk.bbox` 是 **`BBox` 非 `Option`**（[model.rs:237](../../crates/fastsearch-core/src/model.rs#L237)），`Citation.page/bbox` 同样必填（[model.rs:319](../../crates/fastsearch-core/src/model.rs#L319)）。
- 本项目的答案层契约是 `resolve_citation(id) → {page,bbox} → 深链/高亮`（CLAUDE.md 架构大图），docparse 的卖点是"every chunk citable with page + bbox"。
- OvisOCR2 **正文不给坐标**。整页替换的结果是：要么坐标缺失（类型不允许），要么**合成一个页级/假 bbox 冒充真坐标**——这违反 docparse "近似必须标注、不静默"的约定，也让高亮功能实际失效但表面正常。

**三条可行出路**（按优先级）：

1. **区域级接法（推荐）**：沿用 `transcribe.rs` 已验证的形态——版面模型（PP-DocLayoutV2 已内嵌）先出区域几何 → 裁区域图 → **OvisOCR2 读单区域** → 每区域一个带**真实 bbox** 的 chunk。坐标问题消失，且把 OvisOCR2 当"更强的 UniRec"直接替换掉 `transcribe.rs` 里的模型调用，**改动面极小**。
2. **整页 + 文本对齐回填**：整页跑，再把输出文本与确定性解析的带坐标行做模糊对齐，回填 bbox。质量最好（保住整页阅读序），但对齐器是新代码、且扫描件本来就没有确定性行可对齐 → 只在数字页可用。
3. **整页 + 诚实降级**：坐标标为页级、`source: "vlm:ovisocr2"` + 降低 confidence + **文档明写"该路径不支持页内高亮"**。可接受，但要在 fastsearch 侧显式暴露给调用方，不能静默。

### 5.2 🟡 确定性

CLAUDE.md 不变量 #4：*同输入 + 同稳定索引 → 同结果*。严格读，这个不变量约束的是**检索/融合**（同分 `GlobalId` tie-break），摄取侧已有 PP-OCR/UniRec 等模型路径，并不逐字节确定。但 VLM **服务**又弱一档（批处理/后端版本会改变输出）。

**处置**：与现有增强器同规格——`source: "vlm:<model>"` 标注来源 + 降低 confidence + **保留退化门**（`transcribe.rs` 的 `MIN_CHAR_RATIO=0.5` 直接复用）+ 失败一律优雅降级回确定性结果，绝不让服务故障变成解析失败。摄取产物落 PG 真源后，检索侧的确定性不受影响。

### 5.3 🟡 现有 `VlmClient` 的两个参数会掐住它

代码里两个常量对"整页高分辨率解析"是错的：

- `MAX_IMAGE_SIDE = 1024`（[lib.rs:30](../../vendor/docparse/crates/docparse-vlm/src/lib.rs#L30)）——为"图区裁剪描述"定的。OvisOCR2 支持到 2880²，**1024 上限会直接把它的分辨率优势掐掉**，可能重演 UniRec 的固定分辨率天花板。
- `RENDER_SCALE = 2.0`（vlm）vs `3.0`（transcribe）——整页解析该用 3.0 档。
- 另：内置 PNG 编码器用 **stored（未压缩）deflate**，整页 3.0 倍渲染 ≈ 十几 MB 原始字节 → base64 后更大。整页路径需要真压缩，否则每页的网络开销不可接受。

三者都是小改动，但**必须随任务一起改**，否则 spike 会测出一个被自己参数拖累的假结论。

## 6. 建议方案与 spike 门控

### 6.1 落点（不动 fastsearch 架构）

```
新增 docparse-vlm 任务 `--vlm-parse`（复用 VlmClient 协议，零协议工作）
   ├─ 形态 1（推荐）：layout 区域 → 裁图 → OvisOCR2 → 带真 bbox 的 chunk   ← 替换 transcribe.rs 的模型后端
   └─ 形态 2（可选）：整页 → Markdown → 复用 docparse-md 解析器回 IR       ← 坐标降级，文档明说
                                     ↓
fastsearch-cli 新 feature `parse-vlm`（与 parse-ocr / parse-tables 同模式）
   env: FASTSEARCH_VLM_URL / FASTSEARCH_VLM_MODEL / FASTSEARCH_VLM_KEY
   → apply_vlm(doc) 挂在 apply_ocr / apply_tables 同一位置
```

**注意形态 2 的一个便宜处**：OvisOCR2 输出就是 Markdown，而本仓**已有 `docparse-md` 解析器**。整页 Markdown → docparse-md → IR → chunks（heading_path / section_id 免费获得）——归一化函数几乎不用写。这条路代码量最小，但坐标最弱，适合"扫描件优先、能检索比能高亮更重要"的场景。

### 6.2 三道门（照 UniRec spike 的老规矩，任一不过就停）

| 门 | 判据 | 不过则 |
|---|---|---|
| **门 1：坐标**（一票否决） | 形态 1 下每个 chunk 有真实区域 bbox；抽查 20 个 chunk 的 `resolve_citation` 落在正确区域 | 停，或降级到形态 2 并**在 fastsearch 侧显式标注不支持页内高亮** |
| **门 2：质量** | 打 docparse 记分牌**已记录的短板集**，不是打榜单：① 学术难表（2203/2305/redp5110，对照 e2e 0.52）；② CJK 设计版面（`skipped_1page` 0.231 / `normal_4pages` 0.607）；③ 中文扫描件（对照 PP-OCR）。**同口径自测**，不引用官方 v1.6 数字 | 停 |
| **门 3：速度/成本** | 官方零数字 → 必须实测。建议门槛：**≤5s/页**（对齐 UniRec spike 当年定的 ≤5s/表区域量级），并记录 VRAM 峰值与 tok/s | 停，或限定"仅难页路由"而非全量 |

**先决动作**（门 1 之前）：改掉 §5.3 的三个参数，否则测的不是模型。

### 6.3 工作量粗估

| 项 | 量 |
|---|---|
| `VlmClient` 参数/PNG 压缩修正 | 小（~50 行 + 单测） |
| `--vlm-parse` 任务（形态 1，改 transcribe 后端） | 中（~150–250 行，复用现有裁剪/退化门/排序） |
| `--vlm-parse` 任务（形态 2，md 回灌） | 小（~100 行，复用 docparse-md） |
| fastsearch `parse-vlm` feature + env 透传 | 小（~60 行，照抄 `apply_ocr` 形状） |
| spike 三门实测 | 1–2 天（含起 vLLM 服务） |

## 7. 明确**不适用**的方向（防止范围蔓延）

| 想法 | 判定 |
|---|---|
| 拿它做检索侧 embedder | ❌ 生成式解析器，非对比学习表征模型。fastsearch `Embedder` trait 吃 `&[String]`，它不产向量 |
| 拿它的视觉塔做 M1（跨模态单向量）/ M2（ColPali MaxSim） | ❌ 同上。ColPali 类需要检索训练；见 [MM8b 图像检索模型选型调研](2026-07-01-MM8b图像检索模型选型调研.md) |
| 拿它做 rerank | ❌ 不是相关性模型 |
| 内嵌进 tract（像 UniRec 那样） | ❌ Qwen3.5 全 VLM + 动态分辨率 + 16K KV-cache，远超 tract 现实边界；且 1.71GB 权重与"单二进制"身份冲突。**这条路不要试** |
| 用它替代 PP-OCR 做全量扫描件 OCR | ⚠️ 不建议。PP-OCR 是"进程内、断网可用、零服务"的差异化卖点（vlm-service-driven §3 明确划为"不需要服务"）。OvisOCR2 应当是**难页路由的增强档**，不是默认档 |
| 用它做 `--vlm-describe` 的图片描述 | ❌ 它输出 `<img bbox>` 占位而不描述。图描述仍需通用 VLM |

## 8. 一句话总结

**OvisOCR2 是"用 0.8B 的成本买到 32B 档整页转写质量"的机会**，正好落在 docparse 已经建成的 VLM 增强器插座上，能一次闭合三处在案缺口（整页转写 / 公式→LaTeX / 图内嵌表漏检），并直接攻击已判定为"UniRec 固定分辨率天花板"的学术难表短板。

**但它以放弃正文坐标为代价**，而页内可引用坐标是本项目（docparse + fastsearch 两侧）的差异化根基。因此正确的接法是**"区域级"而非"整页替换"**——让版面模型继续提供几何、让 OvisOCR2 只负责它擅长的"读"。这样接入几乎不动架构，且退化门/来源标注/优雅降级三件套全部现成可复用。

**下一步**：修正 §5.3 三个参数 → 起一个 vLLM 服务 → 跑门 1（坐标）与门 2（记分牌短板集）。任一不过就停，按 §6.2 记录负结论——这正是当年 UniRec spike 和 Phase 6 提分的做法。
