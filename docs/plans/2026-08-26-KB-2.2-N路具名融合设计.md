## 1. 要做什么

把"keyword ∥ vector 两路融合"泛化成**具名 N 路融合**：每一路带 `source` 标识与权重，
融合后每条命中能说清**自己是从哪几路来的、各自第几名、各自多少分**。

## 2. 为什么

1. **两路是结构性写死的，多信号落地后就不够用**。KB-2.1 让一个 chunk 同时持有
   `user_text` / `ocr` / `asr` / `vlm_caption` / `image_bytes` 多路信号；没有 N 路融合，
   这些信号**产出了也用不上**。
2. **图片 query 今天只有单路视觉**，模型不可用时没有 caption 兜底
   （FastGPT 的做法是原图向量与 caption 双路并行、任一路失败不取消其他路）。
3. **命中不可解释**。答案层拿不到"这条是靠关键词还是靠向量进来的"，
   调权重只能靠整体指标猜。

## 3. 先纠三处现状认知（读代码得到，与计划原稿不符）

### 3.1 `Normalized` 与 `Weighted` **数学上完全等价**——而且这是**已知的旧账**

`core::fusion::fuse` 里两个分支逐字同构：都是 `normalize(keyword)` + `normalize(semantic)`
再按一个标量做 `(1-x)` / `x` 加权，只有字段名不同（`semantic_ratio` vs `alpha`）。

**这不是本文的发现**：[2026-07-05 代码审查修复迭代计划](2026-07-05-代码审查修复迭代计划.md)
第 223 行已写明"与 `Normalized` 数学等价且零使用——删其一或使其真'不归一化加权'以区分"，
并在[迭代循环看板](2026-06-25-迭代循环.md)里标为**延后**。

⇒ **对 KB-2.2 的影响是好消息**：迭代计划原稿说"两个加权档才是难点"，
实际难点只有**一个**算法，另一个是可以顺手清掉的重复。**本项应当把这笔旧账一并结清**，
而不是把重复的形状原样搬进 N 路。

### 3.2 `req.explain` **只有声明、零使用**

`core::query::SearchRequest.explain` 在全仓除了字段声明与 `Default` 之外**没有任何引用**
（`grep -rn explain crates/ --include=*.rs` 只剩 `model.rs` 注释里一处无关词）。
也就是说：**API 收下 `explain:true` 然后什么都不做**。

这与本仓一路在修的是同一类事（宣称 hybrid 实为 keyword、空 tags 静默变 public）。
⇒ KB-2.2 正好填上它；**但填之前它是个已存在的静默失效面**，本文如实记在这里。

### 3.3 引擎侧的爆炸半径**很小**

`fuse(` 在 `fastsearch-engine` 里**只有一个调用点**（`Engine::run` 内）。
真正的破坏面在**契约与基线**，不在引擎逻辑：

| 面 | 现状 | 受影响程度 |
|---|---|---|
| `core::Fusion`（serde `tag="method"`） | 三变体 | **枚举形状要变** |
| `core::query::SearchRequest::validate` | 校验 `semantic_ratio`/`alpha` ∈ [0,1] | 跟着改 |
| TS SDK `types.ts` 的 `Fusion` 联合 | 三成员齐全 | **要同步** |
| Python SDK | `fusion` 传的是**不透明 dict** | **不受影响**（无类型面） |
| golden 基线 | `en_tech` / `zh_finance` / `multimodal` 各一份 baseline | 融合行为一变即需复核 |
| `fastsearch-mcp` | 允许清单里**没有** `fusion` | 不受影响 |

## 4. 设计

### 4.1 数据结构

```rust
/// 一路召回：带来源标识与权重的候选列表。
pub struct RecallList {
    /// 具名来源，如 "keyword:user_text" / "vector:image_caption" / "vector:image_bytes"。
    /// 形如 `<召回方式>:<信号>`，与 KB-2.1 的 `signal_type` 对齐。
    pub source: String,
    /// 该路权重（仅加权档用；RRF 档忽略）。
    pub weight: f64,
    pub items: Vec<Scored>,
}

/// 每条命中的来源明细（填进 `explain`）。
pub struct SourceHit {
    pub source: String,
    /// 该路内的名次，1 起。
    pub rank: usize,
    /// 该路的**原始分**（未归一化），便于诊断。
    pub score: f64,
    /// 该路对最终融合分的实际加数。
    pub contribution: f64,
}
```

### 4.2 `Fusion` 枚举的演进（**分两步，各自可独立收口**）

**第一步（本项主体）：RRF 先行，向后兼容零破坏。**

`Rrf` 天然 N 路化——现有实现就是 `for path in [keyword, semantic]` 的循环，
换成 `for path in lists` 即可，**序列化形状一个字节都不用动**。
⇒ 第一步可以在**不改任何契约**的前提下把 N 路能力做出来，golden 只需验"两路输入时逐位不变"。

**第二步（加权档）：合并 `Normalized`/`Weighted` 为一个具名权重档。**

```rust
/// 各路 min-max 归一化后按 `weights` 加权。未列出的来源用 `default_weight`。
Weights {
    #[serde(default)]
    weights: BTreeMap<String, f64>,   // BTreeMap：迭代序确定（不变量 #4）
    #[serde(default = "default_weight")]
    default_weight: f64,
}
```

**向后兼容方案（已实施裁定）**：

- 保留 `Normalized{semantic_ratio}` 与 `Weighted{alpha}` 为原枚举成员；新增 `Weights`，不删除、不改写
  旧反序列化结果。这比“反序列化时翻译”更严格地保存 Rust API 与 JSON 行为，弃用另立版本项处理。
- **不改** `method` 判别值，老请求逐字节仍可用。
- TS SDK 的联合类型**加**新成员，不删旧成员。
- 文档与 CHANGELOG 写明：两个旧档数学等价（旧账），新档是它们的具名超集。

### 4.3 确定性（不变量 #4，硬约束）

- 各路内部排名沿用 `rank_desc`：同分按 `GlobalId` 升序。
- **跨路累加顺序必须确定**：`RecallList` 按 `source` 字典序遍历，权重表用 `BTreeMap`。
  用 `HashMap` 迭代序累加浮点会让结果随机漂移——这是最容易在 N 路化时踩的坑
  （两路时只有两个加数，看不出来）。
- 融合后排序沿用 `sort_scored`。
- 验收：`deterministic_under_shuffle` 扩展到 N 路，且**打乱 `RecallList` 的顺序**结果不变。

### 4.4 `explain` 的填充

`req.explain=true` 时，每条命中带 `sources: [SourceHit]`（按 `source` 字典序）。
`explain=false`（默认）时**响应形状逐字节不变**——同 KB-0.4 的预算档，不给既有调用方多出字段。

`SearchHit` 现有的 `bm25`/`vector`/`rerank` 三个分数字段**保留不动**：
它们是两路时代的便利字段，删了会破坏 SDK。新字段是超集。

### 4.5 权重从哪来

**只能由版本化评测选出**，不得把 FastGPT 的 0.3/0.7、1/0.7 设为默认
（[参考建议 §5.3-2](2026-08-24-fastgpt知识库与多模态检索参考建议.md)）。
默认值：所有来源等权（`default_weight = 1.0`），RRF 仍为 `Fusion::default()`。
调权重必须过 `assert_no_regression` 门禁。

## 5. 不做什么

- **不做学习式融合 / LTR**（KB-3 之后，需标注集）。
- **不改 `bm25`/`vector`/`rerank` 现有字段**。
- **不在本项引入新召回路**：本项只提供"能融 N 路"的能力；
  真正产出 caption / 视觉信号是 KB-2.1 + KB-1.3 的事。
  ⇒ **本项落地后，实际仍只有两路在跑**——这一点必须在状态里如实写，
  不能因为"支持 N 路"就宣称"多路召回已上线"。
- 不动 MCP 面（其允许清单里没有 `fusion`，要开是 KB-0.x 的独立决定）。

## 6. 用户使用例子

```jsonc
// 第一步之后：RRF 融 N 路（对调用方透明，请求体不变）
{"query":"毛利率","fusion":{"method":"rrf","rank_constant":60}}

// 第二步之后：具名权重 + explain
{"query":"毛利率","explain":true,
 "fusion":{"method":"weights","weights":{"vector:user_text":1.0,"vector:image_caption":0.4}}}
// → hits[0].sources = [
//     {"source":"keyword:user_text","rank":3,"score":8.6,"contribution":0.016},
//     {"source":"vector:user_text","rank":1,"score":0.83,"contribution":0.4}]

// 老请求继续原样可用（本轮不改写、不标 deprecated）
{"query":"毛利率","fusion":{"method":"normalized","semantic_ratio":0.7}}
```

## 7. 测试用例（验收标准）

1. **两路等价性**：任意输入下，N 路实现喂两路 == 现有 `fuse` 的输出**逐位相同**（防回归的锚）。
2. **确定性**：打乱各路内部顺序 **且** 打乱 `RecallList` 顺序，结果不变。
3. **单路退化**：只给一路时等于该路自身排序（现有 `one_path_empty_degrades` 的 N 路版）。
4. **权重生效**：同一候选集，改某路权重能改变名次，且改动方向符合预期。
5. **向后兼容**：`{"method":"normalized","semantic_ratio":0.7}` 与
   `{"method":"weighted","alpha":0.7}` 均继续反序列化并保持原公开枚举形状；新 `weights` 为加法成员。
6. **explain 开关**：`explain=false` 响应逐字节不变；`explain=true` 时 `sources` 覆盖所有命中路。
7. **golden**：三份 baseline 全绿；若有偏移，必须逐条解释而不是刷新基线。
8. 收口：fmt + clippy `-D warnings` + `cargo test --workspace` + TS SDK 测试。

## 9. 决策与剩余项

1. `[已决策，FS-002]` 旧档原样保留，新 `Weights` 加法兼容；本轮不做 deprecated，避免 Rust API 破坏。
2. `[已决策，FS-002]` `source` 采用 `<召回方式>:<信号>`；模型身份不放入权重键，FS-202 以独立 provenance 字段返回。
3. `[待 FS-202]` 若同一信号存在多个模型，在独立 provenance 字段中确定 model/version 的具体形状；
   当前裁定是不扩权重键，避免模型升级使调用方权重配置失效。
4. `[已决策，FS-002]` 权重表用 `BTreeMap<String, f64>`，不支持通配；
   通配便于表达"所有向量路"，但引入匹配优先级规则，复杂度上一个台阶。
