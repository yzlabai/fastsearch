## 1. 结论

FastGPT 对 FastSearch 的参考价值是**高，但主要集中在知识库产品层和多路检索编排层，不在底层存储与权限内核**。

- `[当前已实现]` 在配置 PG 的生产架构中，FastSearch 已有 FastGPT 不具备或不如其明确的底座：PostgreSQL/pgvector 真源、可重建派生索引、`GlobalId` 确定性排序、服务端强制 ACL、页/框/时间/媒资引用以及受控媒资解析。PG 表已覆盖 chunk、metadata、media、inline 字节、图片向量状态、tenant/ACL 与 embedding（`FastSearch: crates/fastsearch-pg/src/sql.rs:L34-L68`）；融合以 `GlobalId` 同分排序保证确定性（`FastSearch: crates/fastsearch-core/src/fusion.rs:L57-L105`）。无 `DATABASE_URL` 的 local-only 路径并不满足同等真源与恢复保证，见 4.1、4.7。
- `[当前已实现]` FastSearch 也不再只是“图片接口占位”：REST 已接收图片 query，HTTP embedder 能按三种 JSON 形态发送图片，写入端能优先使用图片字节、失败时退化到图片文本，独立图片可直接上传并进入索引（`FastSearch: crates/fastsearch-server/src/lib.rs:L1261-L1357`、`FastSearch: crates/fastsearch-embed/src/http.rs:L210-L230`、`FastSearch: crates/fastsearch-server/src/lib.rs:L2342-L2458`、`FastSearch: crates/fastsearch-server/src/lib.rs:L1939-L2075`）。
- `[待验证]` 仓内没有真实跨模态模型的质量验收证据；现有计划也明确把真实外部 S3/MinIO 与真实跨模态模型验收列为待运行验证（`FastSearch: docs/plans/2026-07-01-图片全模态检索实现方案.md:L1-L5`）。因此不能把“协议已接线”写成“生产级文搜图/图搜图已经完成”。
- `[建议]` 最值得借鉴 FastGPT 的是：图片 query 同时走 VLM caption 与原图向量、多个来源独立召回后加权 RRF、单图失败降级、异步训练任务状态、最终引用再鉴权/再签 URL。FastGPT 的相应链路在源码中是明确的（`FastGPT: packages/service/core/dataset/search/defaultRecall/index.ts:L61-L158`、`FastGPT: packages/service/core/dataset/search/defaultRecall/imageCaption.ts:L28-L128`、`FastGPT: packages/service/core/dataset/training/schema.ts:L41-L102`、`FastGPT: projects/app/src/pages/api/core/chat/record/getQuote.ts:L19-L69`）。
- `[建议]` 不应照搬 FastGPT 的 Mongo chunk + 外部向量库双存储、固定图片权重、可关闭最终成员鉴权的工作流开关，以及开源仓库中不可见的 Plus 任务消费者。这些做法与 FastSearch 的 PG 真源、确定性和不可绕过 ACL 不变量冲突。

一句话路线：**先补齐现有图片链路的正确性缺口，再引入 FastGPT 的 VLM caption 与 N 路融合；产品级来源、任务和资源权限放在独立控制面，绝不污染 FastSearch 的检索内核。**

## 2. 证据口径与项目边界

本文引用采用以下前缀：

- `FastSearch:` 后为相对 FastSearch 仓库根目录的路径与精确行号。
- `FastGPT:` 后为相对 FastGPT 仓库根目录的路径与精确行号。

FastSearch 自身要求“代码现状永远是真源”（`FastSearch: CLAUDE.md:L5-L6`），并明确三条不可破坏的边界：PG 是真源、ACL 由服务端身份强制注入、未经过真机验证的外部能力必须诚实标记（`FastSearch: AI_AGENT_DEV_SPEC.md:L29-L37`）。本评估据此将“结构已实现”“仓内测试覆盖”“真实外部环境已验收”分开陈述。

此外，FastSearch 当前定位仍是通用检索引擎：通用 chunk 管理计划明确把解析、领域层级和调用方语义排除在引擎职责之外（`FastSearch: docs/plans/2026-07-23-generic-chunk-management-api.md:L5-L17`、`FastSearch: docs/plans/2026-07-23-generic-chunk-management-api.md:L31-L38`）。因此，FastGPT 的 Dataset/Collection/Training 产品模型只能作为**可选控制面**参考，不能默认塞进 core/engine。

## 4. FastSearch 当前实现的关键事实与缺口

### 4.1 数据模型：检索内核扎实，知识库控制面很薄

`[当前已实现]` `Chunk` 已把可检索文本、精确坐标、媒资引用、inline 字节、图片向量状态、tenant/ACL、metadata 和 searchable 放在同一稳定单元上（`FastSearch: crates/fastsearch-core/src/model.rs:L239-L274`）。PG 以 `(collection, doc_id, chunk_id)` 为主键，并在真源更新时清空旧 embedding，避免正文与向量错配（`FastSearch: crates/fastsearch-pg/src/sql.rs:L345-L362`）。

`[当前边界]` PG 并不是所有运行模式下都强制存在：只有配置 `DATABASE_URL` 才安装 source store；未配置时普通 searchable chunk 仍会直接写本地派生索引，只有 `searchable=false` 被明确拒绝（`FastSearch: crates/fastsearch-server/src/main.rs:L172-L190`、`FastSearch: crates/fastsearch-server/src/lib.rs:L2240-L2246`、`FastSearch: crates/fastsearch-server/src/lib.rs:L2461-L2497`）。因此“PG 是真源、派生索引可重建”目前是生产架构意图和有 PG 配置时的事实，不是无条件运行时保证；无 PG 模式只能诚实定义为 local-only/ephemeral。

`[当前已实现]` collection 配置却只是进程内、咨询性 registry，不是真源且不跨副本共享（`FastSearch: crates/fastsearch-server/src/lib.rs:L379-L401`）；创建 collection 只向这个 HashMap 写入（`FastSearch: crates/fastsearch-server/src/lib.rs:L2994-L3038`）。这与 FastGPT 的 Dataset/Collection 产品模型不是同一层级。

`[建议]` 若要承载完整知识库产品，应新增独立的 PG 控制面实体（例如 source/collection、ingest_job、artifact/model_profile），而不是扩张 `Chunk` 或让内存 registry 变成第二真源。FastGPT 的 Dataset 保存模型/分块/权限继承设置、Data 挂多个索引身份，说明这些是长期资源状态而非搜索请求参数（`FastGPT: packages/service/core/dataset/schema.ts:L98-L131`、`FastGPT: packages/service/core/dataset/data/schema.ts:L53-L76`）。

### 4.2 摄取：格式覆盖不等于图片字节闭环

`[当前已实现]` parser 能产图片 chunk。图片检索文本在已有 VLM caption 时优先使用它，否则绑定相邻图注和上下文（`FastSearch: vendor/docparse/crates/docparse-core/src/chunk.rs:L365-L393`）。PDF interpreter 在启用图片解码且图片合格时能持有原始 `data`，但 `PdfParser.decode_images` 为节省内存默认关闭（`FastSearch: vendor/docparse/crates/docparse-pdf/src/lib.rs:L30-L35`、`FastSearch: vendor/docparse/crates/docparse-pdf/src/interpreter.rs:L448-L460`）。

`[当前缺口]` 默认 FastSearch CLI 路径只调用 `parse → chunk_document → from_docparse_chunk`，没有执行 docparse CLI 的 image-export/image-embed 步骤（`FastSearch: crates/fastsearch-cli/src/ingest.rs:L208-L238`）。而 docparse chunk 只复制 `ImageChunk.data_base64`，不复制其原始 `data`（`FastSearch: vendor/docparse/crates/docparse-core/src/chunk.rs:L386-L392`）；FastSearch adapter 也只从 `data_base64` 解码 `media_bytes`（`FastSearch: crates/fastsearch-cli/src/ingest.rs:L272-L328`）。PDF 和独立图片 parser 默认都把 `data_base64` 留空（`FastSearch: vendor/docparse/crates/docparse-pdf/src/interpreter.rs:L448-L460`、`FastSearch: vendor/docparse/crates/docparse-img/src/lib.rs:L67-L89`）。因此，文档/本地图片经 `fastsearch ingest` 时通常只有 `DocRegion` 与 caption/OCR 文本，不能据此宣称图片字节已进入视觉向量链路。

`[当前缺口]` FastSearch 自身也没有接入自然图片 VLM caption：当前 CLI 的 VLM 路径只做 PDF 表格区域识别和可选区域级转写，adapter 只能消费 docparse 上游已经填入的图片 caption（`FastSearch: crates/fastsearch-cli/src/ingest.rs:L26-L30`、`FastSearch: crates/fastsearch-cli/src/ingest.rs:L112-L123`、`FastSearch: vendor/docparse/crates/docparse-core/src/chunk.rs:L365-L393`）。所以扫描页 OCR、图表附近文本或上游预填 caption 可以成为文本信号，但不能等价为已实现通用自然图理解。

`[建议]` 这是 P0：在解析边界显式产出 `asset artifact`，把原始图片字节上传对象存储或作为受限 inline 字节随 chunk 一起送入 `/v1/index`；每个图片 artifact 记录来源页、bbox、MIME、hash、解析器/增强器版本。不要把 base64 永久塞进文本或 metadata。

### 4.3 多模态嵌入：协议已实现，能力探测与真模型验收不足

`[当前已实现]` `EmbedInput::{Text,Image}` 与 `EmbedCaps{image,cross_modal,semantic}` 已是加法式接口（`FastSearch: crates/fastsearch-embed/src/lib.rs:L36-L107`）；HTTP 后端支持 data URL、base64 object 和 OpenAI content 三种图片形态（`FastSearch: crates/fastsearch-embed/src/http.rs:L33-L72`、`FastSearch: crates/fastsearch-embed/src/http.rs:L210-L230`）。

`[待验证]` `caps()` 直接信任环境配置，并未在启动时证明外部模型真的接受图片、返回同维且文图同空间（`FastSearch: crates/fastsearch-embed/src/http.rs:L95-L146`、`FastSearch: crates/fastsearch-embed/src/http.rs:L300-L346`）。现有 live test 只在设置 URL 时验证文本嵌入（`FastSearch: crates/fastsearch-embed/src/http.rs:L535-L541`）。

`[建议]` 启动时加入可缓存的 capability probe：固定文本+小图分别请求，验证数量、维度、有限值和重复稳定性；`cross_modal` 仍需配置声明，但必须再由小型真实 golden 验收。失败时要明确选择“启动失败”或“降级 text-only”，并把实际 caps 暴露到 introspection/metrics，不能静默相信开关。

### 4.4 召回、融合与重排：二路内核可靠，图片编排仍单路

`[当前已实现]` 搜索请求只有一个 query、一个 vector 和一个 `query_image`（`FastSearch: crates/fastsearch-core/src/query.rs:L43-L93`）；引擎最多产生 keyword 与 semantic 两路，再交二路 `fuse`（`FastSearch: crates/fastsearch-engine/src/lib.rs:L1561-L1616`、`FastSearch: crates/fastsearch-engine/src/lib.rs:L1664-L1707`）。这比 FastGPT 的文本、caption、原图向量分源召回简单，但也缺少图片模型不可用时的 caption fallback。

`[已修复 2026-08-24]` image-only query 如果客户端仍要求 rerank，词项 reranker 会在空 query 下给所有候选 0 分（`FastSearch: crates/fastsearch-rerank/src/lib.rs:L76-L94`），引擎随后按 `GlobalId` 重排，可能破坏原视觉向量顺序（`FastSearch: crates/fastsearch-engine/src/lib.rs:L1716-L1748`）。

> **复核确认：不是"可能"，是必然，且已复现**。构造"向量序 ≠ gid 序"的三条候选后，
> 带 rerank 的结果从视觉序 `[3,1,2]` 塌成 gid 序 `[1,2,3]`。根因比原文更本质：`Reranker` trait
> 的签名是 `rerank(&str, &[String])`，**结构上只能吃文本**——所以这不是某个 reranker 的实现缺陷，
> 是编排层该拦的。修复：`run()` 在 `req.query` 去空白为空时**整段跳过** rerank（含 `rerank.top_k`
> 重排窗口——那是喂给重排器的成本钮，重排器没被调用就不该用它裁结果），保持融合/视觉序、
> `hit.rerank` 留 `None` 让调用方看得见没重排；不报错（以图搜图顺带带 rerank 是常见用法）。
> 见 [plan](2026-08-24-image-only-query跳过词项rerank.md)、[14-engine spec v2.9](../specs/14-engine.md)。
> **未根治**：query 非空但被分词器切空（纯标点、分词器不认的语种）时仍会退化 gid 序，见该 spec 已知限制。FastGPT 明确只对文本侧 rerank，视觉侧保留给 RRF（`FastGPT: packages/service/core/dataset/search/defaultRecall/index.ts:L120-L146`）。

`[建议]` 先修正确性：纯图片 query + 文本 reranker 必须跳过重排并保持原序；以后若有多模态 reranker，再按 capability 显式开启。然后将融合接口泛化为 `Vec<RecallList{source,weight,items}>`，保留当前 RRF/归一化/确定性逻辑，并在 hit/explain 中记录命中来源。FastGPT 固定的 caption/image 0.3/0.7 与图文 1/0.7 只能作为实验初值，不能成为 FastSearch 默认值（`FastGPT: packages/service/core/dataset/search/defaultRecall/index.ts:L134-L158`）。

### 4.5 权限：数据面原则正确，资源面与生产默认需补强

`[当前已实现]` FastSearch 从 API key 映射出 tenant/tags，搜索 handler 强制构造 ACL 后调用 engine，客户端不能传入更宽权限（`FastSearch: crates/fastsearch-server/src/lib.rs:L556-L596`、`FastSearch: crates/fastsearch-server/src/lib.rs:L1360-L1408`）。PG vector 查询同时做 SQL 下推和 Rust 精确复核（`FastSearch: crates/fastsearch-pg/src/lib.rs:L504-L570`）。写入也会用 Principal 覆盖请求体中的 doc_id、tenant、ACL（`FastSearch: crates/fastsearch-server/src/lib.rs:L2120-L2127`）。

`[当前边界]` API keys 来源是环境变量；未配置时会自动创建无 tenant 限制的 `dev` key（`FastSearch: crates/fastsearch-server/src/main.rs:L75-L87`）。这适合本地开发，不是生产身份控制面。

`[当前边界]` 写入 ACL 虽然不信任请求体，但当 Principal 没有 tags 时会自动写成 `public`（`FastSearch: crates/fastsearch-server/src/lib.rs:L2112-L2127`）。这让“身份映射缺少 tags”从配置遗漏变成公开数据，生产默认并非 fail-closed。

> **2026-08-24 复核修正（原文严重性夸大）**：**tenant 维度的隔离仍然成立**——`AclFilter::visible`
> 先判 tenant（调用者有 tenant 而行无 → 不可见；tenant 不等 → 不可见），再判标签
> （`crates/fastsearch-core/src/filter.rs` 的 `visible`）。所以**有 tenant 的 key 写出的 `public` 行
> 不会跨租户泄露**。真实失效面是两条：①**租户内**对所有 key 可见（本该按 tags 收窄）；
> ②对**无 tenant 的管理/dev key** 全部可见（`tenant: None` 直接放行 tenant 维度）。
> 这仍是该修的 fail-open 默认，但不是跨租户数据泄露——按后者定级会挤占真正的 P0。

`[建议]` 可以在 FastSearch 之上借鉴 FastGPT 的 owner/read/write/manage 和父级继承，用于“谁能管理知识库/来源/任务”；实际检索仍将解析后的 tenant/tags 服务端注入。绝不能照搬 FastGPT 工作流的 `authTmbId=false` 分支——该分支会直接采用应用配置的 dataset IDs（`FastGPT: packages/service/core/workflow/dispatch/dataset/search.ts:L117-L127`），与 FastSearch 的不可绕过数据面原则冲突。生产模式还应在未配置真实 keys/identity adapter 时拒绝启动；空 tags 应拒绝写入或落入显式 private/default ACL，只有调用方明确声明 public 才公开，而不是回退管理员 dev key 或隐式 public。

### 4.6 引用：FastSearch 已有好底座，应补答案层生命周期

`[当前已实现]` FastSearch 的 `citation_id` 是稳定 `collection:doc_id:chunk_id`，Citation 同时带 page/bbox/time/media（`FastSearch: crates/fastsearch-core/src/model.rs:L329-L395`）。媒资解析会重新检查 ACL；Object 无签名器时返回不存在而不是泄露裸 URI（`FastSearch: crates/fastsearch-engine/src/lib.rs:L1441-L1492`）。搜索响应也只在签名器与公网 base 都存在时附加短时 URL，内部对象 URI会被脱敏（`FastSearch: crates/fastsearch-server/src/lib.rs:L1183-L1245`）。

`[建议]` 借鉴 FastGPT 的“聊天记录只持引用身份，展开时重新鉴权、重新取数据和重新签 URL”语义（`FastGPT: projects/app/src/pages/api/core/chat/record/getQuote.ts:L30-L69`）。该能力属于答案层/会话层：FastSearch 保持 `resolve_citation(s)`，上层保存 citation_id、命中时的模型/索引版本和必要的 quote snapshot；回看永远重新 resolve，不保存长期可访问 URL。

### 4.7 运维：可重建性强，摄取作业与部分写路径仍有风险

`[当前已实现]` CDC 采用轮询式 logical decoding；生产安全路径是 peek、派生索引落盘后再 advance slot，流式 `START_REPLICATION` 只是可选后续（`FastSearch: crates/fastsearch-sync/src/replication.rs:L1-L11`、`FastSearch: crates/fastsearch-sync/src/replication.rs:L79-L118`）。索引还提供 snapshot bootstrap 和从真源重建（`FastSearch: crates/fastsearch-engine/src/lib.rs:L1041-L1075`）。

`[已修复 2026-08-24]` **原文此处有一处事实错误**：原文称"只有 CDC `apply_upsert` 路径会调用
`set_embedding` 写回 PG"。实际是**三条写路径里两条早有写穿、唯独 `/v1/index` 缺席**：

| 写路径 | PG 真源 | PG `embedding` 写穿 |
|---|---|---|
| `/v1/chunks`（`batch_upsert_chunks`） | `upsert_chunks` | ✅ 早已存在（`fastsearch-server/src/lib.rs` 的 `has_pg_vector()` 分支） |
| `/v1/index`（`index`） | `upsert_doc` | ❌ **缺席**（本次修复） |
| CDC `apply_upsert` | —（回放） | ✅ 早已存在（`fastsearch-engine/src/lib.rs`） |

问题实质因此不是"缺一套统一的 persist-source + apply-derived 服务"，而是**同一份写穿逻辑漏了一条路径**——
修复成本远低于原文的判断。后果则比原文更尖锐：`PgStore::upsert_doc` 是 doc 级 **delete + insert**
（`fastsearch-pg/src/lib.rs`），新行 `embedding` 必为 `NULL`，所以对同一 doc 重复 `/v1/index`
会**把已可检索的向量清成 NULL**，而不只是"新向量暂不可见"。

修复即照搬 `/v1/chunks` 的既有写穿块（不新造抽象），+1 env-gated 集成测试（去掉写穿即红：直查 0 命中）。
见 [plan](2026-08-24-index写穿pgvector对齐chunks.md)、[19-server spec v2.3](../specs/19-server.md)。
**仍未解决**：真源与 embedding 不在同一事务（`/v1/chunks` 同此），见该 spec 的"已知限制"。

`[当前缺口]` local-only 直写也不能等价为完整持久化：`/v1/index` 末尾调用的 `Engine::commit()` 只提交文本索引，向量快照仅在 `persist(data_dir, lsn)` 中落盘（`FastSearch: crates/fastsearch-engine/src/lib.rs:L1417-L1419`、`FastSearch: crates/fastsearch-engine/src/lib.rs:L1024-L1038`）。进程重启后若没有 PG 真源与 bootstrap/CDC，文本和向量的可恢复语义并不对称。

`[建议]` 这是 P0：统一 `/v1/index` 与 CDC 的向量落地语义。pgvector 直查档必须在 PG chunk 事务成功后写 embedding，或统一复用一个可幂等的“persist source + apply derived”服务；响应需明确区分 `source_committed`、`embedding_ready`、`derived_index_visible`。FastGPT 的 training lease/retry/error 字段可作为作业状态参考，但状态应在 FastSearch 的 PG 控制面而非 Mongo 队列实现（`FastGPT: packages/service/core/dataset/training/schema.ts:L47-L102`）。

## 5. 可直接借鉴、需适配、不应照搬

### 5.1 可直接借鉴的行为原则

1. `[建议]` **图片 query 双路召回**：原图向量与 VLM caption 并行，任一路失败不取消其他路。FastGPT 已按单图捕获 caption 异常并返回空描述（`FastGPT: packages/service/core/dataset/search/defaultRecall/imageCaption.ts:L54-L128`）。
2. `[建议]` **先按来源融合，再跨模态融合**：文本 embedding/full-text、caption embedding/full-text、原图向量分别保留来源，最后 N 路 RRF（`FastGPT: packages/service/core/dataset/search/defaultRecall/index.ts:L86-L158`）。
3. `[建议]` **视觉结果不交给纯文本 reranker**；重排失败保持原召回序（`FastGPT: packages/service/core/dataset/search/defaultRecall/rerank.ts:L52-L109`）。
4. `[建议]` **对象标识晚绑定 URL**：检索和去重期间保留稳定对象/citation ID，最终输出或引用回看时才鉴权签发。FastSearch 已有安全 resolve；FastGPT 的引用回看进一步证明会话层也应重复鉴权（`FastGPT: projects/app/src/pages/api/core/chat/record/getQuote.ts:L30-L69`）。
5. `[建议]` **异步作业具备 lease/retry/error/TTL**，并把模型与解析版本写入 artifact provenance（FastGPT 当前训练状态字段见 `FastGPT: packages/service/core/dataset/training/schema.ts:L47-L102`）。

### 5.2 必须适配后再采用

1. `[建议]` **Dataset/Collection/Data/Training 层级**：只在 FastSearch 要内建知识库产品时采用；以 PG 控制面表实现，并保持 chunk/embedding 真源一致。当前 FastSearch collection registry 非持久真源（`FastSearch: crates/fastsearch-server/src/lib.rs:L379-L401`）。
2. `[建议]` **一个 chunk 多个索引身份**：不要复制 Mongo `indexes[].dataId`；可在 PG 建 `chunk_artifact/chunk_signal` 子表，键包含 GlobalId、signal type、model/version、status、vector reference，用于 caption、视觉、OCR/ASR 等多信号审计。FastGPT 的多索引数组说明了需求（`FastGPT: packages/service/core/dataset/data/schema.ts:L53-L76`），FastSearch 当前单 embedding 列说明需要做架构选择（`FastSearch: crates/fastsearch-pg/src/sql.rs:L53-L63`）。

   > **2026-08-24 复核补充（原稿未谈的约束）**：该子表会撞上两条既有不变量，立 spec 时必须先答：
   > ① `upsert_chunk_sql` 的 `ON CONFLICT ... embedding = NULL`（以及 `upsert_doc` 的 delete+insert）
   > 是**有意的"正文变了就作废旧向量"防错配设计**——多信号后"正文变了该作废哪些信号"必须重新定义
   > （OCR 信号随正文废，视觉信号未必）。② 新表进不进 publication 直接决定会不会引入 CDC 反馈环
   > （现有 DDL 靠**列清单 publication 排除派生列**来断环）。两条都属"托管 PG 可移植 + PG 真源"
   > 的核心约束，不能在实施时顺手决定。
3. `[建议]` **层级权限**：资源管理权限可采用角色与继承；检索时必须编译为服务端 Principal/ACL，且 SQL 与精确后过滤都不可取消。FastGPT 的父级+自身权限合并见 `FastGPT: packages/service/support/permission/dataset/auth.ts:L66-L90`。
4. `[建议]` **异步摄取队列**：放入单独 ingest worker/control-plane，继续让搜索热路径零 docparse/ONNX；FastSearch 当前 feature 已清楚隔离重解析依赖（`FastSearch: crates/fastsearch-cli/Cargo.toml:L29-L77`）。
5. `[建议]` **token 预算**：这是答案层约束，不应塞进通用 engine top-k；FastGPT 会按累计 token 裁剪引用（`FastGPT: packages/service/core/dataset/search/defaultRecall/utils.ts:L34-L78`），FastSearch 可让上层基于 `include_text` 结果执行。

### 5.3 不应照搬

1. `[建议]` 不复制 Mongo chunk + 外部向量库的双写连接模型；FastSearch 已用 PG 主键、embedding 与 CDC 形成更强一致性边界（`FastSearch: crates/fastsearch-pg/src/sql.rs:L40-L68`）。
2. `[建议]` 不固化 FastGPT 的 0.3/0.7、1/0.7 权重；FastSearch 已有评测框架，权重应经数据集选择并进入回归门禁（`FastSearch: docs/specs/18-eval.md:L8-L15`、`FastSearch: crates/fastsearch-engine/tests/relevance_gate.rs:L61-L70`）。
3. `[建议]` 不允许任何“跳过最终用户权限”的工作流开关进入 FastSearch server/MCP/SDK 数据面（FastGPT 分支证据：`FastGPT: packages/service/core/workflow/dispatch/dataset/search.ts:L117-L127`）。
4. `[建议]` 不依赖闭源/外部消费者完成核心状态迁移。FastSearch 每个任务模式必须在同仓可见 worker 或显式 external executor contract 中闭环，并有超时、幂等与死信状态。
5. `[建议]` 不把 HashEmbedder、caption-only 或小型 keyword golden 宣称为真实视觉质量。现有多模态门禁仅验证 caption/转录文本的 keyword 召回（`FastSearch: crates/fastsearch-engine/tests/relevance_gate.rs:L61-L70`）。

   > CLI/SDK、以及全部 golden baseline。按 dev spec §0 属"影响检索结果或数据契约"，
   > **必须单独立 spec + 给向后兼容方案**，不能作为 P1 的一个 bullet 顺手做掉。
   > （RRF 一路是天然可 N 路化的，可作为第一步；两个加权档才是难点。）
4. `[建议]` 增加真实图片 golden：同图、近似图、语义相似但视觉不同、caption 错误、OCR 图表、跨语言文本搜图；分别报告各路和融合后的 recall/nDCG，不只测最终总分。
5. `[建议]` 引用响应加入不可变 provenance：parse profile、caption/VLM model、embedding model/version、artifact hash；URL 仍只在最终 resolve 时生成。

依据：FastGPT 已把五类召回结果分开并在后段融合（`FastGPT: packages/service/core/dataset/search/defaultRecall/index.ts:L86-L158`）；FastSearch 已有确定性融合与 score 明细，适合增量扩展而非重写（`FastSearch: crates/fastsearch-core/src/fusion.rs:L57-L94`、`FastSearch: crates/fastsearch-engine/src/lib.rs:L1618-L1707`）。

### P2：用 PG job/worker 补可恢复摄取与可选控制面

1. `[建议]` 先建 PG `ingest_job / ingest_artifact`：输入 URI/hash、解析 profile、job lease、heartbeat、retry/error、阶段进度、chunk 版本和幂等键都可审计；worker 崩溃后可续租/重放，不靠内存队列。可参考 FastGPT 的 lease/retry/error 字段行为，但不复制其 Mongo schema（`FastGPT: packages/service/core/dataset/training/schema.ts:L47-L102`）。
2. `[建议]` 提供 raw-document ingest API 或显式 external executor contract，由独立 worker 完成 docparse/OCR/VLM/embedding，再以可幂等 chunk/artifact 协议提交；搜索 server 保持零 ONNX/docparse，符合当前 feature 隔离（`FastSearch: crates/fastsearch-cli/Cargo.toml:L29-L77`）。
3. `[建议]` 如果 FastSearch 要直接面向知识库用户，再建立 PG `knowledge_source / collection / model_profile` 控制面：来源 URI、ETag/hash、解析策略、版本与回滚可审计；若仍定位通用 engine，则由上层产品持有，FastSearch 只保留协议和任务状态。
4. `[建议]` 将当前内存 collection registry 持久化或明确降级为纯 introspection cache；模型 profile 和维度不能只跨单进程存在（`FastSearch: crates/fastsearch-server/src/lib.rs:L379-L401`）。
5. `[建议]` 在控制面提供 owner/read/write/manage、成员/组/组织与父级继承，编译到不可放宽的 tenant/tags ACL；为答案层提供批量 `resolve_citations`，每次回看重验身份并重新签短 URL。
6. `[建议]` 摄取 worker 与搜索 server 独立部署/限流，OCR/VLM/embedding 各有队列、超时、批量、积压和成本指标；作业状态、object/PG/derived 写入均暴露可恢复边界。

### P3：有真实需求和数据后再做

1. `[建议]` 音频/视频：上游 worker 做 ASR、说话人/时间段、抽帧与 caption，FastSearch 消费带 `TimeSpan` 的 chunk。当前只有 schema 和转录文本 golden，不能宣称媒体内容摄取已实现（`FastSearch: crates/fastsearch-core/src/model.rs:L30-L94`、`FastSearch: crates/fastsearch-engine/tests/golden/multimodal.json:L9-L17`）。
2. `[建议]` ColPali/多向量 MaxSim：只有单向量真实 golden 达到瓶颈且规模验证后再引入；继续守住 PG 只依赖 pgvector，复杂多向量索引只能是可重建派生层。
3. `[建议]` 学习融合/LTR：在 N 路 source attribution 和足够标注集具备后训练；仍保留确定性导出、版本化和回归阈值。

## 7. 建议验收场景

1. **含图 DOCX/PDF**：解析得到正文、图片字节、page/bbox；对象/PG 真源可读；caption 与视觉向量至少各一路可关闭；文本 query 和图片 query 都能命中；引用 resolve 后可显示原图。
2. **独立图片**：无 caption 时仍能视觉召回；视觉模型不可用时状态是 pending/missing/error 中的明确一种，不伪装 embedded。
3. **单图降级**：多图 query 中一张 VLM/embedding 失败，其他图片与文本召回继续；响应包含失败来源但不返回 500。
4. **重排安全**：image-only + lexical rerank 与不带 rerank 的视觉顺序一致；多模态 reranker 未启用时绝不按 gid 覆盖视觉排名。
5. **权限**：伪造请求体 tenant/ACL、跨租户 Object URI、无权 citation resolve、过期 URL、删除后旧 URL 全部不可用；PG 下推与 Rust 精确复核结果一致。
6. **一致性**：在 PG 写入、embedding 写穿、派生 commit、CDC advance 各点注入失败；重试/重启后收敛到 PG 真值，没有只存在于引擎的权威向量或媒资。
7. **真实质量**：至少 20 张图片和有难负例的文搜图/图搜图集合；分别记录 keyword/caption/vector/fusion 指标，换模型或权重必须过回归门禁。

## 9. 最终建议

FastGPT 最适合为 FastSearch 提供三类经验：**多模态检索编排、知识库摄取任务化、答案层引用生命周期**。FastSearch 应继续坚持自己的三项优势：**PG 真源与可重建派生索引、服务端不可绕过 ACL、带空间/时间坐标的安全 citation**。

建议实施顺序固定为：

```text
P0 运行真实性/PG生产档/权限默认/图片与重排正确性/真实评测
  → P1 多表示 + VLM caption + 具名N路融合 + 来源可解释
  → P2 PG job/worker可恢复摄取 +（按产品目标）来源与层级权限控制面
  → P3 音视频、多向量、学习排序
```

这条路线能吸收 FastGPT 已经验证过的产品经验，同时避免把其存储分裂、固定权重和可选鉴权语义带入 FastSearch 的底层不变量。

> **2026-08-24 复核后的实际起点**：P0 里**真正是 bug 的两条（P0-3、P0-4）已修完并收口**，
> 它们合计只动了两处编排逻辑 + 两个回归测试。剩下的 P0 条目都不是 bug：两条是待决策
> （FastSearch 要不要承担生产身份/运行档控制面），两条是需独立立项的大工程，
> 其中"真实跨模态质量门禁"依赖的 VLM 区域级路径**刚被仓内实测证伪**（§8-3）。
> 因此本路线图的下一个真实动作不是继续往下推 P1，而是**先答 §8 的两条 `[待决策]`**——
> 答案是否定的，P2 的整个控制面就该落在调用方产品，本路线图随之缩短一大截。
