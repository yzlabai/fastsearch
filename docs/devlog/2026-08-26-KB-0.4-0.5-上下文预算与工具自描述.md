## 为什么这条是 L0 的最后一块

agent 的稀缺资源是 context，不是磁盘。而 `search` 此前对**命中数与片段长度完全不设上限**，
`include_text` 一开就能冲爆调用方的上下文——这正是"方不方便用"的分水岭。
TS SDK 的 `formatHitsForLLM` 早有 `maxCharsPerHit`，但 **MCP 面完全没有**，
而 MCP 恰恰是 agent 直连的那张脸。

## 三个判断

### 1. 落点在 MCP 层，engine 一行不动

token/上下文预算是**答案层约束**。塞进通用 engine 的 top-k 会让"检索该返回什么"与
"调用方的上下文有多大"耦死——[FastGPT 参考建议 §5.2-5](../plans/2026-08-24-fastgpt知识库与多模态检索参考建议.md)
已经论证过，本次遵循该结论。

### 2. 旋钮叫 `max_context_chars`，**不叫 tokens**

spec 原文写的是 `max_context_chars|tokens`。选 chars，因为**本面没有分词器**——
吐一个 `estimated_tokens` 就是编造的数字，而"编一个看起来专业的估计值"正是本仓一路在修的那类事
（宣称 hybrid 实为 keyword、空 tags 静默变 public、探测字段名错了静默变 unknown）。
描述里直说："不是 token：本面没有分词器，估算 token 会是编造的数字。"

按**字符**而非字节计：CJK 一个字 3 字节，按字节算会离谱地高估。

### 3. 截断必须**对 agent 可见**，且确定

- 按融合后的既有顺序**前向累加**——不重排、不抽样 ⇒ 同输入必同结果（不变量 #4，测试断言两次调用逐字节相同）。
- 放不下整条时：还能留够 `MIN_HIT_CHARS`(80) 就**截断**并标 `text_truncated`，否则整条丢弃。
  一个被砍到只剩十几个字的片段对答案层没价值，却仍占一条 citation 的位置。
- 响应多出 `dropped`（丢弃条数）与 `context_chars`（实际用量）。**静默丢证据 = 让 agent 以为
  自己看到了全部**，那是本仓反复在修的那类错。
- **不设预算时响应形状与本能力落地前逐字节一致**（只有 `hits`），不给既有调用方平白多出字段。

## KB-0.5：描述要讲**本实例**，不是讲产品

agent 没有人类的试错直觉，只能读描述与错误文本。所以 `search` 的描述现在带一句作用域提示：
怎么限定集合（`filter` 的 `Eq("collection", …)`，MCP 不设 collection 入参）、可用 filter 字段
（collection / doc_id / kind / modality / page）。

远端档还会列出探到的集合名单，**必须带 caveat**："已注册（咨询性、可能不全——registry 是 server
进程内内存态、非真源）"。ADR《职责边界》已把内存 registry 定为"必须写进对外契约的 caveat"。
**本地档拿不到这个信息就什么都不说——编一个比不说更糟**（测试断言本地档描述里不出现"已注册"）。

## 一处旧契约的有意变更

`include_text` 此前在**拒绝**侧（`unadvertised_args_are_rejected_with_guidance` 钉着）。
KB-0.4 把它连同 `max_context_chars` 一起宣称——**两者必须同时进 schema 与允许清单**：
只放开 `include_text` 而不给预算，等于把冲爆上下文的开关递给 agent 却不给刹车。
测试已按新契约更新（`include_metadata` 顶替它留在拒绝侧）。
