# FS-301 `ingest_job` 存储与状态机开发日志

> 日期：2026-08-31
> 状态：✅ 完成
> 计划：[FS-301 实施计划](../plans/2026-08-31-FS-301-ingest-job存储与状态机.md)

## 交付结果

1. `fastsearch-pg` 新增一张普通 `fastsearch_ingest_jobs` 表：tenant/ACL 与 chunk 同构，保存原始对象 provenance、六状态、进度、lease、retry/error 和时间戳；不建产品对象、不进 publication、不依赖扩展。
2. 新增独立 `JobStore`，不复用 `PgStore` 的单连接锁。它提供 additive schema、enqueue/get、并发 claim、heartbeat、阶段推进、finish 和 fail；后续 worker 可按并发槽各建连接。
3. claim 以 `FOR UPDATE SKIP LOCKED` 原子领取并将 epoch+1；heartbeat/advance/finish/fail 全部校验 `job_id + lease_owner + lease_epoch + lease 未过期`。迟到 worker 不能靠心跳复活过期租约。
4. `IngestState` 固化六状态迁移；dead-letter 由 failed + retry 上限派生。退避为确定性指数策略，带稳定 ±25% 抖动并封顶五分钟。
5. 新作业输入 fail-closed：ACL 非空、SHA-256 为完整 64 位十六进制、max_retries 为正数、profile 为 JSON object；重复 job/doc 由存储层显式返回 conflict，幂等/覆盖策略留给 FS-302。

## 实库发现与修复

- 首轮 pgvector:pg17 执行发现租约毫秒占位符被 PG 推断为 `float8`，tokio-postgres 拒绝绑定 Rust `i64`。
  SQL 改为先 `$n::bigint` 接收，再转 `double precision` 计算秒，领取/心跳/推进/失败路径统一修复。
- 输入审查发现 `max_retries=0` 会形成既不可领取又不满足 dead-letter 派生条件的 queued 行，现由 Rust 校验和新表 CHECK 双层拒绝。
- publication 收敛用例继续使用独立临时数据库，避免固定 `fastsearch_pub` 与并行 PG 测试互相锁表。

## 验收结果

- 纯测试覆盖单表/无扩展/无 publication、身份列红线、claim 形态、全部 fencing SQL、状态迁移、死信和退避。
- Docker pgvector:pg17：两个独立连接并发 claim 得到不相交集合；过期租约重领 epoch+1；旧 owner/epoch 的 heartbeat、advance、finish 被拒绝；重试耗尽后不再领取。
- 从旧版最小作业表并发执行 additive schema，旧行与 ACL 保留，新列默认正确；误加入作业表后，chunks schema 将 publication 收敛回 chunks-only。
- workspace fmt 与 clippy `-D warnings` 通过；环境门禁 PG/CDC `executed=37 skipped=0 missing=0`，真实模型未配置，`executed=0 skipped=3 missing=0`。
- Standards / Spec 双轴初审发现的状态记账、公共 SQL 校验边界、持久化重开归属和 stale fail 实库覆盖均已修复；最终复审双 PASS。

## 范围边界

- 本项没有新增 server 路由、内存 job map、worker crate 或 MCP 工具。
- 无 PG 返回 503、上传幂等/覆盖、ACL 可见性和 job-scoped chunks 写入由 FS-302 实现。
- docparse 仍未进入 server/engine 热路径；独立 worker 与 adapter 下沉由 FS-303 实现。
