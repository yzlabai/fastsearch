## 为什么这条值钱

ADR《职责边界》把解析推给调用方。但**推出去职责却没交出契约**：非 Rust 调用方今天要
读 Rust 侧 `from_docparse_chunk` 的源码才能拼对 JSON。本仓自己的 `example/` 自建 chunker
+ SQLite 台账，就是这笔欠账的活证据。

## 做了什么

- **两个 SDK 各加一对 helper**（TS `chunksFromDocparse`/`chunkText`，Python 同名 snake_case）：
  字段映射表的**可执行版本**。
- **一份正式指南** [接入文档摄取](../接入文档摄取.md)（中/英），三条摄取路径 + 字段映射 +
  两个必踩的坑 + 明确写出"还不能做什么"。
- example 的自研 chunker 加指路注释（它引的是**已发布**的 npm 包 `^0.2.0`，而 helper 在
  本地 0.3——**不能改成用未发布的 API**，否则示例直接编译不过。等发版后删掉即可）。

## 写文档前先实测，抓到三处"照结构体推测会写错"的地方

这是前几轮教训的直接应用：**凡与外部实际接口对接的说明，先跑一遍再写**。

### 1. `media_bytes` 是**字节数组**，不是 base64 字符串

`core::Chunk.media_bytes: Option<Vec<u8>>` 用的是**默认 serde**，所以线缆形态是数字数组。
而解析器给的是 base64。实测：

```
{"media_bytes": "iVBORw0KGgo="}
→ 400 chunks[0]: invalid type: string "iVBORw0KGgo=", expected a sequence
```

这一步解码**必须做**，是手写 JSON 最容易踩的坑。两个 SDK 的 helper 都内建了，并各有单测钉死
（断言解出来的前四字节是 PNG 魔数 `[137,80,78,71]`）。

### 2. TS SDK 的 `Chunk` 类型**根本没有 `media_bytes`**

也就是说：**非 Rust 调用方用带类型的 SDK 根本表达不了 inline 图片字节**。已补进类型，
注释直接写明"是字节数组、不是 base64"。

### 3. `resolve_assets` 的 `url` 可能是**相对路径**

server 未配公网 base 时返回 `/v1/object/…/bytes?exp=…&sig=…`。直接 `urlopen` 会
`ValueError: unknown url type`。已写进指南——这正是非 Rust 调用方会撞上的那类事。

## 顺手修掉两个 SDK 里的"半个适配器"

读代码时发现**两个 SDK 的 `index()` 里都藏着半截映射**：`id`→`chunk_id`、补 `doc_id` 做了，
**图片三态没做** ⇒ 直接把解析器的 image chunk 丢进去会**静默丢掉图片字节**。
这正是"契约没交出去、每个人自己拼一半"的症状。已在两侧 docstring 写明本方法只做最小兜底、
完整适配用新 helper。

还有一处**教给调用方假象**的默认值：两个 SDK 都在客户端把 `acl` 默认成 `["public"]`，
而服务端 `apply_ingest_identity` **总是覆盖** tenant/acl ⇒ 这个值从来不起作用。

- Python：直接移除（对任何现役 server 都是行为中性的）。
- TS：`defaultAcl` 是**已发布的显式选项**，保留行为但在类型注释里写明"服务端会覆盖，
  设它不影响结果；要控可见性请换 key"。

两侧同时补上 `store_media`（Python 此前**没有**这个参数，等于无法选择图片字节存哪）。
