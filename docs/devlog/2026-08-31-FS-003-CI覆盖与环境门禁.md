## 1. 本轮结果

FS-003 将“代码里有测试”收紧为“CI 明确进入、执行情况可见、关键环境不可静默跳过”：

- 解析四档现已全部有常态门禁：`parse` 运行 clippy/测试，`parse-ocr`、`parse-tables`、`parse-vlm` 做编译检查。
- Python SDK 同时运行 `test_integrations.py` 和 `test_ingest.py`；example 独立 job 运行单测与 TypeScript 类型检查。
- 新增 MCP↔server 真二进制 e2e，不再仅依赖 mock HTTP 或库内单测。
- PG/CDC 与真模型 env-gated 测试统一输出 executed/skipped/missing；关键 CI 硬断言 PG/CDC 用例实际执行。
- `/readyz` 明确为进程级语义，不再用裸字符串 `ready` 暗示所有依赖已就绪。

## 2. CI 入口与防回归契约

`scripts/ci/check_workflow_contract.py` 直接检查 workflow 中的六个硬入口：

1. `parse-vlm` 编译门禁。
2. Python integration 与 ingest 两套测试。
3. `run_environment_gates.sh --require-pg`。
4. `mcp-server-e2e` job。
5. MCP/server e2e 执行脚本。
6. example job。

这不代替 GitHub Actions 自身，而是避免后续重构 workflow 时在 YAML 仍然合法的情况下静默丢掉验收入口。

## 3. 环境门禁记账

`scripts/ci/run_environment_gates.sh` 先运行 `cargo test --workspace -- --nocapture`，再按显式清单归类：

| 类别 | 用例数 | 本地无依赖结果 | CI 要求 |
|---|---:|---|---|
| PG/CDC | 20 | `executed=0 skipped=20 missing=0` | `--require-pg`：20 executed、0 skipped |
| 真模型 | 3 | `executed=0 skipped=3 missing=0` | 如实记账，不伪装已运行 |

`missing` 表示脚本清单与实际测试名称漂移，任何一项都会让 job 失败。

## 4. MCP↔server 真二进制链路

`scripts/ci/mcp_server_e2e.sh` 启动一个真 server，再用 key `a=acme:team-a` 和
`b=acme:team-b` 分别启动远程档 MCP stdio 进程。全链路验证：

- `/healthz` 与进程级 `/readyz`。
- `initialize` 和 `tools/list` 的实际能力声明。
- 两个 key 分别经 `index_chunks` 写入自己可见的 chunk。
- 同一查询下，两 key 只返回各自文档。
- key A 解析自己的 citation 得到 `found=true` 与正确 doc-render 位置；解析 key B 的 citation 得到 `found=false`。
- key A 的 MCP 命中 ID 序列与直连 REST 完全一致。

本地实跑结果：

```text
mcp-server-e2e: PASS (probe=1 index=2 search=2 resolve=2 acl_keys=2 rest_parity=1)
```

## 5. `/readyz` 语义

当前尚未建立统一的 PG/CDC/embedder 组件健康状态机，因此不伪造“全依赖就绪”。
`GET /readyz` 返回：

```json
{"ready":true,"scope":"process","dependencies_checked":false}
```

组件能力与真源状态仍由 `/v1/collections` introspection 和 `/metrics` 暴露。后续如引入组件级 readiness，需新增明确状态契约，不可在当前字段上静默改语义。
