# devlog 2026-08-26 — KB-2.2 第一步：N 路融合内核（契约零破坏）

> 上游：[KB-2.2 设计](../plans/2026-08-26-KB-2.2-N路具名融合设计.md) §4.2 的"第一步"。
> 本次只落**内核**：`fuse_n` + `RecallList`。**引擎仍然只喂两路**——见下面的诚实记账。

## 做了什么

`core::fusion` 加 `RecallList{source, weight, items}` 与 `fuse_n(lists, fusion)`；
原 `fuse(kw, sem, f)` 变成它的**两路特例**（一个薄壳）。

**序列化契约一个字节没动**：`Fusion` 枚举、`SearchRequest`、TS/Python SDK、REST body 全部原样。

## 一个比设计更进一步的发现

设计里把"加权档 N 路化"排在第二步，因为 `Normalized{semantic_ratio}` / `Weighted{alpha}`
是**结构性二路**的（一个标量分给两边）。实施时发现：**标量只是权重的一种表达方式**——
把权重挪到 `RecallList.weight` 上，加权档的**数学**立刻就是 N 路的，
只有"调用方怎么表达权重"还停在两路（那才是第二步要改的枚举）。

于是第一步实际交付的是**三种融合方法的完整 N 路内核**，而不只是 RRF：

```rust
Fusion::Normalized { .. } | Fusion::Weighted { .. } => {
    for l in order { for s in normalize(&l.items) {
        *acc.entry(s.id.clone()).or_insert(0.0) += l.weight * s.score;
    } }
}
```

两个加权档在这里**共用一份实现**——它们数学等价是 [2026-07-05 审查](../plans/2026-07-05-代码审查修复迭代计划.md)
记录在案的旧账，本次没有把重复搬进 N 路。

## 确定性：N 路化真正的坑

`fuse_n` **按 `source` 字典序遍历各路**再累加浮点，而不是按输入顺序。

理由不是洁癖：浮点加法不满足结合律，`(a+b)+c ≠ a+(b+c)` 的尾数差会传导到融合分，
进而改变名次。**两路时只有两个加数，这个坑根本冒不出头**；N 路化正是它出现的地方。

测试 `n_way_deterministic_under_list_shuffle` 对三路做全排列，断言
**`score.to_bits()` 逐位相同**——不是 `abs() < eps`。

## 最重要的一条测试

`n_way_matches_two_way_bitwise`：六种融合配置下，N 路实现喂两路必须与旧两路实现
**逐位相同**（同样用 `to_bits()`）。这是整个改动的回归锚——
只要它绿，三份 golden 基线就不该有任何偏移（实测确实全绿，基线一个字没改）。

`fuse` 的两路壳里把来源命名为 `keyword`/`vector`，正是为了让字典序累加顺序
与原实现一致（`keyword` < `vector`）⇒ 尾数不变。这一点写进了代码注释，
否则以后有人改名字会莫名其妙地让 golden 漂移。

## 诚实记账（重要）

**引擎侧仍然只喂两路。** `Engine::run` 的调用点未改——本次交付的是"**能**融 N 路"的内核，
不是"多路召回已上线"。真正产出 caption / 视觉信号是 KB-2.1（多信号子表）+ KB-1.3 的事，
两者都还没实施。

设计文档 §5 就写着这条约束，这里再记一次：**不得因为"支持 N 路"就宣称"多路召回已上线"**。
