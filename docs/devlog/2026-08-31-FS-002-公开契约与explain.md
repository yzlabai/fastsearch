# FS-002：公开契约一致性与 explain

> 日期：2026-08-31  
> 状态：完成  
> 对应计划：[FS-002](../plans/2026-08-30-迭代开发计划.md#fs-002-公开契约一致性与-explain-处理--2026-08-31)

## 1. 本轮结果

本轮把搜索接口从“各层各写一份字段清单”收敛为可自动核对的投影，并使既有的
`explain` 开关真正生效：

- Rust 内部、REST 外部和 MCP 工具使用同一份
  [`search-fields.json`](../contracts/search-fields.json) 作为字段集合依据。
- `Fusion` 新增加法兼容的 `weights` 具名权重档；旧 `rrf`、`normalized`、`weighted`
  请求保持可反序列化且行为不变。
- Engine 把现有召回路命名为 `keyword:user_text`、`vector:user_text`。
  `explain=true` 时命中返回各路 rank、归一化前 score、实际 contribution；默认关闭时
  `sources` 完全省略。
- OpenAPI、TS 和 Python SDK 补齐公开字段；MCP 对未声明字段明确拒绝。
- 修复 TS/Python 图片搜索参数的线上协议错误：SDK 对字节数组做 base64 编码并发送
  `query_image_base64`，不再发送 server 明确禁止的内部 `query_image`。

## 2. 契约边界

三层字段集合故意不完全相同：

| 面 | 图片字段 | explain/fusion | 策略 |
|---|---|---|---|
| Rust `SearchRequest` | `query_image` 字节 | 支持 | 进程内部模型 |
| REST / OpenAPI / SDK | `query_image_base64` | 支持 | 外部传输契约 |
| MCP `search` | 不开放图片 | 不开放 | schema/allowlist 声明的子集；其余字段明确报错 |

这不是“所有层字段强行相同”，而是每个公开面的投影必须可追踪、可测试，且不允许静默吞参。

## 3. 融合与解释语义

`fuse_n_with_sources` 先按 source 字典序处理召回路，再按 GlobalId 做最终同分裁决。
RRF 的 contribution 是 `1 / (rank_constant + rank)`；加权档的 contribution 是
`source_weight * min_max_normalized_score`。`SourceHit.score` 始终保留归一化前原始分。

`Normalized` 和 `Weighted` 没有改造成 serde 别名，而是原样保留为兼容成员；新
`Weights { weights, default_weight }` 作为枚举新成员加入。这样老 JSON 与已有 Rust 调用方
都不需要同时升级。

## 4. TDD 与回归证据

实施中先分别钉住以下失败面，再完成实现：

1. 具名权重不能反序列化、无法给出来源贡献。
2. Engine 接收 `explain=true` 但命中没有 `sources`。
3. OpenAPI 字段集合少于真实 REST 请求/响应。
4. TS/Python SDK 请求字段与 REST 矩阵不一致，图片字节发到了内部字段。
5. agent 适配器丢失 `sources` 元数据。

收口测试覆盖 core、engine、server、MCP、两套 SDK、工作区全量测试、clippy、格式检查、
golden 和真二进制 HTTP 冒烟；最终命令与结果记录在本次提交说明中。

## 5. 明确保留的后续工作

FS-002 只把公共契约和现有两路闭合，不代表多表示召回已经上线。以下仍属于 FS-201/FS-202：

- 从 `chunk_signal` 读取 `vector:image_caption` 等第三路及更多召回路。
- 在 explain provenance 中增加 signal 的 model/version。
- 增加多表示 golden，并在真实 Engine 中验收至少三路召回。

因此当前能力应表述为“支持 N 路具名融合内核，Engine 已接入两条现有 user_text 召回路”，
不能表述为“多路多模态召回完成”。
