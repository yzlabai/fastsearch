# devlog 2026-08-30 — FS-001 HNSW 随机门禁稳定化

> 上游：[迭代开发计划 FS-001](../plans/2026-08-30-迭代开发计划.md#fs-001-hnsw-测试确定性与召回门禁-2026-08-30)；spec 回写 [15-vector](../specs/15-vector.md) §6。

## 问题与结论

`hnsw::tests::ef_search_override_honored` 在同一 commit 的 20 次独立构图中通过 19 次、
失败 1 次，失败样本为 `default=0.85 high=0.85`（审计时也曾观测到
`default=0.56 high=0.56`）。上游 `hnsw_rs 0.3.4` 使用 `StdRng::from_os_rng()` 分配图层级，
公开 API 无法注入 seed。

根因是一个测试同时承担了两种不同性质：

- `ef_search` 覆盖是否生效，应在同一张图上做相对比较；
- 图的绝对召回质量，应使用独立 ground truth 和聚合样本门禁。

因此本轮不更改生产 HNSW 参数、图结构或快照格式；只修正测试定义。

## 实施

1. 保留 `recall_vs_brute_force` 作绝对质量门禁：固定 1,500 条 32 维语料、50 个查询、
   `k=10`，以 `MemVectorIndex` 作精确真值，聚合 500 个 top-k 判定，保持
   `recall@10 >= 0.90`。
2. `ef_search_override_honored` 只验证 ef 性质：同图从测试低档 `ef=10`
   逐查询覆盖到高档 `ef=512`，断言必须产生严格召回增益。
3. 该测试使用 `over_fetch=1`。旧测试的默认 `over_fetch=8` 会令 `k=10` 时
   `want=80`，继而用 `max(ef, want)` 把声明的低 ef 抬到 80，使参数差异被部分拉平。

## 统计门禁与验收

统计口径为“每次新建索引 = 一次独立 OS 随机构图”：

| 门禁 | 修复后结果 | 判定 |
|---|---:|---|
| 绝对 `recall@10 >= 0.90` | 100/100 | 通过 |
| `ef=512` 相对 `ef=10` 有严格召回增益 | 100/100 | 通过 |
| `cargo test --workspace` 连续执行 | 10/10 | 通过 |

100 次零失败时，按“rule of three”，对未观测失败率的单侧 95% 经验上界约为 3%。
这不把 HNSW 伪装成确定算法，但已消除原门禁约 5% 的实测随机红灯，且保留了
能识别建图质量回归的绝对阈值。两个测试都由 `cargo test --workspace` 在 CI 每次执行一次。

收口同时通过 `cargo fmt --all --check`、
`cargo clippy --workspace --all-targets -- -D warnings` 与上表的 workspace 连续门禁。

为验证门禁本身的灵敏度，曾在本地做突变测试：故意令 `search_with_ef` 忽略
`ef_search` 并始终传 `None`，专项立即按预期失败（`low=0.81 high=0.81`）。
撤回突变后恢复全绿，证明该断言会捕获“override 被忽略”回归。

## 取舍

- 不 vendor/修补 `hnsw_rs`，避免为测试 seed 承担一份 ANN fork 的长期维护成本。
- 不打开 `keep_pruned`/`extend_candidates` 或改大 M/`ef_construction`：这些都会改变生产构建成本、
  内存或召回曲线，当前证据不支持扩大修复范围。
- 不降低 0.90 召回阈值；只从 ef 行为测试移除了重复的绝对阈值。
