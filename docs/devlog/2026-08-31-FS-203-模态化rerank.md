# FS-203：模态化 rerank、保序降级与可解释原因

> 日期：2026-08-31
> 状态：已完成
> 计划：[FS-203 模态化 rerank](../plans/2026-08-31-FS-203-模态化rerank.md)

## 1. 交付结果

- `Reranker` 公开 `RerankCaps{text,image,cross_modal}`、`RerankInputKind`/类型化输入与 `RerankOutcome::Scores|Skipped`。
- `LexicalOverlapReranker` 明确为 text-only；query 分词为空返回 `EmptyQueryTokens`，不再伪造全零分。
- Engine 先复制 rerank 窗口，只有 capability 匹配、数量正确且分数全有限时才提交；不适用、后端错误和非法输出保留完整融合结果。
- 有效 rerank 等分以融合分为二级键、GID 为最终键；新 rerank 游标编码二级键，旧游标与未重排游标保持兼容。
- `SearchHit.rerank_explain` 在 explain 请求中返回 applied/skipped、模型标签和稳定原因；Server/OpenAPI/TS/Python agent metadata 同步。

## 2. TDD 证据

1. rerank 模块先因不存在 caps/类型化输入/Skipped 而编译红灯，再实现 Lexical text-only seam。
2. 纯标点 + `rerank.top_k=2` 对三条向量命中先错误截成两条；事务式临时窗口后恢复为与基线逐位一致的三条。
3. 文本查询 + 图片候选先被旧字符串接口重排成 GID 序；capability 整批守卫后保持向量序并解释 unsupported candidate。
4. 故障 adapter 首轮令 search 返回 error；改为 backend_error 保序降级。NaN/短数组首轮部分写分；校验前置后分别用有限短数组、正确长度 NaN、正确长度 Inf 证明完全拒绝。
5. 等分 adapter 首轮按 GID 覆盖向量序；融合二级键修复后又由分页测试发现旧游标重复命中，增加兼容的 rerank 复合游标后闭环。
6. OpenAPI、TypeScript Hit 和 TS/Python agent metadata 都以先失败测试证明契约缺口，再补实现。
7. 双轴 review 发现空白纯文本被误归为 Image；新增红灯后按“无图片/显式向量仍为 Text”修复，使 tokenizer 返回 `EmptyQueryTokens`。

## 3. Review 收口

- Spec 初审的 2 项已修：空白纯文本模态裁定；短数组、NaN、Inf 的独立拒绝证据。
- Standards 初审的 3 项 judgement call 已修：`RerankCaps::admit` 下沉整批能力规则；统一 `attach_rerank_explain`；内部 reason 改为序列化 `RerankExplainReason` enum，线上的 snake_case JSON 不变。
- 修复后再次执行 Standards/Spec 双轴复审：两轴均 PASS，无新问题、缺失需求或 scope creep。

## 4. 活服务验证

实际启动 `fastsearch-server`，经 `/v1/index` 写入三条预计算二维向量，令向量顺序为 `[3,2,1]`：

- `query="!!!"`、无 rerank：`[3,2,1]`；
- 同请求加 `rerank:{model:"lexical",top_k:2}`：仍为三条 `[3,2,1]`，全部 `rerank=null`，`rerank_explain.reason=empty_query_tokens`；
- `query="plain three"`：chunk 3 居首，全部 `rerank_explain.status=applied` 且有数值 rerank 分。

临时服务数据已移入废纸篓，进程已停止。

## 5. 兼容性与限制

- rerank 未请求或 `explain=false` 时不输出新字段；旧 REST/SDK 消费方不要求同步升级。
- 非 rerank 游标格式不变；parser 继续接受旧游标。rerank 新游标为不透明加法格式。
- 当前没有真实 image/cross-modal adapter，也不隐式批量读取候选媒资；capability 不等于已部署模型。
- `RerankSpec.model` 当前是请求/解释标签，不提供逐请求模型路由。
