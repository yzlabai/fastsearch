## 一、`POST /v1/assets/resolve` 丢 `time` —— 两个端点自相矛盾

**发现者**：A1（写 MCP spec 时对照两档 `resolve_citation` 的返回形状）。

`GET /v1/asset/{cid}` 的 `DocRender` 分支带 `"time": a.time`；而批量档
`POST /v1/assets/resolve` 的**三个分支全都没有**。同一个 `ResolvedAsset`、同一件事，
两个端点的契约不一致。

**为什么要紧**：`time`（`TimeSpan`）是音视频 citation 的深链锚点，与 PDF 的 page+bbox
同为一等 citation 维度（CLAUDE.md「数据模型锚点」）。而批量档**正是答案层一次解析多个引用要走的那条**
——也是 KB-0.2 远端模式 MCP 要代理的那条。所以受影响的恰恰是主路径。

**修法**：三个分支补 `"time": a.time`（`SignedUrl` 分支顺带补上此前也缺的 `media_type`）。
`match a.fetch` 是部分移动，`a.time`/`a.media_type` 仍可读，无需重构。

**测试** `assets_resolve_carries_time_like_single_asset_endpoint`：索引一条带 `TimeSpan` 的
音频 chunk，断言批量档返回 `time`，**并与单个档 `GET /v1/asset/{cid}` 的 `time` 逐字段相等**——
钉的不只是"有这个字段"，而是"两个端点对同一 citation 说同样的话"。

## 二、MCP 诚实契约的**反向**半边 —— `vector` 是暗门

**发现者**：A1（它把 KB-0.1 的契约补成双向，顺手指出我自己的实现只做了一半）。

KB-0.1 立的规矩是"schema 宣称的能力必须等于实际能力"，但只做了正向：
**不宣称做不到的**。A1 指出反向同样成立——**能兑现却不宣称的，是暗门**，调用方只能靠读源码发现。

据此 `vector` 入参是第二处违例：它真能走通（`reject_unavailable_mode` 明确放行，
`caller_supplied_vector_is_not_rejected` 测试就是背书），却不在 `inputSchema` 里。
对一个只能 keyword 的实例来说，这条恰恰是**唯一**能开出向量召回的路——藏起来最亏。

**修法**：`vector` 进 schema，且描述**按档位分叉**：无语义档时点破"这是在此开出
mode=vector/hybrid 的唯一途径，须与索引同模型同维度"；有语义档时它只是"跳过服务端嵌入"的旁路。
测试在 `tools_list_advertises_only_real_capability` 里加了反向断言。

## 三、CDC 旁表 DELETE 会**误删整个 chunk** —— 补形状守卫

**发现者**：A2（为回答"新表能不能进 publication"而读 `replication.rs`）。

`map()` 只按 `rel_oid` 取 Relation、**从不校验表身份**，而 `row_to_gid` 只需要
`collection`/`doc_id`/`chunk_id` 三列。设计中的 `chunk_signal` 主键**正好含这三列**
⇒ 它的一条 DELETE 会被映射成 `Change::Delete{gid}`，**把整个 chunk 从派生索引里删掉**。

不对称在于：Insert/Update 侧本就被 `row_to_chunk` 需要 `kind`/`text` 挡住（退化为确定性毒丸、
被 `decode_batch_lenient` 跳过），**只有 Delete 侧完全没有防护**。

**此前"安全"是碰巧**：DDL 用 `ALTER PUBLICATION … SET TABLE`（**替换**语义）使 publication 恒为单表。
那是安全网，不是设计。A2 也据此裁定「publication 永远单表」（见其设计文档 §3）。

**修法**：`relation_is_chunks(rel)` 按**声明的列集合**判（不看元组，因 Delete 在
REPLICA IDENTITY DEFAULT 下只带键列），要求 gid 三列 + `kind`/`text`；
Insert/Update/Delete 三个分支前置该守卫，非 chunks 形状 → `Ok(None)` 静默忽略
（**不是毒丸、不计死信**——旁表的变更本来就不关我们的事）。

**测试**两条，直接对 `map()` 单测（不必手搓 pgoutput 字节）：
`sibling_table_delete_is_ignored_not_mapped_to_chunk_delete`（造一张有 gid 三列 + `signal_type`
但无 `kind`/`text` 的旁表，断言 DELETE 被忽略）、`chunks_table_delete_still_maps`（守卫不得误伤）。

## 复盘

1. **三条 bug 全部来自"为写设计文档而读码"**，没有一条来自跑测试或用户报障。
   Wave 1 名义上的产出是三份 spec，实际最值钱的产出是这三条——**并行评审的收益主要在读，不在写**。
2. **两条是我自己刚写下的东西里的洞**：KB-0.1 的契约只做了一半、计划 §5.4 的 worker 写入口
   会静默错配 ACL（后者尚未实施，已在计划里改掉）。自己写的东西自己复核，抓不到这种。
3. **守卫的形态值得留意**：这次三条修复里有两条是"把碰巧的安全变成显式的"——
   `SET TABLE` 碰巧挡住了旁表、`vector` 碰巧能用但没人知道。与 Wave 1 里 A2/A3 用的
   「把不变量做成结构性保证」（穷尽 `match`、唯一索引）是同一种思路：
   **不要让正确性依赖于"目前恰好如此"**。
