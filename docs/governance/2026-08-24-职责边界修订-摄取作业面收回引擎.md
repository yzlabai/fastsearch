# 职责边界修订：把「文档摄取作业面」收回引擎

> 日期：2026-08-24 · 类型：决策记录（ADR **部分推翻并重立**）· 状态：**已决**
> 被修订：[职责边界：不承担生产身份与知识库控制面](2026-08-24-职责边界-不承担身份与控制面.md)
> —— **该 ADR 除本文明确推翻的一项外，全部继续有效。**
> 触发：[知识库引擎迭代计划 §5.0](../plans/2026-08-24-知识库引擎迭代计划.md)（推翻论证清单）

原 ADR 写明："若将来定位改为…本决策需显式推翻并重立——不要在没有推翻它的情况下，
顺着单个需求把控制面一点点做回来。" 本文即那份**显式记录**：只推翻一项，其余逐条钉死为继续有效。

---

## 1. 精确边界：推翻了什么、保留什么

| 原 ADR 列举的职责 | 本次处置 |
|---|---|
| **类别 1 · 生产身份控制面**：用户/组织/成员/角色（owner-read-write-manage）、权限继承、密钥全生命周期、登录与会话 | **全部保留**（仍归调用方，一项不动） |
| 类别 2 · Dataset/Collection/Source 的**产品对象** | **保留**（不做） |
| 类别 2 · **摄取任务队列** | 🔓 **推翻 —— 收回引擎** |
| 类别 2 · 摄取任务队列的 **UI** | **保留**（不做） |
| 类别 2 · 来源**版本与回滚** | **保留**（不做） |
| 类别 2 · 模型 profile 的**产品化管理** | **保留**（不做；引擎侧的 profile *记录* 属 provenance，不是产品化管理） |

**一句话**：收回的是**摄取过程的状态与可恢复性**，不是任何产品对象、层级、版本或权限模型。

---

## 2. "收回摄取作业面"的准确定义

引擎接受**原始文档字节 + 已认证身份**，负责把它变成可检索 chunk，并**如实报告这个过程的状态**。

**收回（引擎从此负责）**：
- 原始文档上传入口（字节落对象存储，返回作业标识）
- 摄取作业的持久状态机：queued / parsing / chunking / embedding / indexed / failed
- 可恢复性：租约、心跳、重试、死信、内容 hash 幂等
- 作业与文档处理状态的查询

**不收回（仍归调用方）**：
- 谁能创建/管理知识库，谁能看见谁的文档（身份与授权）
- Dataset/Collection/Source 的产品对象与层级
- 来源版本、回滚、定时同步、增量抓取
- 任何 UI

**一处判断（明确记下来，便于日后追责）**：`GET /v1/documents` 这类"文档列表 + 状态"端点，
本文定性为**对既有 chunk 行与作业行的派生只读视图**，**不新建产品对象表、不引入层级、不带版本**。
它落在推翻的一侧。若将来它开始长出"文档属于哪个 Dataset""谁是 owner""第几版"这类字段，
说明边界已被越过，按 §5 回滚。

## 3. 逐条回应原 ADR 的三条理由

### 理由 ①：它花的正是护城河的预算

**原文**：差异化是"只依赖 pgvector + 逻辑复制、因而能跑在任意托管 PG"；控制面意味着一批有状态表，
每张都要在 RDS/Supabase/Neon 上可移植、可迁移、可向后兼容升级。

**回应**：这条理由**对产品对象成立，对作业状态不成立**，因为两者的表面积差一个量级——
收回的是**一张表**（`ingest_job`）+ 两个端点 + 一个独立 worker 二进制，
不是 users/orgs/roles/datasets/versions 一批表。可移植性代价可界定且已知：
只用普通表 + `SELECT … FOR UPDATE SKIP LOCKED`（PG 9.5+ **核心**特性，非扩展），不碰 `shared_preload_libraries`。

**更关键的是反向论证：不收回同样在花护城河的预算，而且花得更冤。**
"以托管 PG 为真源、派生索引可重建、崩溃恢复靠重放"是本项目的核心卖点（不变量 #2），
但它今天**在摄取路径上是断的**：`/v1/index` 是一次同步 HTTP 请求内做完"嵌入 → 写 PG → 写派生索引"，
没有 job、没有恢复点、失败只返回 500。结果是每个调用方都必须自建重试与台账
（本仓 `example/` 自己写 chunker + SQLite 文档表，就是活证据）——
**等于把"崩溃安全"这条卖点，在整条链路最容易崩的一段外包了出去**。
这不是把预算从检索质量挪走，这是把已经付过的账补齐。

### 理由 ②：它会削弱已经守住的不变量

**原文**："ACL 不可绕过"之所以成立，恰恰**因为引擎对身份没有观点**——它只接受一个已认证 Principal 并强制注入。
一旦引擎自持 users/orgs/roles/继承，该不变量就退化为"ACL 的正确性 = 我们自研 RBAC 求值器的正确性"。

**回应**：这条理由**完全成立，且本次推翻不触碰它**——摄取作业面**继续对身份没有观点**。
作业行只存"已认证 Principal 编译出的 tenant/tags"，与 chunk 行今天存的完全同构；
不引入 owner、role、成员、继承、可见性规则。RBAC 求值器一行都不会出现。

**这条回应不是承诺，是靠 §4 的红线钉住的**：`ingest_job` 不得出现身份列；
上传端点必须走与 `/v1/index` 同款的 `apply_ingest_identity` 服务端注入；
"跳过成员鉴权"这类开关（FastGPT `authTmbId=false` 那种口子）在任何面上都不得存在。

**对价**：正因为本次把"引擎对身份没有观点"当作推翻 ① 的对价押了上去，
**KB-4（层级权限/角色/继承）的封禁比之前更强，而不是更弱**——它一旦启动，本文的回应即刻失效。

### 理由 ③：相邻轴上早已如此决定，且是更难的那一侧

**原文**：通用 chunk 管理 plan 已写死"Parsing and domain hierarchy remain caller responsibilities"，
解析比身份难推给调用方得多——更难的那个已经推出去了，把身份收进来是自相矛盾。

**回应**：**解析继续归调用方，这条不变**，所以不构成自相矛盾。本次收回的是**状态**，不是**算力**：
- 解析仍然发生在搜索进程之外（独立 `fastsearch-ingest-worker` 二进制）；
- CI 的 `hot-path-isolation` 门禁（`server/engine/core/text/vector` 五 crate `cargo tree` 零 docparse）**保持不变、保持绿**；
- 调用方仍可完全绕开引擎的摄取面，自己解析后直接 `POST /v1/index`——那条路一天都不会关。

且原 ADR 自己已经指出解析契约是产品表面（对身份契约的论证同理）。
[迭代计划 KB-1.4](../plans/2026-08-24-知识库引擎迭代计划.md) 把解析契约（文档 + SDK 适配 helper + example 改造）
交付到位，是本次推翻的**前置条件**：先把解析这条缝真正交出去，再谈把状态收回来。

## 4. 使本修订成立的硬约束（红线，违反即按 §5 回滚）

1. **`ingest_job` 无身份列**：不得出现 owner/role/member/group/继承关系；只有 `tenant` + `acl`（与 chunk 行同构）。
2. **不进 publication**：作业表不得进入 `fastsearch_pub`（否则 CDC 反馈环）。
   且须先解决现有 DDL 的 `ALTER PUBLICATION … SET TABLE`（**替换**语义）问题——
   任何在别处 `ADD TABLE` 的第二张表会在下次启动被静默移除，见[迭代计划 KB-2.1](../plans/2026-08-24-知识库引擎迭代计划.md)。
3. **托管 PG 可移植不破**（不变量 #1）：只用 pgvector + 逻辑复制 + 普通表能力（含 `FOR UPDATE SKIP LOCKED`），零原生扩展。
4. **热路径隔离不破**：解析只在独立 worker 二进制里发生，`hot-path-isolation` 持续绿。
5. **无 `DATABASE_URL` → 作业面一律 503**，与既有 `management_source` 一致；**不造第二个内存真源**。
6. **不新增产品对象**：无 dataset/source/version 表，无层级，无回滚。
7. **ACL 服务端注入不可绕过**（不变量 #3）：上传/作业/状态每个新入口都要有"越权用例进测试"。

---

## 5. 复审与回滚触发

出现以下任一情况，说明推翻的前提已不成立，应回滚本修订、恢复原 ADR 的完整效力：

- 作业面开始长出身份/角色/继承字段，或出现任何"跳过鉴权"开关；
- `GET /v1/documents` 开始携带产品对象语义（归属、owner、版本号）；
- 作业表的 schema 迁移在某个托管 PG（RDS/Supabase/Neon）上被证明不可向后兼容或不可回滚；
- worker 之外的 crate 出现 docparse 依赖（`hot-path-isolation` 变红）；
- 摄取面的维护成本开始明显挤占检索质量（KB-2 各项长期停滞）。

  P2-6（worker 与 server 独立部署/限流）复活；**P2-3（来源/集合控制面）、P2-5（层级权限）继续不做**；
  P2-4（collection registry 持久化）维持原 ADR 的定性：**写进对外契约的 caveat，不是待修 bug**。

- 原 ADR 的**类别 1 全部、类别 2 的其余四项**继续有效，不因本次修订而松动。
