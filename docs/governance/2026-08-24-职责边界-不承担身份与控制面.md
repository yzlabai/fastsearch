## 决定

FastSearch **不**承担以下两类职责，它们归**调用方产品**：

1. **生产身份控制面**：用户/组织/成员/角色（owner-read-write-manage）、权限继承、密钥全生命周期管理、
   登录与会话。
2. **知识库资源控制面**：Dataset/Collection/Source 的产品对象、摄取任务队列与其 UI、
   来源版本与回滚、模型 profile 的产品化管理。

FastSearch 继续只做：**以托管 PG 为真源的混合检索引擎** —— 接受已分块输入、派生可重建索引、
在服务端把**已认证身份**强制编译为不可绕过的 ACL、返回带 page/bbox/time 的安全 citation。

## 为什么

1. **它花的正是护城河的预算。** 定位原话是"外部单二进制混合检索引擎"，超越 ParadeDB 的关键是
   **只依赖 pgvector + 逻辑复制、因而能跑在任意托管 PG**（[产品设计文档](../plans/2026-06-24-产品设计文档.md)）。
   控制面意味着 users/orgs/roles/jobs 一批有状态表，每张都要在 RDS/Supabase/Neon 上可移植、
   可迁移、可向后兼容升级。这份预算投到一个竞争点在 UI、且 FastGPT/Dify/RAGFlow 已领先数年的轴上，
   是最差的资源配置。

2. **它会削弱已经守住的不变量。** "ACL 不可绕过"之所以成立，恰恰**因为引擎对身份没有观点**——
   它只接受一个已认证 Principal 并强制注入。一旦引擎自持 users/orgs/roles/继承，该不变量就退化为
   "ACL 的正确性 = 我们自研 RBAC 求值器的正确性"，正确性面积大一个量级。
   参考建议里点名"绝不能照搬"的 FastGPT `authTmbId=false` 分支，正是自持控制面必然长出的那种口子。

3. **相邻轴上早已如此决定，且是更难的那一侧。**
   [通用 chunk 管理 plan](../plans/2026-07-23-generic-chunk-management-api.md) 已写死：
   *"Parsing and domain hierarchy remain caller responsibilities"*，目标用户是
   *"callers that already own chunking"*。解析比身份难推给调用方得多——更难的那个已经推出去了，
   把身份收进来是自相矛盾。

## 这个决定**不**豁免什么（重要）

不拥有身份**不等于**可以对身份和运行档含糊其辞。恰恰相反：

1. **fail-closed 的优先级因此上升，而不是下降。** 既然 100% 依赖调用方接对，就**绝不能在调用方
   没接对时替他编一个**。故：未配置 keys 不得自造管理密钥；身份没有 ACL 标签不得替他默认公开。
   见 [plan](../plans/2026-08-24-fail-closed默认与运行档如实标注.md)。
2. **运行档必须如实可观测。** "生产必须配 PG"是可以拒绝的策略；但"本实例有无真源、能否从真源重建"
   属**不变量 #2 + 诚实记账**，必须在启动日志/introspection/metrics 里如实暴露。同上 plan。
3. **身份契约升格为一等交付物。** 调用方拥有身份 ⇒ "请求凭据 → Principal"这条缝是对四张脸
   （REST/库/MCP/CLI）的产品表面。当前整条缝是一个 `;` 分隔的环境变量（`parse_keys`），
   撑不过密钥轮换、大量租户、每请求从 JWT 取用户身份等真实需求。
   **正确的最小动作不是控制面，是一个身份适配 trait**（凭据 → `Principal`，env 表作默认实现）。
   **暂不实施**——等第一个真实调用方提出形状再做，现在做属于猜。记在这里以免被忘记。
4. **内存 collection registry 从"待修 bug"降级为"必须写进对外契约的 caveat"**：
   多副本各持一份、非真源、dim 校验仅咨询性。
