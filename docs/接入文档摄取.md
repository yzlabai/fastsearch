# 接入文档摄取（给非 Rust 调用方）

> 🌏 English: [connecting-document-ingestion.md](connecting-document-ingestion.md)
>
> fastsearch 的契约是：**调用方拥有解析与分块，引擎拥有检索**
> （见 [职责边界 ADR](governance/2026-08-24-职责边界-不承担身份与控制面.md)）。
> 既然把解析推给调用方，就得把**契约**交出去——本文就是那份契约。
> 本文所有字段与错误信息都经过**实跑验证**，不是照着结构体推测的。

---

## TL;DR

```python
from fastsearch_client import FastsearchClient, chunks_from_docparse, chunk_text
c = FastsearchClient(base_url="http://127.0.0.1:8642", api_key="dev")

# ① 有解析器（推荐）：任意工具产出 chunk → 适配 → 索引
c.index("kb", "report.pdf", chunks_from_docparse(parsed, doc_id="report.pdf"),
        store_media="object")

# ② 纯文本 / markdown：直接切
c.index("kb", "notes.md", chunk_text(text, doc_id="notes.md"))
```

TypeScript 同名 API：`chunksFromDocparse(parsed, { docId })` / `chunkText(text, { docId })`。

---

## 一、三条摄取路径，选一条

| 路径 | 谁解析 | 什么时候用 |
|---|---|---|
| **A. 自带解析器 + SDK 适配** | 你（任意语言/工具） | 有 PDF/DOCX 等真实文档，要 page/bbox 溯源 |
| **B. 纯文本 / markdown** | 无 | 粘贴的文本、笔记、已经是纯文本的数据源 |
| **C. Rust CLI 一条命令** | `fastsearch ingest`（进程内 docparse） | 你能跑 Rust 二进制，见[文件解析与摄取](文件解析与摄取.md) |

A 和 B 都走同一个终点：`POST /v1/index`。

---

## 二、路径 A：解析 → 适配 → 索引

### 1. 拿到 chunk

用任何能输出"带坐标的块"的工具。本仓 vendor 了一个现成的（docparse），它自带 REST 服务：

```bash
# vendor/docparse 是被根 exclude 的独立 workspace，必须指 manifest-path。
# 注意它默认端口也是 8642，与 fastsearch-server 撞，显式换一个。
cargo run --manifest-path vendor/docparse/Cargo.toml -p docparse-cli -- serve --port 8700
curl -F file=@report.pdf "http://127.0.0.1:8700/parse?format=chunks&images=embedded"
```

> 该服务**无鉴权**、默认只绑 `127.0.0.1`（同机信任模型）。当内部解析微服务用，别直接暴露。

也可以用 MinerU、Unstructured、自家管线——只要产出的对象能对上下面的字段表。

### 2. 字段映射（**只有三处要动**）

两侧 schema 刻意同构。SDK 的 `chunks_from_docparse` / `chunksFromDocparse` 就是这张表的可执行版本：

| 解析器输出 | fastsearch chunk | 说明 |
|---|---|---|
| `id` | `chunk_id` | **唯一的重命名** |
| `kind` / `text` / `page` / `bbox` / `heading_path` / `section_id` / `char_len` | 同名同义 | 直通 |
| `image.data_base64` | `media.asset = {"kind":"inline"}` + **`media_bytes`** | 见下面的坑 |
| `image.file` | `media.asset = {"kind":"object","uri":…}` | 字节已在对象存储 |
| （图片但两者皆无） | `media.asset = {"kind":"doc_region","page":…,"bbox":…}` | 只能跳回原文位置 |
| — | `doc_id` | 由你注入（解析器不知道文档标识） |

### 3. ⚠️ 最容易踩的坑：`media_bytes` 是**字节数组**，不是 base64 字符串

解析器给的是 base64，fastsearch 要的是字节数组。**必须解码**，否则：

```json
{"media_bytes": "iVBORw0KGgo="}
```
```
400 Failed to deserialize the JSON body into the target type:
    chunks[0]: invalid type: string "iVBORw0KGgo=", expected a sequence
```

正确形态是 `"media_bytes": [137, 80, 78, 71, ...]`。用 SDK helper 就不会碰到这个。

### 4. ⚠️ **不要在 chunk 里设 `tenant` / `acl`**

服务端按 API Key 强制注入并覆盖它们（`apply_ingest_identity`），你设的值一律无效。
要控制可见性，**换一把对应的 key**。

> MCP 面的 `index_chunks` 工具更严格：夹带 `tenant`/`acl` 会**直接拒绝**而不是静默覆盖——
> 静默覆盖会让调用方以为自己控制了可见性。

### 5. `store_media`：字节存哪

| 值 | 行为 |
|---|---|
| `"auto"`（服务端默认） | 有对象存储就上传，否则 inline 进真源 |
| `"object"` | 上传对象存储，chunk 里换成 `Object{uri}` |
| `"inline"` | 字节随 chunk 进真源（PG `bytea`）。**需要配 `DATABASE_URL`**，否则 `/v1/asset` 对 inline 一律 404 |
| `"none"` | 丢弃字节，只留坐标 |

体积注意：server 的 body 上限是 **20MB**，整本 PDF 的 inline base64 很容易超。

## 三、路径 B：纯文本 / markdown

```python
chunks = chunk_text(text, doc_id="notes.md", target_chars=900, overlap=80)
```

空行分段聚合到 `target_chars`；markdown 标题（`# …`）维护 `heading_path` 并自成一块；
`overlap > 0` 时相邻块首尾相接，避免答案正好被切在块边界上。

> **坐标是占位的**：`page=1`、`bbox` 全 0 —— 纯文本没有版面。
> 想让 `resolve_citation` 在原文里高亮，必须走路径 A。这点不说清，很容易以为自己拿到了可溯源坐标。

## 四、验证摄取成功

```python
hits = c.search("kb", "毛利率", top_k=5)
# → [{'citation_id': 'kb:report.pdf:2', 'page': 3, 'bbox': {...}, ...}]

asset = c.resolve_assets(["kb:report.pdf:2"])[0]
# → {'type': 'object', 'url': '/v1/object/…/bytes?exp=…&sig=…', 'expires_s': 300}
```

⚠️ **`url` 可能是相对路径**（server 未配公网 base 时），要自己拼上 base URL 再取。

## 五、还不能做什么（诚实记账）

- **不能把原始文件丢给 server**：没有上传端点，`/v1/index` 只收切好的 chunk。
  作业面（上传 + 状态查询）见[知识库引擎迭代计划 KB-3](plans/2026-08-24-知识库引擎迭代计划.md)，设计完成、未实施。
- **没有文档台账**：`GET /v1/chunks?collection=&doc_id=` 要先知道 `doc_id`，且**需要配 PG**（否则 503）。
  "列出这个库里有哪些文档"目前归调用方自己存。
- **`Rgb8`/`Gray8` 栅格图**经 Rust CLI 摄取时拿不到字节（需 PNG 重编码，见迭代计划 §10-8）；
  自带解析器不受此限——你给什么字节就是什么。
