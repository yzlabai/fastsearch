# fastsearch 阶段性项目情况说明

> 日期：2026-08-30  
> 审计基线：`main` / `3e136d1`（与 `origin/main` 同步）  
> 范围：根 workspace、`clients/`、`example/`、`vendor/docparse` 接线、CI、部署制品、`docs/plans` 36 份计划文档  
> 口径：代码是事实源；“代码存在”“本机测试通过”“真实外部依赖验证”“生产验证”分开记账。

## 1. 结论摘要

fastsearch 已经不是概念验证：项目形成了完整的 Rust workspace，具备全文、向量、混合检索、ACL、引用溯源、PG 真源与 CDC、REST/CLI/MCP、Python/TypeScript SDK、文档解析接线和多种向量后端。Agent 使用面的基础读写闭环已经成立。

但项目仍是一个**功能丰富、主链路可用的 0.1.0**，不能据现状认定为原始产品文档所定义的“1.0 GA 完善产品”。主要原因有五项：

1. `chunk_signal` 多表示和 `ingest_job` 摄取作业面只有设计、没有源码实现。
2. N 路融合只有内核，Engine 仍只投喂 keyword/vector 两路；`explain` 是公开字段但没有实际结果。
3. CDC 仍有 PK UPDATE、TRUNCATE、半状态原子性和 slot 并发首建等已知正确性债务。
4. 本轮没有真实 PostgreSQL、真实嵌入模型、真实对象存储或 K8s 验收，部分测试会在环境变量缺失时提前返回并被 cargo 计为 `ok`。
5. 版本、发布、文档治理尚未收口：所有 Rust crate 仍为 `0.1.0`、无 Git tag、根目录缺少正式 `LICENSE`，多份计划顶部状态与代码事实冲突。

因此，当前最合适的阶段判断是：

| 能力线 | 阶段判断 | 说明 |
|---|---|---|
| L0 Agent 易用 | **基本闭合** | MCP 能探测能力、远端检索、写 chunk、控制字符预算并溯源 |
| L1 摄取保真 | **部分完成** | 十类轻解析、OCR/表格/VLM 接线、JPEG/Encoded 图片字节已通；profile、自然图 caption、RGB/Gray 编码未闭合 |
| L2 表示完备 | **未完成** | PG 仍是一条 chunk 一个 `embedding/embed_model`，无 `chunk_signal` |
| L3 检索质量 | **部分完成** | 两路混合检索和 N 路融合内核存在；具名权重、来源解释、模态化 rerank、真实跨模态门禁未完成 |
| L4 运维诚实 | **部分完成** | fail-closed、能力探测、metrics 已有；readiness、WAL/slot 健康、真实环境常态验证不足 |
| L5 摄取作业面 | **未完成** | 无上传文档端点、job 表、状态端点和独立 worker |

## 2. 项目规模与工程形态

### 2.1 仓库快照

- Rust workspace 有 12 个 crate，成员定义见 [`Cargo.toml`](../../Cargo.toml#L7)。
- `crates/` 下 Rust 代码约 29,048 行；SDK 与 example 的 Python/TypeScript 代码约 4,257 行。
- vendored docparse Rust 代码约 25,289 行，保持独立 workspace，通过 CLI feature 接入。
- `docs/` 约 15,424 行，其中 `docs/plans` 36 份、`docs/specs` 14 份、`docs/devlog` 35 份。
- 当前仓库共 441 个 commit；2026-06-25 fastsearch 主体启动后约 199 个 commit。
- `main` 与 `origin/main` 同步，审计开始时 worktree clean。
- Rust crate 统一版本 `0.1.0`；TS SDK `0.3.0`；Python SDK `0.2.0`；没有 Git tag。

规模说明只用于判断工程复杂度，不等于成熟度。当前文档量已经很大，但状态回写没有形成可靠的单一真源，见 §7。

### 2.2 架构现状

当前主链路是：

```text
文件/chunk → CLI/docparse 或外部调用方解析 → REST 写入
                                        ↓
                         PostgreSQL + pgvector 真源
                                        ↓ CDC / snapshot
                Tantivy BM25 + VectorStore 派生索引
                                        ↓
                   Engine 融合/重排/ACL/citation
                                        ↓
                       REST / CLI / MCP / SDK
```

架构中最重要的已落实边界：

- PG 侧只要求 pgvector 与逻辑复制，DDL 入口集中在 [`fastsearch-pg/src/sql.rs`](../../crates/fastsearch-pg/src/sql.rs#L31)。
- ACL 由服务端身份注入，不接受客户端放宽；router 和鉴权入口见 [`fastsearch-server/src/lib.rs`](../../crates/fastsearch-server/src/lib.rs#L600)。
- docparse 被根 workspace 排除，默认搜索热路径不引入 ONNX/解析重依赖，见 [`Cargo.toml`](../../Cargo.toml#L1) 与 CI 的 `hot-path-isolation`。
- CLI 是 REST 客户端；MCP 支持远端模式，避免另养一套文本嵌入编排。
- 派生索引支持快照和 LSN 检查点；CDC 当前采用 SQL polling，而不是 `START_REPLICATION` 流式连接。

## 3. 已落实的主要能力

### 3.1 检索与数据模型

- Chunk 已含 tenant、ACL、metadata、searchable、page/bbox、heading/section、media/time 等字段，见 [`model.rs`](../../crates/fastsearch-core/src/model.rs#L239)。
- 查询支持 keyword/vector/hybrid、过滤、rerank、collapse、深分页、高亮和分面，见 [`query.rs`](../../crates/fastsearch-core/src/query.rs#L43)。
- 文本后端具备 BM25、jieba CJK、短语/slop、前缀检索和过滤/ACL 双重守卫。
- 向量侧具备 Brute、二值/RaBitQ/FHT、HNSW、TurboQuant 与 f32 sidecar，实际枚举见 [`fastsearch-vector/src/lib.rs`](../../crates/fastsearch-vector/src/lib.rs#L29)。
- 引擎已实现混合融合、rerank、auto-merge、collapse、search-after、more-like-this、引用解析和对象媒资读取。

### 3.2 真源、同步与服务面

- PG chunks 真源、pgvector ANN、publication、doc/chunk 管理 SQL 已落地。
- 初始快照、派生索引持久化、检查点和崩溃安全的 `peek → persist → advance` 主路径已存在。
- CDC 已实现 pgoutput 解码、TOAST 回源和旁表 DELETE 形状守卫，见 [`replication.rs`](../../crates/fastsearch-sync/src/replication.rs#L239)。
- REST 已覆盖 search、similar、asset、index、chunk CRUD、image、document delete、collection 等端点，见 [`server router`](../../crates/fastsearch-server/src/lib.rs#L609)。
- MCP 已覆盖 search、resolve_citation、远端档 `index_chunks`、能力自描述和字符预算，入口见 [`fastsearch-mcp/src/lib.rs`](../../crates/fastsearch-mcp/src/lib.rs#L218)。

### 3.3 文档摄取与多模态地基

- CLI 的 `parse` 档接入 PDF、DOCX、HTML、MD、CSV、XLSX、PPTX、SRT、EML 与图片。
- `parse-ocr`、`parse-tables`、`parse-vlm` 均可编译；真实模型能力仍受外部资源门控。
- 文档图的 JPEG/Encoded 原始字节已能进入媒资通道；RGB8/Gray8 仍被诚实标为 `missing_bytes`。
- 图片 query、caption-as-text、多模态 metadata/citation、对象存储抽象和签名媒资 URL 的代码路径已存在。
- 真实图文同空间检索仍未得到当前环境的质量验证，不能把 HashEmbedder 基线称为生产级跨模态检索。

### 4.2 已实证的测试稳定性风险

后台全量审计首次运行 workspace test 时，`hnsw::tests::ef_search_override_honored` 出现：

```text
default=0.56 high=0.56
```

而测试要求高 `ef_search` 召回率至少为 0.9，断言位于 [`hnsw.rs`](../../crates/fastsearch-vector/src/hnsw.rs#L632)。HNSW 实现说明建图随机种子来自 OS，见同文件顶部说明。后续针对同一测试连续执行 20 次，在第 14 次再次失败（`default=0.85 high=0.85`），结果为 **19/20 通过、1/20 失败**；另一个 HNSW recall 测试连续 20 次均通过。由此可确认它是**低频但可重复出现的随机门禁风险**，不是稳定的功能失败，也不是单次环境噪声。

处理原则：不应直接把阈值降到 0.56；应固定可控随机源，或把门禁改为稳定数据集上的多次统计，同时保留有效的召回下限。

### 4.3 本轮未完成的真实环境验证

本机没有 `DATABASE_URL`。多个 PG/CDC 测试在函数内发现环境变量缺失后直接返回，例如 [`fastsearch-pg/src/lib.rs`](../../crates/fastsearch-pg/src/lib.rs#L889) 和 [`cdc_closed_loop.rs`](../../crates/fastsearch-engine/tests/cdc_closed_loop.rs#L76)。cargo 会把这种返回显示为 `ok`。

因此，本轮 379 passed **不能解释为**：

- 本轮真实 PG/pgvector/逻辑复制已通过；
- 本轮真实 Ollama/OpenAI 兼容嵌入服务已通过；
- 本轮真实 S3/MinIO、OvisOCR2、OCR/UniRec 模型已通过；
- 本轮 K8s 多副本或生产流量已通过。

CI 配置会启动 pgvector 容器并执行 workspace test，这比本地结果更强；但本次审计没有联网读取某次 CI run 的状态，不能替代为当前运行证据。

## 5. 尚未完成的需求与技术债

### 5.1 P0：可信度与公开契约

1. **HNSW 测试随机失败**：会造成 CI 偶发红，必须先稳定。
2. **`explain` 静默失效**：字段已在 [`SearchRequest`](../../crates/fastsearch-core/src/query.rs#L92) 声明，但 `SearchHit` 没有 sources/contribution，Engine 也未消费该开关。
3. **OpenAPI/SDK/运行契约缺少统一校验**：OpenAPI 未完整描述 `explain` 等现有结构；需要字段级契约测试。
4. **CI 漏项**：`parse-vlm` 未进 CI，Python `test_ingest.py` 未进 CI，MCP↔server 缺真二进制 e2e。
5. **发布合规缺口**：根目录声明 Apache-2.0，但没有根 `LICENSE`/`NOTICE`；无 tag/CHANGELOG/release workflow。

### 5.2 P1：CDC 正确性与并发

以下项目在 [`2026-07-06-代码审查-剩余迭代项`](../plans/2026-07-06-代码审查-剩余迭代项.md) 中已有记录，源码仍未闭合：

- 主键 UPDATE 只取新 tuple，旧 GlobalId 可能成为幽灵命中。
- TRUNCATE 被映射层忽略，PG 清空后派生索引可能继续返回旧数据。
- text upsert 发生在 embedding/PG 写穿之前，后续失败可能留下可被其他 commit 带出的半状态。
- `Applier` 的公开 LSN 水位说明与生产路径实际用法不一致。
- `ensure_slot` 使用 `WHERE NOT EXISTS`，多副本并发首启有 TOCTOU。
- CDC/快照逐 chunk 同步调用 embedder，并持有全局 Engine 锁，批量导入会阻塞查询。

### 5.3 P1：知识库主计划未闭合项

- **KB-0.4-SDK**：MCP 有总字符预算；TS 只有格式化辅助，Python 无同等总预算旋钮。
- **KB-1.2**：分块 profile、target/overlap 暴露与 provenance 未实现。
- **KB-1.3**：自然图 VLM caption 未接；源码仍明确记为下一迭代。
- **KB-2.1**：无 `chunk_signal` 表、API、失效规则实现或真实 PG 测试。
- **KB-2.2 第二步**：`fuse_n` 已有，但 Fusion 仍为旧二路表达，Engine 只喂两路，`explain` 未落地。
- **KB-2.3**：reranker 只有文本能力，缺模态 capability 和编排守卫。
- **KB-2.5**：当前多模态 golden 主要证明 caption/transcript 文本检索，不是真实图文向量质量门禁。
- **KB-3.1–3.5**：无 `ingest_job` DDL、`/v1/documents`、`/v1/jobs/{id}`、独立 worker、MCP `ingest_document`。
- **KB-4**：按 ADR 明确封禁，不计作当前欠债。

### 5.4 P2：生产化与产品能力缺口

- collection registry 仍为进程内 HashMap，不持久、不跨副本。
- `/readyz` 无条件返回 `ready`，未汇总 PG/CDC/embed/index 健康。
- Engine 使用单一 `tokio::Mutex`，检索、写入、CDC 争用同一锁；已有基准显示向量路径延迟落后 Qdrant 约 5–7 倍。
- CDC 仍是 SQL polling；缺流式复制、keepalive/feedback、WAL lag 与 slot 健康治理。
- 查询能力尚缺 typo/同义词/停用词管理、did-you-mean、query expansion 等原始需求项。
- 分面只覆盖有限字段，并基于候选窗口统计；collection 声明的 dot/l2 距离没有真实后端语义。
- 大文件仍受 20MB body limit；无分片或预签名上传作业面。
- 真实 S3/MinIO、真实跨模态模型、OvisOCR2 四道质量门、ColPali、视频精定位、Helm/HA/蓝绿重建均未完成当前验收。

## 6. 质量与治理评价

### 做得好的部分

- 模块边界清楚，核心 trait 和 crate 分层较稳定。
- 安全不变量被反复测试：ACL 服务端注入、对象路径校验、token 签名、过滤后精确守卫均有覆盖。
- 对外部模型和重依赖采用 feature/env gating，基本遵守“无法验证就不宣称”的原则。
- 相关性 golden、clippy `-D warnings`、热路径隔离、SDK 和 Docker build 均进入 CI。
- 设计文档经常能反向发现实现漏洞，体现出良好的审查习惯。

### 需要改善的部分

- 计划/设计/状态散落在大量文档中，顶部状态和正文回写经常互相矛盾。
- 环境门控测试用提前 `return` 表达“skip”，cargo 输出却显示 `ok`，容易误读完成度。
- 单文件过大：`fastsearch-server/src/lib.rs` 已超过 6,000 行，handler、OpenAPI、测试混在一起，继续扩 KB-3 会显著增加变更风险。
- 主要提交高度集中于单一贡献者，架构知识和发布流程的人员冗余较低。
- 发布元数据不完整，与 README 中的 Apache-2.0 声明不匹配。

## 8. 阶段结论与下一步

当前可以对外稳定表达的是：**fastsearch 已具备可运行的全文/向量/混合检索内核和 Agent 基础接入面，适合继续做受控试用与工程化迭代；尚不具备 1.0 GA 的发布、摄取作业、真实多表示检索和完整生产运维保证。**

后续执行顺序见 [`2026-08-30-迭代开发计划`](../plans/2026-08-30-迭代开发计划.md)。第一轮必须先处理测试与契约可信度，再进入 CDC、`chunk_signal` 和 KB-3，不建议跳过正确性债务直接建设新作业面。
